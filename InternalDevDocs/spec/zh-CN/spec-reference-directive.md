## 概述
[summary]: #summary

本规范定义 Visual Basic 脚本方言（scripting dialect）的 `#R` 引用指令：一条为一次脚本编译点名一个程序集（assembly）的指令。`#R` **不是一项语言特性**。它是一对契约。编译器一侧把 `#R "…"` 做成一种指令 trivia，它只在脚本方言（`SourceCodeKind.Script`）中合法，并且只能位于编译单元首个 token 之前。宿主（host）一侧定义操作数（operand）字符串的含义：语言从不解释它，而由宿主提供的引用解析器决定该操作数指称哪个程序集、或哪些程序集。

该指令的效果是一组元数据引用（metadata reference）。一条 `#R` 可以贡献不止一条引用：索引 0 是该操作数所点名的**主资产（primary asset）**，其余各项是该资产的**依赖闭包（dependency closure）**。每一条被贡献的引用都是这次编译的一条显式引用（explicit reference），而一个提交会继承上一个提交的显式引用，所以闭包中的类型在后续提交里仍然可用，无需再来一条指令。

引用可以携带别名（alias）。脚本宿主用 `<host>` 为宿主对象的程序集取别名，并用 `<implicit>` 为用来替代缺失依赖的那个程序集取别名；编译器尊重这些别名，所以一个被取别名程序集的元数据在源码层面不可见，除非它经由全局别名暴露出来。Visual Basic 没有 `extern alias` 构造，因此携带非全局别名的引用根本无法从 Visual Basic 源码触及。

C# 的对应物是 C# 脚本的 `#r` 指令，它共有那两条界定性的性质：语言不解释操作数，且指令必须先于首个 token。`.vbx` 文件的对应物是一个 C# 脚本（`.csx`），不是一个文件式程序。

`#R "nuget:…"` 与 `#R "project:…"` 操作数前缀是本指令的宿主扩展。它们的语义在本规范的范围之外。

## 动机
[motivation]: #motivation

脚本文件没有工程文件，也不自带命令行：既没有 `<Reference Include="…" />` 元素，也没有附在该文件上的 `/r:` 选项。因此源文本自身必须能够点名脚本所使用的程序集。`#R` 就是这个机制：它是脚本方言唯一的源码层程序集引用，而包引用与工程引用两种形式是同一条指令的操作数前缀。

该指令有三条性质具备契约的形状，必须写明，而不能留给读者。

第一，**操作数没有语言含义**。`#R "System.Text.RegularExpressions"` 与 `#R "…\libs\Contoso.dll"` 是同一种语法；差别完全在于宿主如何解析这个字符串。一份只描述示例的规范会把实际的搜索顺序、以及其中依赖机器的部分留白不谈。

第二，**解析顺序由操作数字符串的形状决定**，不以任何声明决定。区分文件路径与程序集名的判据纯是文本性的，它使 `System.Text.RegularExpressions` 与 `System.Text.RegularExpressions.dll` 为同一个程序集走上不同的搜索路径。读者无法从语言规范推出这一点，而两种形式解析到不同结果时编译器也不报任何诊断。

第三，**别名规则改变存在哪些名字**。被宿主取了别名的一条引用不把自己的命名空间贡献给非限定查找。这条规则的症状不是一条二义性错误，而是一个看起来不存在的名字，正因如此该规则必须写明而不能靠摸索。

## 详细设计
[design]: #detailed-design

### 该指令

引用指令（reference directive）是一种条件编译指令（conditional-compilation directive），由 `#` 引出，后跟关键字 `R`：

```ANTLR
referenceDirective
    : '#' 'R' stringLiteral
    ;
```

关键字按不区分大小写匹配，因此 `#r` 与 `#R` 是同一条指令。操作数是一个字符串字面量 token 且必不可少；缺少操作数的指令是一个语法错误，且不被收集。指令在逻辑行的起始处被识别，其前可有可选的空白。

该指令由 `ReferenceDirectiveTriviaSyntax` 节点表示，它派生自 `DirectiveTriviaSyntax`，带有一个 `ReferenceKeyword` 子节点和一个类型为 `StringLiteralToken` 的 `File` 子节点。语法 kind 为 `ReferenceDirectiveTrivia`。因为该指令是 trivia 而非语句，它独占一行，后续诊断的行号不会漂移。

**决策**：拼写定为 `#R`，并且不再定义其他拼写别名。同一条指令出现第二种拼写，就等于同一件事的第二种做法，而已发布的拼写必须对那些已经在使用它的脚本保持稳定。

### 模式门控

引用指令只在脚本方言中合法。普通编译（ordinary compilation）中的 `#R` 是一个错误；该指令仍会被解析并作为 trivia 消费，因此树保持良构，文件的其余部分照常解析。

```vbnet
' Compiled as ordinary code, not as a script:
#R "System.Text.RegularExpressions"   ' Error BC36964: #R is only allowed in scripts
```

指令从每一棵源码 kind 不是 `Regular` 的树中收集，而[收集与增量再绑定](#collection-and-incremental-rebinding)一节所述的那枚失效标志只对源码 kind 为 `Script` 的树置起。

### 位置：头部指令

`#R` 是一条**头部指令（head directive）**：它只在编译单元首个 token 的前导 trivia（leading trivia）中被识别。跟在任何 token 之后的 `#R` 仍会作为指令被解析，报一个错误，并且不被收集。

```vbnet
Dim x = 1
#R "System.Text.RegularExpressions"   ' Error BC36959: cannot use #r after first token in file
```

位置判据是「首个 token 之前」，而不是「位置 0」：注释、空白以及其他头部指令可以出现在 `#R` 之前，`#R` 写在首个 token 之前的任意一行都被接受。

语言的指令模型并不统一，本规范把这一区分明确写出：

| 指令 | 类别 | 位置判据 |
|---|---|---|
| `#If`、`#Const`、`#Else`、`#End If`、`#Region`、`#ExternalSource`、`#Disable Warning` | 自由位置 | 任意逻辑行边界，受块结构约束 |
| `#R`、`#Load` | 头部 | 编译单元首个 token 的前导 trivia |
| `#!` | 头部 | 文件的位置 0 |

**决策**：两类头部指令判据不同，是有意的。shebang 由操作系统内核读取，内核要求它的两个字符是文件的前两个字节；`#R` 与 `#Load` 是在编译开始之前配置编译，只需先于任何 token。因此脚本作者应当预期：写在语句之后的 `#R` 是一个错误，而不是一条被静默忽略的指令。

### 空操作数

操作数为空字符串的指令在进入声明表之前就被丢弃：它不是一条指令，不贡献引用，也不报诊断。

```vbnet
#R ""   ' Okay: no operation
```

**决策**：这是有意的空操作，并且它镜像 C# 编译器——后者的声明表构造器施加同一条判据。空操作数不是解析失败，而是操作数的缺席。改为报一条诊断将是对 C# 的分叉，需要它自己的理由与语言版本门控。

### 禁用的条件编译区域

位于被假 `#If` 排除的条件区域之内的 `#R` 完全不会被识别为指令。扫描器把整个禁用区域（disabled region）作为单一条禁用文本 trivia 消费，因此不产生指令节点，也不报诊断。模式检查与位置检查只适用于活动区域中的指令。这与适用于 shebang 指令的是同一条边界。

### 收集与增量再绑定 <a id="collection-and-incremental-rebinding"></a>

指令是在构建声明表（declaration table）时收集的，不是在绑定时收集的。声明树构造器遍历编译单元的引用指令，丢弃其字符串字面量带有诊断或其值文本为空的那些，并把余下的作为操作数文本连同该指令的源码位置一起记录在根声明上。声明表把所有根声明的指令合并成这次编译的指令集合。收集对每一棵非 `Regular` 树发生；一棵 `Regular` 树贡献空集合。

编译把收集到的指令暴露出来，并把它们的存在当作一枚失效标志来使用。当一棵语法树的源码 kind 为 `Script` 且至少含有一个 `#R` 时，该树报告自己含有引用指令。增删或替换一棵树会累积那枚标志，而编译只在标志为假时才复用自己的引用管理器（reference manager）。

那枚标志回答的是「这棵树是否含有 `#R`」，而不是「指令集合是否变了」。把一棵含 `#R` 的树替换成一棵含有完全相同 `#R` 的树，仍然会重建引用绑定。

**决策**：这一失效判定有意是粗粒度的。正确性要求指令集合的变化绝不被漏掉，而声明表能够在任何绑定发生之前判定引用集合可能已经变了，这正是让编译得以避开重新绑定引用的原因。其代价——编辑一个含有 `#R` 的脚本会重建引用管理器——是一条已知的性能边界，不是缺陷。

### 宿主解析器契约

操作数字符串由经编译选项提供的 `MetadataReferenceResolver` 解释。编译器请该解析器解析操作数，以含有该指令的语法树的文件路径作为基准路径，并以启用递归别名的方式请求程序集引用，因此施加在一条指令引用上的别名会传播到它所引用的那些程序集。

解析器由宿主挑选，并取决于编译以何种方式运行：

- **脚本运行器。** 脚本运行器安装命令行引用解析器，它解析操作数可能包含的任何路径或程序集名。
- **普通编译。** 为产出程序集而被调起的编译器安装的解析器把指令引用限制在命令行上已经提供的那些程序集之内。它先解析操作数，然后只保留程序集标识与那些引用中的某一个相匹配的结果。

**决策**：普通编译中的这条限制是有意为之。当一个脚本被纳入一个工程时，`#R` 不得引入一个该工程未声明的依赖。因此同一条指令在两种宿主下的触达范围不同，而这是两种宿主的性质，不是这条指令的缺陷。

### 解析顺序

当脚本宿主的解析器被要求解析一个操作数时，它按下列顺序查找。任何一步产出引用，查找即停止。

1. **包前缀。** 若操作数带有宿主包解析器所识别的包引用前缀，解析即委托给那个解析器。若宿主没有配置包解析器，该指令解析为零条引用，查找也不再继续。该前缀的语义在本规范范围之外。
2. **路径。** 否则，若按下面的判据该操作数是一个文件路径：
   1. 若操作数不含目录分隔符且可信平台程序集（trusted-platform-assembly，TPA）表可用，在该表中按操作数去掉扩展名后的文件名查找；
   2. 否则，或者第 1 步未命中，则把操作数作为路径解析，依次相对于基准路径、相对于宿主的基目录、相对于每一处已配置的搜索路径。
3. **程序集名。** 否则，在全局程序集缓存（global assembly cache，GAC）中查找该操作数，然后把它解析为一个程序集显示名，并在 TPA 表中查找它的简单名。

若没有任何一步产出引用，该指令解析为零条引用，编译器在该指令上报 BC2017，"could not find library '{0}'"。

**路径判据。** 当一个操作数的扩展名——最后一个目录分隔符之后、最后一个句点之后的那段文本——是 `.dll` 或 `.exe`（按不区分大小写比较），**或者**它含有一个目录分隔符（`\` 或 `/`）时，它是一个文件路径。该判据不是「含不含分隔符」：`System.Text.RegularExpressions.dll` 是一个路径，尽管它一个分隔符也没有；`System.Text.RegularExpressions` 不是一个路径，尽管它看起来像，因为它的扩展名是 `.RegularExpressions`。因此加上或去掉 `.dll` 会改变哪些搜索步骤被执行，而两种情形下编译器都不报诊断。

**缺失的程序集。** 操作数本身按上述顺序解析。一个被引用程序集的、编译在其他情况下并未引用的依赖，则由一条**独立的**契约、按一个**不同的**顺序解析：

1. 全局程序集缓存，仅限强名标识；
2. TPA 表，按简单名；
3. 声明了该依赖的那条引用所在的目录。

**决策**：两条顺序分别规定，不作统一。操作数是作者写下的，所以路径这条分支要查找作者的目录和已配置的搜索路径；缺失的依赖是在读取元数据的过程中发现的，所以它的查找止于声明它的那个程序集。一个必须在给定宿主下解析结果相同的脚本，应当写一个相对于该脚本的路径，或者写该宿主平台程序集中某个程序集的裸名；一个指望在全局程序集缓存中找到的裸程序集显示名是不可复现的。

### 一条指令，若干引用

一个解析器对单个操作数可以返回不止一条引用。返回的第一条引用是主资产——操作数所点名的那个程序集——其余引用是该资产的依赖闭包。每一条返回的引用都被加入这次编译的显式引用，并且全部锚定在同一条指令的位置上，按解析器返回它们的顺序排列。

编译器内部维护的逐指令映射——它不属于公共 API——对每条指令只保存主资产。它回答的是「这条指令点名的是哪个程序集」，不是「这条指令贡献了哪些引用」。

由指令贡献的完整集合可通过公共的 `Compilation.DirectiveReferences` 与 `Compilation.References` 观察。出现在那个视图里的一条引用未必是源文件所点名的程序集：闭包中的一项是由源文件写下的一条指令贡献的，但它所属的程序集并未在源文件中拼出。

**去重。** 当两条指令有着相同的操作数文本和相同的所在文件路径时，它们是同一条指令；第二次出现不再被解析。一棵没有文件路径的树以空字符串充当文件路径分量，所以在同一次编译的两棵无路径树里操作数文本相同的两条指令会被当作重复项，只解析一次。一条解析到已被引用的程序集上的指令是允许的，不是一个错误。

引用集合按注册顺序的逆序枚举。该数组先是存放一次编译的指令引用，然后是它的外部引用，然后是从上一个提交继承来的显式引用，因此继承来的引用最先注册，外部引用其次，指令引用最后。一个本次编译已经引用了的项——例如因为某条外部引用点名了同一个文件——会被去重：它不保留指令位置（它的位置是 `Location.None`），也不出现在 `Compilation.DirectiveReferences` 中。因此，闭包中的一项能否通过指令视图观察到，取决于这次编译是否已经引用了它。

### 跨提交继承

每个提交都是一次独立的编译，而一个提交的引用集合包含上一个提交的每一条显式引用。因此，由此前某个提交里的一条指令引入的闭包，在后续提交里仍然可用，无需重复那条指令。

引用是**继承**的；`Imports` 是**累积**的。宿主在延续一个脚本时会清空引用与导入，然后经由各自的机制重新施加它们：引用集合随编译链前行，而一条 `Imports` 子句由宿主在每个提交上重放。二者不得互相替着描述。

### 引用别名

一条元数据引用可以携带别名。编译器尊重它们：一个别名为空、或者别名中包含 `global` 的程序集，把它的全局命名空间贡献给合并后的命名空间；而携带任何其他别名的程序集则不贡献。别名由宿主或工具链（toolchain）施加到一条引用上；没有任何源码构造能附加一个别名。

脚本宿主施加两个别名：

- **`<host>`** 施加于宿主对象的程序集，并带递归别名。它把宿主对象的命名空间与全局类型挡在脚本的非限定查找之外。
- **`<implicit>`** 施加于解析器用来替代缺失依赖的那个程序集。它让这个程序集能够满足一个程序集标识，而不把它的类型并入全局命名空间——否则那些类型可能把一个原本无二义的名字变得有二义。

**没有逃生口。** Visual Basic 没有 `extern alias` 构造，编译器也不提供其他能够点名被取别名引用的语法。因此，一条携带非全局别名的引用无法从 Visual Basic 源码触及：这种遮蔽是绝对的。「绝对」修饰的是那条引用，不是那个程序集，也不是那个结果——本规则决定哪些引用被并入全局命名空间，所以为同一份元数据再添加一条未取别名的引用，就能让那个名字重新可及。与 C# 的不对称也不像初看那样宽：C# 的 `extern alias` 能触及一条携带标识符别名的引用，但脚本宿主自己施加的那两个别名 `<host>` 与 `<implicit>` 不是合法的标识符，因而同样在它能力之外。

这种遮蔽没有属于自己的诊断。对一个被非全局别名遮蔽的命名空间写 `Imports`，报出的警告与对一个并不存在的命名空间写 `Imports` 相同——同一个 ID（`BC40056`）、同一条消息模板、报在被导入的名字上——于是二者只在消息所引用的那个名字上有差别。同一个诊断码与同一条模板还覆盖第三种起因：一个存在但不含任何公开成员的命名空间（该模板名为 `UndefinedOrEmpty`，它的文本把两种情形都点了出来）。那条诊断中没有任何东西提示「引用别名」是这个名字够不着的原因：消息自带的建议（"Make sure the imported element name doesn't use any aliases"）说的是 `Imports` 别名，那是作者写下、也能由作者改动的；而引用别名由宿主或工具链施加，任何源码动作都移除不了它。这条诊断没有被特化，是因为作者无法创建一个别名、只能被一个别名影响：该条件属于编译环境而不属于源文本，所以没有任何源码层面的动作是一条针对别名的专属消息能指引作者去做的。

有两条限定约束上面那句话。共用同一个 ID 这一点就源层面的 `Imports` 子句成立；因同一原因失败的一个工程层面导入报为 `BC40057`，是另一个诊断码配另一条消息。而且这条警告只在没有任何未取别名的引用提供那个名字时才出现：当另一条引用贡献了同一个名字的命名空间时，该子句绑定到它上面，根本不作任何诊断——被取别名引用的类型面就只是从那个名字上缺席，对此不作任何说明。第二种情形才是这种遮蔽唯一真正无声的形式。另需注意，这条警告是被产生的，未必是被送达的：脚本入口点只在某个提交没有编译错误时，才把该提交的警告呈现出来。

**普通编译使用同一条规则。** 别名过滤器并非脚本专属。在 `/nostdlib` 之下，命令行编译器把一条非全局别名施加在它用于替代那些门面程序集的真实核心库上，从而使该库的类型面不并入全局命名空间，"type not defined" 错误的集合保持不变。因此该过滤器对普通编译同样是功能性语义。

### `#R` 不导入命名空间

引用指令把程序集加入编译。它不将任何命名空间带入作用域，也不让任何类型名可以非限定地取用。做这件事的构造是 `Imports`。

```vbnet
#R "System.Text.RegularExpressions"

Dim m = Regex.Match("vbi 2.0", "\d+\.\d+")   ' Error BC30451: 'Regex' is not declared
```

```vbnet
#R "System.Text.RegularExpressions"
Imports System.Text.RegularExpressions

Dim m = Regex.Match("vbi 2.0", "\d+\.\d+")   ' Okay
```

这两个构造互补：`#R` 是程序集那一面，`Imports` 是名字那一面。一个需要一个库的脚本通常两样都需要。

### 运行时加载与提前编译

当一个提交被编译时，脚本宿主向它的程序集加载器登记每一条引用：它遍历已绑定的引用管理器所引用的那些程序集，并把每一条有文件路径的引用的文件路径登记下来，以程序集标识为键。一条指令所贡献的每一条引用——主资产与闭包——都被登记，正是这一点使闭包中的类型能在后续提交里于运行时可用。在运行时，宿主按标识解析程序集，而不是按指令解析。

一个脚本提交被编译为一个内存中的程序集，动态加载，并针对以对象数组传入的状态执行。它处在提前编译（ahead-of-time compilation）与裁剪（trimming）的范围之外，引用指令也不自带任何提前编译或裁剪上的阻力。

### 错误

| 诊断码 | 诊断 | 条件 |
|---|---|---|
| BC36964 | `ERR_ReferenceDirectiveOnlyAllowedInScripts` | `#R` 出现在普通编译中。消息："#R is only allowed in scripts" |
| BC36959 | `ERR_PPReferenceFollowsToken` | `#R` 出现在编译单元首个 token 之后。消息："Cannot use #r after first token in file" |
| BC2017 | `ERR_LibNotFound` | 解析器对一条活动指令未产生任何引用。消息："could not find library '{0}'" |
| BC37002 | `ERR_PPLoadFollowsToken` | `#Load` 出现在编译单元首个 token 之后。消息："Cannot use #Load after first token in file" |

模式错误与位置错误互斥：模式检查先应用，因此普通编译中的 `#R` 无论位置是否正确都报 BC36964。BC37002 是姊妹头部指令 `#Load` 的位置错误；两条指令共用同一条位置规则，只在所报的诊断码上不同。

### 与 C# 实现的对齐

本指令的 C# 对应物是 C# 脚本的 `#r` 指令。二者共有那两条界定性的性质：语言不解释操作数，且指令必须先于编译单元的首个 token。模式门控与空操作数过滤器同样对齐。

| 维度 | C# | Visual Basic |
|---|---|---|
| 引用指令 | `#r "…"`（C# 脚本） | `#R "…"`（`ReferenceDirectiveTrivia`） |
| 操作数是否由语言解释 | 否 | 否 |
| 位置约束 | 首个 token 之前 | 首个 token 之前 |
| 模式门控 | 脚本之外报 CS7011 | 脚本之外报 BC36964 |
| 位置错误 | CS7009 | BC36959 |
| 空操作数 | 丢弃 | 丢弃 |
| 包引用形式 | 被忽略指令 `#:package id@version`，以及脚本形式 `#r "nuget:…"` | 操作数前缀 `#R "nuget:…"` |

三处差异不得混为一谈。从 C# 14 的 [ignored-directives] 提案引来的那条位置规则属于被忽略指令 `#!` 与 `#:`，不属于 `#r`；`#r` 的位置检查是 C# `#r` 实现的一部分。该 ignored-directives 提案还施加了一条 C# `#r` 所没有的约束——一条被忽略的指令必须先于任何 `#if`——而 C# `#r` 与 Visual Basic `#R` 都没有这条约束。最后，C# 的被忽略指令只在文件式程序解析选项下才合法，而 Visual Basic 没有文件式程序模式；`.vbx` 文件的对应物是一个 C# 脚本，而 `#R "nuget:…"` 与 `#:package id@version` 不可互换。

## 健全性
[soundness]: #soundness

该指令不引入任何新的绑定规则。它只改变一次编译所引用的程序集集合，而语言已经定义了引用集合如何影响名字查找。因此增加一条指令只能通过引入一个语言已经会处理的二义性来改变既有代码的含义，不能通过改变任何既有构造的含义来做到。

两道门控使该指令的触达范围清晰明确。普通编译中的 `#R` 是一个错误，所以没有任何普通程序能在编译器不报的情况下依赖宿主解析。一条位置错误的 `#R` 会得到诊断且不被收集，所以一次编译的引用集合恰好就是它的各棵脚本树的首个 token 的前导 trivia 中的那些指令的集合。

就名字查找而言别名是健全的，因为它被统一施加：同一条判据对每一条引用决定它的全局命名空间是否参与合并。非全局别名唯一的制造者是宿主与工具链，所以作者可能受影响的那种局面无法由源码制造出来。

## 缺点
[drawbacks]: #drawbacks

- **同一条指令在两种宿主下含义不同。** 脚本运行器解析任何路径或名字；普通编译只保留命令行已经提供的引用。因此一个被挪进工程的脚本会失败，或者解析到另一个程序集上，而任何语言改动都消不掉这道落差。
- **裸名解析取决于宿主进程。** 同一条指令在不同机器上可以解析到不同的程序集，且没有任何诊断。脚本不是自含的；它的引用集合有一部分是它所运行的环境的性质。
- **相对路径取决于启动上下文。** 一个路径操作数以脚本的文件路径、宿主的基目录以及已配置的搜索路径为基准解析，所以挪动脚本或从另一个目录启动宿主都会改变结果。
- **一条指令不再与一条引用一一对应。** 一条指令所贡献的各条引用共享它的位置，于是关于闭包中某一项的诊断——包括一次元数据读取失败——指向的是那条指令，而不是闭包内部的某个位置，而逐指令映射只暴露主资产。锚定在指令上胜过一条没有位置的诊断，但诊断锚定的是源文件写下的那条指令，而不是那个失败的程序集。从公共视图重建一次编译的引用集合的工具，会看到源文件从未点名过的程序集。
- **别名是绝对的。** 一条携带非全局别名的引用无法从源码触及，而其症状是一个看起来并不存在的名字。没有任何语法是作者能用来把它找回的。
- **失效是粗粒度的。** 对一棵含有 `#R` 的树的任何编辑都会重建引用绑定，因为那枚标志记录的是一条指令的存在，而不是指令集合的变化。

## 替代方案
[alternatives]: #alternatives

- **在宿主里剥掉 `#R` 行，并把它们换算成命令行的引用选项。** 已否决：它会让每一条诊断的行号偏移，在宿主里复述一遍解析器的位置与模式判断，并把这条指令从编辑器和语言服务器面前藏起来——它们看到的是与编译器同一棵树。同样的理由也否决了对 shebang 指令做宿主侧剥离。
- **让一条指令在普通编译中解析任意的路径与名字。** 已否决：普通编译宿主有意把指令引用限制在命令行所提供的程序集之内，从而使「把一个脚本纳入一个工程」不可能引入一个未声明的依赖。
- **保留每条指令一条引用的上限。** 已否决：包引用与工程引用两种形式都需要一条指令在一步之内贡献一个主资产及其依赖闭包。多引用解析对零条与一条引用的结果保持蛰伏，也不改动逐指令视图，因此它纯粹是叠加性的。
- **不给宿主引用与被替代引用取别名。** 已否决：宿主别名之所以存在，是为了把宿主对象的命名空间与全局类型挡在非限定查找之外；隐式别名则是为了不让一个被替代进来的程序集把类型并入全局命名空间而造出二义性。去掉其中任一个都会改变脚本里哪些名字能解析成功。
- **在绑定时收集指令，而不在声明表里收集。** 已否决：声明表能够在任何绑定发生之前判定引用集合可能已经变了，正因此一次编译才能复用它的引用管理器。在绑定时刻收集会导致每次编译都重新绑定引用。
- **把 `#Load` 用于程序集引用。** 不适用：`#Load` 把源文件纳入同一次编译，并不添加程序集引用。
- **为空操作数报一条诊断。** 未采纳：空操作数在两种语言里都是空操作，报一条诊断将是对 C# 的分叉，需要它自己的理由与语言版本门控。

## 考量
[considerations]: #considerations

### 为什么这不是一项语言特性

语言规范的指令模型涵盖条件编译、外部源与区域；它没有源层面的程序集引用语法，编译单元的文法里也没有留给指令的位置。程序集引用是编译环境的性质，`#R` 以同样方式留在语言之外：它是 trivia，只在脚本方言中合法，在普通编译里是一个错误而不是引用程序集的第二种做法。正是这一落位，让本指令的操作数可以由宿主定义，而语言不必依存于任何特定的包模型或文件系统模型。

### 操作数的可复现性

因为操作数的含义依存于宿主，操作数形式的选择就是一项可移植性决定。一个搜索顺序包含全局程序集缓存或不限定的平台查找的形式，在不同宿主下可能解析到不同结果；一个相对于该脚本的路径，或者宿主平台程序集中某个程序集的裸名，在那个宿主下是可复现的。本规范写出精确的顺序，好让读者能判断哪些形式依存于宿主，而不必从示例里去猜。

### 逐指令视图与完整视图

两个不同的问题不得混为一谈。「这条指令点名的是哪个程序集」由编译器内部的逐指令映射回答，它保存主资产；那张映射不属于公共 API，所以需要作者意图的工具通过语法树的指令 API 直接读取那些指令本身。「这次编译从指令那里得到了哪些引用」由公共的指令引用视图回答，它包含每一条由指令贡献且未被去重的引用。

## 测试
[testing]: #testing

本特性由进程内的无副作用测试来验证：它们不进行网络访问、不启动进程、不访问注册表，也不在隔离的临时目录之外写文件。测试夹具是测试程序集本身、在内存中构建的程序集，或者发射到按测试准备的临时目录中的程序集。

- **解析测试。** 一条点名磁盘上某个库的指令，让该库的类型在同一个提交里可用，也在同一会话的后续提交里可用。同一条指令写两遍会被接受，并且只贡献一次引用。点名一个不存在文件的指令在该指令上报 BC2017。一个被引用库的、住在同一目录里的依赖无需自己的指令即可解析。
- **多引用测试。** 解析器返回一个主资产加一个闭包的那条指令，使闭包中的类型在一个不重复任何指令的后续提交里可被绑定。两条各自展开为一个有效主资产与一条不可读引用的指令，在它们自己所在的那一行上报 BC31519，而夹在二者之间的一条寻常指令不受影响。
- **指令解析测试。** 一个 shebang、一条引用指令与一条加载指令共存于同一个脚本文件：三者都能解析，各自都能通过各自的指令 API 被发现，而被加载的代码得以运行。
- **零回归测试。** 一个寻常脚本，其指令点名一个平台程序集，在没有配置任何包解析器的情况下通过交互这条接缝完成编译并运行，也不会尝试任何还原。
