## 概述
[summary]: #summary

本规范定义 Visual Basic 脚本方言（scripting dialect）的 `#Load` 源码加载指令：一条把另一个脚本文件的源码纳入同一个提交（submission）的指令。`#Load` **不是一项语言特性**。它是一对契约。编译器一侧把 `#Load "…"` 做成一种指令 trivia，它只在脚本方言（`SourceCodeKind.Script`）中合法，并且只能位于编译单元首个 token 之前。宿主（host）一侧定义操作数（operand）字符串的含义、以及到底是否会加载任何内容：语言从不解释操作数，而展开该指令的宿主会把每个被点名的文件解析为各自的语法树，并把得到的树集合作为一个提交一起提交。

该指令的效果是一组语法树，不是一组引用。一棵被加载的树是一棵普通的脚本树：它的顶层（top-level）声明与发起加载的那个文件的顶层声明成为同一个脚本类（script class）的成员，它的顶层语句汇入同一个初始化器，它与该提交共享引用集合与解析选项，而它的诊断带着它自己的文件路径与行号。该指令本身在编译器一侧没有任何状态——它不进入声明表，也不使引用管理器失效——所以一次编译从一个 `#Load` 上学到的唯一东西，就是宿主决定作为树传进来的那些内容。

展开是宿主的义务。直接由一棵含有 `#Load` 的树构造出的编译，相对该指令是惰性的：被加载文件的声明并不存在，也没有任何诊断说明这一点。这是本指令最值得写明的一条性质，因为它在源码中不可见，很容易被误当作缺陷。

被加载的树排在点名它们的那棵树之前，而提交结果由最后一棵树决定，所以一个被 `#Load` 的文件无法靠写一个末尾表达式来改变提交结果。任何一棵树里的 `Return` 都会返回整个提交；在一个带类型的提交中，该值就是进程退出码。

C# 的对应物是 C# 脚本的 `#load` 指令。它共有那两条界定性的性质——语言不解释操作数，且指令必须先于首个 token——但它在编译对象内部展开，并按解析后的路径去重。`.vbx` 文件的对应物是一个 C# 脚本（`.csx`），不是一个文件式程序。

## 动机
[motivation]: #motivation

脚本文件没有工程文件，也不自带命令行：既没有 `<Compile Include="…" />` 元素，也没有一个可以把多个文件组装起来的构建步骤。因此源文本自身必须能够点名构成这个程序的其他文件，`#Load` 就是这个机制。它回答了脚本作者每天都会遇到的三个问题——被加载文件的成员能否由发起加载的文件调用、哪个文件的顶层语句先运行、一条诊断指向哪个文件——所以这些答案必须写明，而不能靠摸索得来。

该指令有四条性质具备契约的形状，必须予以陈述。

第一，**操作数没有语言含义**。`#Load "helpers.vbx"` 与 `#Load "…/lib/helpers.vbx"` 是同一种语法；差别完全在于宿主如何解析这个字符串。一份只描述示例的规范会把搜索顺序、以及其中依赖机器的部分留白不谈。

第二，**没有宿主展开时该指令是惰性的**。编译器解析并保留该指令，它也报告语法与模式上的违规，但它从不加载文件。直接调用编译构造 API 的消费者会得到一次编译，其中该指令什么都没做，也没有任何诊断说明此事。把这项义务明确写出，正是防止后来的读者去「修好」一个只实现了一半的展开的办法。

第三，**该指令不是引用**。`#R` 与 `#Load` 共享一种语法形状、一条位置规则、一道模式门控，也常被放在一起描述；但 `#R` 进入声明表并改变引用集合，而 `#Load` 改变树的集合。把 `#Load` 描述成第二种引用会直接导向一个错误的实现——一个源码引用无法承载顶层语句、脚本类的部分或初始化器条目。

第四，**文件的同一性是宿主环境的性质**。相对操作数以写下该指令的文件为基准解析，所以挪动一个脚本、或者经由另一个文件加载它，都会改变实际加载的内容。树被提交的顺序同样由宿主决定，而它决定的正是顶层执行的先后。

## 详细设计
[design]: #detailed-design

### 该指令

加载指令（load directive）是一种条件编译指令（conditional-compilation directive），由 `#` 引出，后跟关键字 `Load`：

```ANTLR
loadDirective
    : '#' 'Load' stringLiteral
    ;
```

关键字按不区分大小写匹配，因此 `#load` 与 `#Load` 是同一条指令。操作数是一个字符串字面量 token 且必不可少；缺少操作数的指令报 BC30217，并且不贡献任何待加载的文件。指令在逻辑行的起始处被识别，其前可有可选的空白。

该指令由 `LoadDirectiveTriviaSyntax` 节点表示，它派生自 `DirectiveTriviaSyntax`，带有一个 `LoadKeyword` 子节点和一个类型为 `StringLiteralToken` 的 `File` 子节点。语法 kind 为 `LoadDirectiveTrivia`。该节点没有指令结束 token；扫描器把该指令之后的行结束符作为 trivia 消费掉。因为该指令是 trivia 而非语句，它独占一行，后续诊断的行号不会漂移。

**决策**：拼写定为 `#Load`，并且不再定义其他拼写别名。同一条指令出现第二种拼写，就等于同一件事的第二种做法，而已发布的拼写必须对那些已经在使用它的脚本保持稳定。

### 模式门控

加载指令只在脚本方言中合法。普通编译（ordinary compilation）中的 `#Load` 是一个错误；该指令仍会被解析并作为 trivia 消费，因此树保持良构，文件的其余部分照常解析。

```vbnet
' Compiled as ordinary code, not as a script:
#Load "helpers.vbx"   ' Error BC36967: #Load is only allowed in scripts
```

该指令在方言的两副面孔下都可用：脚本文件与交互提交（interactive submission）。在交互会话中，被加载的树归属于含有该指令的那个提交，所以它们贡献的声明通过后寻常的提交链（submission chain）在后续提交中可见。

### 位置：头部指令

`#Load` 是一条**头部指令（head directive）**：它只在编译单元首个 token 的前导 trivia（leading trivia）中被识别。跟在任何 token 之后的 `#Load` 仍会作为指令被解析，报 BC37002，并且不被收集。

```vbnet
Dim x = 1
#Load "helpers.vbx"   ' Error BC37002: Cannot use #Load after first token in file
```

位置判据是「首个 token 之前」，而不是「位置 0」：注释、空白以及其他头部指令可以出现在 `#Load` 之前，`#Load` 写在首个 token 之前的任意一行都被接受。该判据按树逐棵应用，因此写在被加载文件第一行的 `#Load` 是合法的。

语言的指令模型并不统一，本规范把这一区分明确写出：

| 指令 | 类别 | 位置判据 |
|---|---|---|
| `#If`、`#Const`、`#Else`、`#End If`、`#Region`、`#ExternalSource`、`#Disable Warning` | 自由位置 | 任意逻辑行边界，受块结构约束 |
| `#R`、`#Load` | 头部 | 编译单元首个 token 的前导 trivia |
| `#!` | 头部 | 文件的位置 0 |

**决策**：两类头部指令判据不同，是有意的。shebang 由操作系统内核读取，内核要求它的两个字符是文件的前两个字节；`#R` 与 `#Load` 是在编译开始之前配置编译，只需先于任何 token。因此脚本作者应当预期：写在语句之后的 `#Load` 是一个错误，而不是一条被静默忽略的指令。

模式检查与位置检查互斥：模式检查先应用，因此普通编译中的 `#Load` 无论位置是否正确都报 BC36967。

### 空操作数

操作数为空字符串的指令是空操作：宿主展开（host expansion）会跳过空操作数，编译器不报诊断。

```vbnet
#Load ""   ' Okay: no operation
```

**决策**：这是有意的空操作。空操作数不是解析失败，而是操作数的缺席。这一选择与 C# 编译器分叉：C# 的 `#load ""` 报 CS1504；该分叉记录在[与 C# 实现的分叉](#divergences-from-the-c-implementation)一节下，而不是留给读者推断。

### 禁用的条件编译区域

位于被假 `#If` 排除的条件区域之内的 `#Load` 完全不会被识别为指令。扫描器把整个禁用区域（disabled region）作为禁用文本消费，因此不产生指令节点、不报诊断，宿主也不会展开它。模式检查与位置检查只适用于活动区域中的指令。Visual Basic 的指令 trivia 没有活动/非活动标志，所以这一边界是扫描器的性质，而不是节点的性质。

### 编译器做了什么，以及没做什么

**收集。** `CompilationUnitSyntax.GetLoadDirectives` 返回编译单元首个 token 的前导 trivia 中的加载指令。不在该位置的指令不会被返回，即便它仍被解析并被诊断。

**不进声明表。** 声明表（declaration table）构造器只记录引用指令，此外别无其他。`#Load` 不贡献任何条目，编译器一侧也没有任何状态记录某棵树含有这样一条指令。

**不使引用失效。** 当一棵语法树的源码 kind 为 `Script` 且至少含有一个 `#R` 时，该树报告自己含有引用指令。`#Load` 不属于该判据的一部分，因此增删一棵只含 `#Load` 的树本身并不会使引用管理器（reference manager）失效。

**边界。** 该指令自身的贡献为零，但被加载的树是一棵普通的脚本树。如果被加载的文件含有一个 `#R`，那条指令会像其他任何指令一样被收集，并且当该树被添加或被替换时，它存在于编译之中就足以置起失效标志。两个事实彼此一致：该标志回答的是「这棵树是否含有 `#R`」，而被加载的树确实含有。

**决策**：该指令有意不属于引用机制的一部分。「哪些树构成这个提交」与「哪些程序集被引用」是正交的状态；把二者通过同一枚失效标志耦合起来，会使对一份 `#Load` 列表的一次编辑去重建引用绑定，也会让一个树级别的概念冠以一个引用级别的名字。

### 宿主展开契约

展开 `#Load` 的宿主执行下述遍历。遍历的结果就是构造该提交所依据的树列表。

1. 把脚本文本解析为**主树（main tree）**，使用脚本的解析选项与它的文件路径。
2. 当主文件有路径时，用主文件的规范化路径为**活动展开集（active expansion set）**播种，比较时不区分大小写。因此，一个加载了主文件的文件就构成一个环。
3. 对主树前导 trivia 中的每一条加载指令，按源码顺序：
   1. 空操作数被跳过；
   2. 以写下该指令的那棵树的文件路径为基准解析操作数；
   3. 若解析没有产生路径，或者该路径已在活动展开集之中，停止遍历并报 BC2001，锚定在该指令的字符串字面量 token 上；
   4. 否则读取该文件并把它解析为**一棵新树**，使用同样的解析选项，并以解析得到的路径作为它的文件路径；
   5. 递归地展开那棵树，深度优先；
   6. 把该路径从活动展开集中移除，并把该树追加到列表末尾。
4. 最后追加主树。

该遍历是深度优先的，且一个文件在它自己所加载的那些文件之后追加，因此一个文件的顶层语句先于加载它的那个文件的语句执行，而主文件最后执行。此顺序下的第一次失败即中止遍历；在此之前解析出的树连同该失败一起被丢弃，因为展开的结果要么是一份完整的树列表，要么是一条诊断。

**相对路径以发起引用的树为基准解析。** 被加载文件中的嵌套 `#Load` 以那个被加载文件的路径为基准解析，而不是以主文件的路径为基准，因此一个库可以相对于自身定位。

**该相对基准是唯一的文件系统输入。** 操作数字符串本身对语言不透明，它与发起引用的文件的路径一起传给宿主的源码引用解析器。

**决策**：采用深度优先顺序，每棵被加载的树都排在引用它的那棵树之前。这正是作者阅读的顺序，也是一个文本内联实现本会产生的顺序，因此依赖顶层语句先后顺序的脚本得以保持其行为。

**决策**：展开失败报在该指令上，而不报在缺失文件内部的某个位置。作者写下的唯一位置就是那条指令，而必须改动的也正是那条指令。

**大小写与同一性。** 指令关键字按不区分大小写匹配，活动展开集上的路径同一性也按不区分大小写比较。

**环检测只覆盖活动展开集。** 一条路径在其子树被完全展开之后就从该集合中移除，因此一个可由同一次遍历的两条不同分支到达的文件会被加载两次。这与 C# 实现分叉，后者按解析后的路径去重；参见[与 C# 实现的分叉](#divergences-from-the-c-implementation)。

### 多树提交

该树列表作为**一个提交**提交，而不是作为几个提交。提交模型——合成的脚本类、初始化器、结果规则以及先前提交的链——都不变；唯一的区别是脚本类每棵树有一个部分。

**一个声明空间。** 任何树中的顶层 `Dim` 都是脚本类的一个字段，任何树中的顶层 `Sub` 或 `Function` 都是一个实例成员——若声明为 `Shared` 则是 `Shared` 成员——任何树中的顶层类型都是一个嵌套类型。在被加载文件中声明的名字对加载它的文件以及每一棵后续的树都可见，而在主文件中声明的名字对被加载的那些文件也可见。同一个名字在两棵树中重复即是一条重复声明，因为这些树是同一个类型的各个部分。

**一个初始化器。** 所有树共同贡献一个初始化器序列。在一棵树之内，实例字段与属性的初始化器以及顶层语句按源码顺序收集进同一个列表，所以同一个文件中位于某个 `Dim` 之前的语句先于那个字段的初始化器执行。树与树之间，这些列表按树顺序整体串接：先是被加载的树，按遍历产出它们的顺序，然后是主树。因此被加载文件的顶层语句先于主文件的字段初始化器执行。

**提交结果由最后一棵树决定。** 主树是最后一棵树，所以主文件末尾语句的形状决定这个提交是否有结果，而被加载文件中的末尾表达式不是结果。任何一棵树里的一个 `Return` 都是该初始化器的返回语句，因而返回整个提交；在一个带类型的提交中——即 `.vbx` 文件被执行时所取的形状——无论它写在哪棵树上，该值都是进程退出码。

**零 span 漂移。** 因为每个文件都是自带文件路径的一棵独立树，被加载文件中的诊断带着那个文件的路径与行号，而主文件的 span 不会因被加载的文本而偏移。这正是该指令被做成「一条指令 trivia 加上一组树」而不是文本包含的原因。

**共享引用。** 所有树都以同一个引用集合构造，所以被加载的文件无需自己的指令就能使用该提交所引用的类型。

下面两个文件构成一个完整的程序。`helpers.vbx` 是被加载的文件：

```vbnet
' helpers.vbx — its own tree, with its own path, so its diagnostics carry its own line numbers
Imports System.Text                          ' in effect in this file only (see below)

Dim greeting As String = "hello"             ' a field of the script class
Dim sb As New StringBuilder("loaded")        ' a field initializer: runs before the main file's statements

Function LoadedValue() As Integer            ' an instance member of the script class
    Return 42
End Function

Print("helpers.vbx: " & sb.ToString())       ' a top-level statement: runs before the main file's statements
```

`main.vbx` 是主文件：

```vbnet
' main.vbx
#Load "helpers.vbx"                          ' a directive trivia; the operand is resolved by the host
Print("main.vbx: " & LoadedValue() & " " & greeting)
Return 0                                     ' a typed submission: only an explicit Return is the exit code
```

运行主文件会打印：

```text
helpers.vbx: loaded
main.vbx: 42 hello
```

而退出码为 `0`。

### 被加载树中的 `Imports`

有两条规则同时适用，且不得把二者混为一谈。

- **在一个提交之内，`Imports` 以文件为单位。** `Imports` 语句的作用域明确不涵盖其他源文件。被加载文件的 `Imports` 只在那个文件内生效，在该提交的其他任何地方都不生效，而发起加载的文件看不到它。
- **跨提交时，`Imports` 会累积。** 宿主收集链中每个提交的每棵树的所有子句，并把它们施加到下一个提交，所以写在被加载文件里的一个子句在该会话的下一个提交中生效。

引用沿链**继承**；`Imports` 由宿主**累积**。这两种机制不得互相替着描述。

**决策**：被加载文件的导入不与发起加载的文件共享。否则 `Imports` 语句的作用域将取决于恰好是哪个其他文件加载了它，而这是 `Imports` 语句的作者看不到的性质。

### 与其他头部指令共存

`#!`、`#R` 与 `#Load` 可以全都出现在同一段前导 trivia 中。每一条都会被解析，每一条都能通过各自的指令 API 被发现，彼此之间不要求任何先后顺序。

**决策**：`#R` 与 `#Load` 之间不施加顺序。二者的效果互不相干——`#R` 改变引用集合，`#Load` 改变树集合——且彼此都不是对方的前提。一条顺序规则将是一个没有语义后果的约束。

### 运行时加载与提前编译

一个提交被编译为一个内存中的程序集，动态加载，并针对以对象数组传入的状态执行。被加载的树是该提交的一部分，并被编译进同一个程序集。这一机制处在提前编译（ahead-of-time compilation）与裁剪（trimming）的范围之外，也不自带任何提前编译或裁剪上的阻力。

### 错误

| 诊断码 | 诊断 | 条件 |
|---|---|---|
| BC36967 | `ERR_LoadDirectiveOnlyAllowedInScripts` | `#Load` 出现在普通编译中。消息："#Load is only allowed in scripts" |
| BC37002 | `ERR_PPLoadFollowsToken` | `#Load` 出现在编译单元首个 token 之后。消息："Cannot use #Load after first token in file" |
| BC30217 | `ERR_ExpectedStringLiteral` | 该指令没有字符串字面量操作数。消息："String constant expected." |
| BC2001 | `ERR_FileNotFound` | 宿主无法展开一条活动指令：操作数解析不到任何文件，或者解析出的路径正在展开之中。消息："file '{0}' could not be found" |

前三条是编译器诊断。BC2001 由宿主在展开过程中产生，而非由编译器产生；它锚定在该指令的字符串字面量 token 上。展开失败以一个只携带该条诊断的 `CompilationErrorException` 抛出。

BC2001 既是文件缺失的诊断，也是环形加载的诊断。即使文件存在、真正的原因是环，消息也仍说 "file not found"；该分叉记录在[与 C# 实现的分叉](#divergences-from-the-c-implementation)一节下。

### 与 C# 实现的对齐

本指令的 C# 对应物是 C# 脚本的 `#load` 指令。两者共有那两条界定性的性质——语言不解释操作数，且指令必须先于首个 token——也共有深度优先的树顺序，被加载的树排在引用者之前。二者的差别在于展开所在的方位，以及同一个文件两次可达时会发生什么。

| 维度 | C# `#load` | Visual Basic `#Load` |
|---|---|---|
| 指令节点 | `LoadDirectiveTriviaSyntax`，带指令结束 token | `LoadDirectiveTriviaSyntax`，不带指令结束 token |
| 操作数是否由语言解释 | 否 | 否 |
| 位置约束 | 首个 token 之前 | 首个 token 之前 |
| 模式门控 | 脚本之外报 CS8097 | 脚本之外报 BC36967 |
| 位置错误 | CS8098 | BC37002 |
| 展开点 | 编译对象之内，由编译的源码引用解析器驱动 | 宿主，在编译被创建之前 |
| 引用管理器复用 | `#load` 算作一条可能影响引用集合的指令，因此含有它的树会阻止复用引用管理器 | 只有 `#R` 计入；单有一条 `#Load` 指令不造成失效 |
| 空操作数 | `#load ""` 报 CS1504 | 空操作，不报诊断 |
| 文件缺失 | CS1504，锚定在文件 token 上 | BC2001，锚定在文件 token 上 |
| 环形加载 | 静默终止：已加载过的路径不再重新加载 | BC2001，锚定在闭合成环的那条指令上 |
| 同一文件两次可达 | 按解析后的路径只加载一次 | 按遍历的每一条分支各加载一次 |
| 读取失败 | 转换为一条诊断（CS2015） | 不转换；解析器的异常向外传播 |
| 源码解析器缺失 | CS8099 | 空引用失败 |
| 树顺序 | 被加载的树在前，引用者最后追加 | 相同 |
| 被加载树的解析选项 | 发起引用的那棵树的选项 | 该提交的解析选项 |
| 指令关键字大小写 | 不区分大小写 | 不区分大小写 |
| 活动/非活动标志 | 指令 trivia 带有该标志 | 无此标志；禁用区域不产生指令节点 |

引用管理器复用、空操作数、读取失败、解析器缺失、环形加载以及菱形（diamond）这几行是语义上的分叉。其中空操作数那一行尤其不得当作对齐来读：姊妹指令 `#R` 的空操作数在两种语言里都被丢弃，而 `#Load` 的空操作数只在 Visual Basic 里被丢弃。

## 健全性
[soundness]: #soundness

该指令不引入任何新的绑定规则。它改变的是构成一个提交的树的集合，而该集合中的每棵树都是一棵普通的脚本树；语言本就定义了一个具有多个部分的脚本类意味着什么，因为脚本类是一个部分类型（partial type），它的各个部分会合并。因此增加一条加载指令只能通过合并声明的寻常后果来改变既有代码的含义，绝不会通过改变任何既有构造的含义来做到。

该指令的触达范围是明确的。它只在脚本方言中合法，所以没有任何普通程序能在编译器不报的情况下依赖宿主展开；模式检查先于位置检查，所以普通编译中一条位置错误的指令报一个错误而不是两个；而位置错误的指令不被收集，所以一棵树的加载指令集合恰好就是它首个 token 的前导 trivia 里的那些指令。

顺序规则是健全的，因为它是对宿主产出的陈述而非对源码的陈述：本规范固定了宿主必须产出的树列表的顺序，而语言从树列表出发定义一个提交的初始化器的顺序。两者可以复合，所以一个含 `#Load` 的脚本中顶层语句的执行顺序是源码的函数。

名字解析不受影响。`#Load` 不导入命名空间，被加载文件的 `Imports` 在该提交之内仍是文件局部的，所以不会仅仅因为某个其他文件被载入同一个提交，某个名字就在一文件之中变得可见。

## 缺点
[drawbacks]: #drawbacks

- **操作数的含义取决于环境。** 相对操作数以写下它们的文件为基准解析，所以挪动一个脚本、经由另一个文件加载它，或者从另一个目录启动宿主，都会改变实际加载的是哪个文件，而且没有任何诊断提示发生了变化。
- **可由两条路径到达的文件会被加载两次。** 环检测只覆盖活动展开集，所以一个菱形会让同一文件每条分支各加载一次：它的顶层语句执行两次，它的声明变成同一个脚本类的两个部分，这可能在被加载的文件内部产生一条重复声明错误，而不是在促成此事的那条指令上报错。
- **文件缺失与环形加载共用一条诊断。** 两者都报 BC2001，其消息说找不到该文件；当起因是一个环时，文件其实在场，消息便有误导。
- **展开失败不产生编译对象。** 失败在编译存在之前就被抛出，所以工具无法向那次失败的编译查询诊断；它收到的只是一个携带一条诊断的异常。
- **缺少源码解析器时以异常失败，而不是以诊断失败。** 一次编译，其脚本选项不带源码解析器、其脚本又含有一条操作数非空的 `#Load`，会以空引用异常失败，而不是报出一条诊断。
- **未经展开的 `#Load` 既惰性又无声。** 直接从该树构造编译的消费者，既拿不到被加载的声明，也拿不到「它们缺席」这条诊断。
- **顶层语义取决于宿主的树顺序。** 哪个文件的 `Dim` 是一个字段、哪个文件的语句先运行，随树列表而定，而不随声明在源码中的位置而定。
- **遍历归宿主所有。** 需要同样语义的工具必须复现这套展开，包括环检测、路径同一性与排序；此契约之所以在此写明，正是因为没有任何编译器侧的状态可供查看。

## 替代方案
[alternatives]: #alternatives

- **把被加载文件的文本内联进发起加载的文件。** 已否决：它会把 `#Load` 之后的每一个 span 按插入的行数偏移，并使被加载文件内部的诊断带着错误的文件与行号，而这正是本指令的设计所要避免的失败。同样的理由也否决了对 shebang 指令做宿主侧剥离。
- **让 `#Load` 作为源码引用进入声明表。** 已否决：`#Load` 的产物是一组语法树，不是一组程序集引用。把它经由声明表路由，会把「存在哪些树」与「引用了哪些程序集」耦合进同一枚失效标志，而且源码引用无法承载顶层语句、脚本类的部分或初始化器条目。
- **按解析后的路径对被加载文件去重。** 当前实现未采纳：环检测的作用域限于活动展开集，所以一个菱形会让文件每条分支各加载一次。C# 编译器按解析后的路径去重，环形加载因而静默终止。采纳该规则会改变那些依赖「一个文件每条分支执行一次」的既有脚本的行为，所以它是另一个独立的决策。
- **为环形加载报一条独立的诊断。** 当前实现未采纳：文件缺失与环报成同一条诊断、同一个消息。C# 编译器根本不报环，所以一个独立的诊断码将是一项 Visual Basic 专属的精化，而非一次对齐。
- **为空操作数报一条诊断。** 未采纳：空操作数是空操作，报一条诊断将是与当前行为的分叉，而其中并无失败可报。
- **在编译器里展开 `#Load`。** 未采纳：树集合是宿主在构造提交时提供的一项输入，而宿主才是拥有文件系统抽象的一方。C# 编译器在编译对象内部展开，由编译选项所携带的源码引用解析器驱动；这两种落位是一个真实的设计差异，不是疏漏。
- **把 `#Load` 用于程序集引用。** 不适用：`#Load` 把源文件纳入同一个提交，并不添加程序集引用。

## 考量
[considerations]: #considerations

### 展开是宿主的义务

该指令是一个编译器可识别的语法节点加上一个宿主所定义的操作，两半不可互换。编译器保证节点本身、模式门控、位置门控、操作数的语法，以及把该指令暴露出来的树 API；它不保证操作数意味着什么，也不保证是否加载了文件。因此，由一棵含有 `#Load` 的树构造出的编译里没有任何被加载文件的痕迹，也不为它的缺席报任何诊断。这是一条契约，不是一个缺口：一个提交的树集合是一项输入，而构造该提交的宿主正是决定它的一方。

对工具而言的后果是：直接构造编译的消费者必须执行同一次遍历——把每个操作数以发起引用的树为基准解析、检测环、按深度优先给树排序——才能得到脚本运行器本会产出的语义。从树里读出这条指令，能告诉工具作者要求了什么；它并不能告诉工具加载了什么。

### 失败通道

展开失败以 `CompilationErrorException` 抛出，而脚本 API 在编译这一步把它转换为诊断：`Script.Compile()` 捕获该异常并返回其诊断而不再抛出，所以在运行之前先编译的调用方会收到一份诊断列表。建立在该 API 之上的宿主因此表现如下。

- **交互。** 会话先编译该提交；若编译报出错误，该提交被丢弃，会话继续。交互式 `#Load` 里拼错的文件名报出一条诊断，并不终结会话。
- **脚本文件。** 文件这条路径不先编译，所以异常在运行期间抛出；宿主捕获它，报告其诊断，并返回一个失败退出码。
- **仅检查模式。** 检查这条路径与交互这条路径使用同一个编译步骤，所以当一条 `#Load` 展开失败时，退出码契约——无编译错误时为零、有编译错误时非零——仍然成立。

与 C# 的残余差异是结构性的：因为失败发生在编译对象被创建之前，一次失败的提交没有可供查询的编译，而 C# 编译器有一个编译对象，其诊断中包含了该加载失败。这一点对分析工具可见，对命令行用户不可见。

### 与 C# 实现的分叉 <a id="divergences-from-the-c-implementation"></a>

有六处分叉在此写明，而不是留待被发现，因为每一处都是熟悉 C# 的读者会预测出错误行为的地方。

- **引用管理器不因 `#Load` 而失效。** C# 把 `#load` 视为一条可能影响引用集合的指令，因为被加载的文件可以携带 `#r`；Visual Basic 的失效判据只问一棵树是否有 `#R`。这一差异只作为编译器内部的一次复用决定而可观察，它不改变一次编译的引用集合：携带 `#R` 的被加载树仍然贡献那条引用，仍然置起那枚标志。
- **空操作数保持无声。** C# 对 `#load ""` 报 CS1504；本方言把它跳过。
- **读取失败不转换为诊断。** C# 把读取已解析文件时的失败包装成一条锚在该指令上的诊断（CS2015）；本方言不为读取设守卫，所以解析器抛出的异常会传播出展开，并传播出脚本编译这一步——后者只转换 `CompilationErrorException`。
- **源码解析器缺失时以异常失败。** 当编译没有源码引用解析器而脚本中含有 `#load` 时，C# 报 CS8099；本方言不为解析器设守卫，所以同样的输入以空引用异常失败。
- **环形加载会得到诊断。** C# 按解析后的路径去重，所以环静默终止；本方言在活动展开集上检测环，并在闭合成环的那条指令上报 BC2001。
- **菱形不做去重。** 对一个两次可达的文件，C# 按解析后的路径只加载一次；本方言按遍历的每一条分支各加载一次，所以它的顶层语句执行两次，它的声明变成同一个脚本类的两个部分。

### 路径同一性不区分大小写

活动展开集按不区分大小写比较路径。因此一条交替使用某个文件名大小写的加载链会被检测为环，而只有大小写之分的两种拼写在环检测看来是同一个文件。该规则与语言标识符以及指令关键字的不区分大小写相一致。

### 环形加载的诊断文本

BC2001 的消息说找不到该文件，而环形加载在文件在场的情况下报出同一条消息。对缺失文件这一常见情形，该消息是准确的；对一个环，它点出的是其加载闭合了环的那个文件。作者若在一个确实存在的文件上看到这条消息，应当去读诊断的位置——闭合环的那条指令——而不是消息里的文件名。

## 测试
[testing]: #testing

本特性由进程内的无副作用测试来验证：它们不进行网络访问、不启动进程、不访问注册表，也不在隔离的临时目录之外写文件。多数用例使用内存中的源码解析器，因此根本不从磁盘读取任何文件。

- **端到端脚本测试。** 首行为一条加载指令的 `.vbx` 文件调用被加载文件中声明的一个函数，并以零退出码退出。一个加载了文件的交互会话可以在后续提交中调用被加载文件的函数并打印其值，而被加载文件首行的加载指令被接受。
- **嵌套展开与结果测试。** 自身又加载了第三个文件的被加载文件可以编译，且在最深层文件中声明的函数可由加载中间那个文件的文件调用。唯一一条语句是 `Return 17` 的被加载文件使提交结果为 `17`。
- **span 与位置测试。** 主文件中位于一条加载指令之后的诊断报出主文件的真实行号，而不是偏移后的行号。被加载文件内部的诊断报出被加载文件的真实路径与行号。
- **失败测试。** 点名一个不存在文件的一条加载指令抛出 `CompilationErrorException`，其唯一诊断锚定在发起引用的文件中那条加载指令所在的那一行。一个加载环报在闭合该环的那条加载指令上，位于写下它的文件里。
- **引用与导入测试。** 被加载文件无需自己的指令即可解析来自该提交引用的类型。写在被加载文件里的一条 `Imports` 子句会被重放到该会话的下一个提交，而一条格式不当的累积子句由提交门报出，而不是作为异常抛出。
- **指令共存测试。** 同一段前导 trivia 中的一个 shebang、一条引用指令与一条加载指令都能解析，各自都能通过各自的指令 API 被发现，而被加载的代码得以运行。
- **位置门测试。** 首个 token 之后的一条加载指令报 BC37002，而第一行上的一条加载指令不报位置诊断。
