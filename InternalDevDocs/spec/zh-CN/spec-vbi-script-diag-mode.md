## 概述
[summary]: #summary

本规范为 Visual Basic 脚本宿主新增一种仅诊断检查模式。`/check` 开关把一个 `.vbx` 脚本文件作为单个提交进行编译、报告所得诊断、然后退出——不执行脚本，也不写出任何输出文件。该开关是一道编译门：退出码 `0` 表示脚本没有编译错误（允许存在警告），退出码 `1` 表示至少存在一个错误。

本特性之前，一次性脚本路径以单步完成编译与执行，因此成功的运行会把警告完全吞掉，而且没有任何办法在不运行脚本的前提下取得诊断。交互窗口已经用一道「编译不运行」的步骤对每个提交做门控，但那条路径是逐提交的、会截断诊断显示，也不是一次性的文件检查。`/check` 把既有的编译不运行机制接到一次性脚本文件路径上，并使其成为可观察契约。

该模式类比 `cargo check` 与 `tsc --noEmit`：完整的语义检查，无产物、无执行。它面向脚本编写循环，以及需要仅诊断反馈通道、又不愿承担脚本副作用的 AI 工具链。

## 动机
[motivation]: #motivation

脚本文件的执行是把编译与运行合成一步。成功的运行打印其输出并以 `0` 退出，而警告——未使用的局部变量、后期绑定的调用——从不显示。失败的运行停在第一个编译错误处，因此看到诊断的唯一办法就是通过运行把它们触发出来。现有三条路径都不满足「无副作用地取得诊断」这一需求，且各有三种不同的原因：

| 路径 | 行为 | 缺口 |
|---|---|---|
| **脚本执行**（`vbi script.vbx`） | 一步完成编译与运行 | 成功的运行不报告任何警告；没有办法在不运行的前提下检查 |
| **交互模式**（`/i`） | 检查每个提交，然后运行它 | 只能逐提交，且交互诊断显示被截断 |
| **编译模式**（`.vb` 源文件，或 `/out:`/`/target:`） | 执行完整的普通编译并发射程序集 | 会发射文件；它不是「仅诊断」 |

本特性所需的机制已存在于脚本引擎中。`Script.Compile()` 编译一个提交并返回其诊断而不运行它；交互窗口用来决定每个提交可否运行的正是同一个 API。一次性脚本路径根本从不调用它——它直奔 `RunAsync`，把编译与执行焊在一起。缺的是开关，不是机制。

主要消费者是迭代 `.vbx` 脚本的 AI 工具链，它需要一条返回编译器诊断但不执行脚本代码的反馈通道。因此开关的命名遵循「消除 AI 误读」这一标准：AI 在读到任何帮助文本之前，会先按训练数据先验来解读一个裸开关。`/check` 的先验干净且吻合——`cargo check`、`node --check` 与 `biome check` 都表示「验证、不产出产物、不执行」。备选名 `/diag` 的先验相反——`msbuild /diag` 与 `dotnet build -v:diag` 表示「运行并产出最详细的构建日志」——故被否决。

## 详细设计
[design]: #detailed-design

### 脚本模式中的 `/check` 开关

脚本模式命令行解析器在其脚本专属开关集中把 `/check` 识别为一个裸开关，与 `/i`、`/nostdlib`、`/optimize` 并列。给它赋值（例如 `/check:on`）会被拒绝并报「开关需布尔值」错误，与裸开关惯例一致。该开关置位一个布尔量，该布尔量流入共享的命令行参数对象。

**决策**：该标志以 `Check` 之名存放在共享的参数基类上，而非放在语言专属的参数类型上。执行检查的代码路径位于共享宿主代码中，它从基类型读取该标志。这沿袭 `InteractiveMode` 的先例——由脚本解析器置位、由共享 runner 读取——避免了在共享宿主代码中做语言专属的强转。C# 脚本解析器从不置位该标志，因此 C# 交互宿主不受影响。

### 与交互模式的互斥

`/check` 要求给出脚本文件，并且优先于交互模式。两条规则落实这一点，一条在解析器，一条在 runner：

- **在解析器中**，`/check` 抑制那种在未给出源文件时本会自动生效的交互模式推断，而不带源文件的 `/check` 调用会产生缺失脚本错误（`BC36963`）。
- **在 runner 中**，当 `Check` 标志置位时宿主直接进入脚本路径，绝不进入交互循环，即使传入了 `/i`。

因此可观察行为为：

| 调用 | 行为 |
|---|---|
| `vbi /check script.vbx` | 编译脚本并报告诊断；退出码遵循下述契约 |
| `vbi /check /i script.vbx` | 与上一行的调用行为相同；`/check` 胜过 `/i`，且 REPL 提示符从不出现 |
| `vbi /check`（无文件） | 解析期缺失脚本错误 `BC36963`；退出码 `1` |

### 检查路径

标志置位时，一次性脚本路径编译脚本并报告诊断，而不是运行它：

```csharp
if (arguments.Check)
{
    var diagnostics = script.Compile(cancellationToken);
    return ReportDiagnostics(diagnostics, console.Error, errorLogger, compilation: null)
        ? Failed
        : Succeeded;
}
```

`Script.Compile()` 编译这个单提交脚本并返回其诊断，而不运行它。宿主通过共享的诊断报告器报告这些诊断；该报告器把每条诊断打印到错误流，并返回其中是否存在错误。

### 退出码契约

- `0` —— 脚本没有编译错误；可能存在警告。
- `1` —— 脚本有一个或多个编译错误。

退出码恰为共享诊断报告器的返回值，因此契约是「任一被报告的错误即令门失败」。这与普通编译器和 `dotnet build` 的语义一致。

### 诊断面

`/check` 报告错误与全部警告。Info 与 hidden 诊断被底层编译 API 以及命令行报告器滤除，因此该诊断面是「错误加上完整警告集」。对编译门而言这是正确的语义：info 与 hidden 诊断从不阻塞构建。

成功路径完整显示警告。这是本特性相对脚本执行的主要改进——脚本执行在成功运行时什么都不显示。例如，一个声明了未使用局部变量、然后打印内容的脚本：

```vbnet
Sub S()
    Dim unusedVar As Integer
End Sub
Print("RAN")
```

用 `vbi /check warn.vbx` 检查它：宿主报告该未使用局部变量的 `BC42024` 警告并以 `0` 退出，脚本不被执行，因而 `RAN` 永不被打印。

### 严重度配置

第一版不新增严重度配置。`/warnaserror`、`/nowarn` 与 `/ruleset` 是普通编译器的开关，脚本模式解析器不予识别，因此它们落到无法识别的选项警告（`BC2007`）并被忽略。于是 `/check` 的严格度等同于 `dotnet build` 与 `vbc` 的默认门：错误令其失败，警告予以显示。

**决策**：本版本不以 `/warnaserror` 或 `/nowarn` 扩展脚本解析器。把警告升级为错误推迟给未来面向分析器的配置面。逐文件的严格度已可通过源级 `Option Strict` 语句控制，这正是 Visual Basic 表达逐文件严格度的模型。

### `Option Strict` 与逐文件严格度

检查的严格度由文件内容决定。脚本中的 `Option Strict On` 得到与执行时完全一样的遵守——后期绑定与收窄转换产生它们惯常的错误。宿主提供一个默认的 `Option Strict` 值；源级语句按文件覆盖它。检查模式不新增自身的严格度配置。

### `/check` 配 `.vb` 源文件

`/check` 是脚本模式开关，对 `.vb` 源文件不起作用。宿主在脚本解析之前就把 `.vb` 源文件（或带 `/out:` 或 `/target:` 的调用）派发到普通编译模式，因此那里不识别 `/check`：它产生无法识别的选项警告（`BC2007`），编译照常进行并正常发射。想对 `.vb` 文件做编译门的用户应使用普通编译器。

### 与 `/removeintchecks` 和 `Option Checked` 的关系

`/check` 是一道编译门：它编译并报告诊断而不运行。`/removeintchecks`——以及 C# 编译器的 `/checked`——控制发射代码中的运行期整数溢出检查。两者无关，帮助文本也明确说明了这一点。用于溢出检查的源级 `Option Checked` 语句是一项独立的未来语言特性，并非本特性所需；纵使将来引入它，源级 `Option` 语句与命令行开关也分处两个命名空间、互不干扰。

### 内存发射：无落盘、无执行

`Script.Compile()` 通过脚本引擎的标准路径构建提交执行器，该路径通过交互窗口所用的同一个内存程序集加载器在内存中发射提交程序集。因此「只编译」意味着不写文件、不运行代码；它不是「零编译」。`#load` 了前置脚本的脚本，那些前置脚本同样在内存中被编译。本规范全篇采用的措辞是「无落盘、无执行」。

### 分析器不在范围内

`/check` 只报告编译器诊断。规则式诊断——fxcop 与 `oxlint` 那一类——需要 `CompilationWithAnalyzers` 以及脚本路径上的分析器管线，那是另一项独立提案。`/check` 类比的是 `tsc`，不是 `eslint`。

## 缺点
[drawbacks]: #drawbacks

- **无严重度升级。** 没有 `/warnaserror`，一道必须因警告而失败的门槛无法仅用 `/check` 表达。缓解：完整警告集现已可见，且逐文件严格度可通过 `Option Strict` 取得；升级推迟给未来的分析器面。
- **内存发射并非字面的「零编译」。** 提交程序集经标准脚本引擎路径在内存中发射。可观察契约——无落盘、无执行、无副作用——不受影响。
- **`.vb` 源文件不遵守 `/check`。** 想对 `.vb` 文件做仅诊断门的用户必须使用普通编译器；`/check` 在那里退化为无法识别的选项警告。这是有意为之——该开关属于脚本模式。

## 替代方案
[alternatives]: #alternatives

- **`/diag`。** 因命名被否决。在 MSBuild 工具链中，「diag」已绑定到「最详细的构建日志」——运行构建并打印详细日志——这与「不运行地检查」恰为相反。命名的首要标准是 AI 先验，而 `/diag` 的先验指向相反方向。
- **`/norun` / `/noemit`。** 这是 `tsc --noEmit` 的命名风格，以被抑制的动作命名。否决理由：对一个执行验证而非抑制动作的模式来说，它作为动词可读性更差。
- **`/analysis`。** 因误导被否决——该模式报告编译器诊断、不含任何分析器——并且与 `/analyzer:` 概念纠缠。
- **v1 中做严重度配置。** 在 `/check` 之外以 `/warnaserror` 与 `/nowarn` 扩展脚本解析器。第一版否决：严格度控制属于未来的分析器面，而逐文件严格度已可用 `Option Strict` 表达。
- **什么都不做。** 警告在成功执行路径上仍然不可见，AI 工具链仍然没有无副作用的诊断通道。本提案要补的缺口继续敞着。

## 考量
[considerations]: #considerations

### 命名与 AI 先验

主要消费者是 AI 工具链，因此命名标准是「消除 AI 误读」：AI 在读帮助文本之前，会先按训练数据先验解读裸开关。`/check` 的先验干净且吻合——`cargo check`、`node --check` 与 `biome check` 都表示「验证、不产出产物、不执行」。`/diag` 的先验相反——`msbuild /diag` 与 `dotnet build -v:diag` 表示「运行并产出最详细的构建日志」。命名决定因此选定 `/check`。与 `/removeintchecks` 的残余联想是可读性顾虑，不是误导：两个语义域（编译门与运行期溢出行为）互不相交，且帮助文本用一句就作了区分。

### 与普通编译器门的对齐

不带严重度配置的 `/check`，其严格度恰好等同于默认的 `dotnet build` 或 `vbc` 调用：错误令其失败，警告予以显示。这让该门对 CI 与脚本编写循环保持可预测，并且相对执行路径是严格的改进——执行路径上成功的运行根本不显示警告。

### 执行路径上的警告

脚本执行（`vbi script.vbx`）仍然一步完成编译与运行，只在运行编译失败时报告诊断，因此成功的运行继续吞掉警告。让执行在运行之前先把警告显示出来会改变既有输出，故有意留作独立的、不阻塞的后续事项。

## 测试
[testing]: #testing

本特性由无副作用的内存测试来验证：这些测试不进行网络访问、不启动进程、不访问注册表。脚本文件用例只写入既有的隔离临时目录测试装置，宿主必然要读取它。

- **解析器断言。** 未给 `/check` 时，解析所得参数把该标志留在默认值；`/check` 经脚本解析器流入共享参数对象；不带源文件的 `/check` 产生缺失脚本错误；`/check /i` 使该标志保持置位、交互模式保持开启。
- **冒烟断言。** 干净脚本以 `0` 退出、无任何诊断输出、且不被执行；含错误的脚本以 `1` 退出、报告该错误、且不被执行；只有警告的脚本以 `0` 退出、显示完整警告集、且不被执行；`/check /i` 编译脚本且从不显示 REPL 提示符。
- **`.vb` 边界。** `.vb` 源文件走到普通编译路径；runner 层测试断言脚本解析器对非脚本扩展名的处理。经由可执行文件的端到端派发（编译模式、`BC2007`、正常发射）由集成验证覆盖。
