# 任务：让 `#Load` 在同一个脚本编译里不重复塞入同一个文件

（任务文件夹名：`load-directive-dedup`。对应缺陷登记：`..\..\issues\issue-load-directive-cycle-reports-file-not-found.md`——那份是写给人看的，做任务不需要读它，本文件把需要的内容都写全了。）

## 1. 问题是什么，用大白话讲

我们的脚本语言允许在一个 `.vbx` 文件里写 `#Load "另一个文件"`，把另一个文件的内容塞进当前脚本一起编译运行。

出问题的情况：

- 有 3 个文件。`lib.vbx` 里写着 `Dim z As Integer = 9`。
- `a.vbx` 写 `#Load "lib.vbx"`。`b.vbx` 也写 `#Load "lib.vbx"`。
- 主文件 `main.vbx` 先 `#Load "a.vbx"`，再 `#Load "b.vbx"`。

结果主文件编译失败，报两条错：

```
lib.vbx(2) : error BC30260: “z”已在此 type 中声明为“Private z As Integer”。
lib.vbx(3) : error BC31429: “z”不明确，因为 type“Submission#0”中存在多种具有此名称的成员
```

原因很直白：**`lib.vbx` 被塞进来两遍**，里面的 `z` 就声明了两次。

而且报错位置指向 `lib.vbx` 自己，用户会以为是公共库写错了，实际是加载规则的问题。

C# 的脚本（`csi.exe`，版本 5.10.0-1.26380.3）跑同样的结构是正常的，输出：

```
SHAREDZ-ran z=9
A-ran
B-ran
DIAMONDZ-main z=9
```

也就是说 **C# 会自动把同一个文件只算一次，我们没有**。

结论：这不是"我们故意和 C# 不一样"，是**正常写法被判成错误**，属于必须修的缺陷。

## 2. 还要知道的两个已测事实（避免走弯路）

1. **同一个主文件里连着写两遍 `#Load "part.vbx"`**：我们的实现会把 `part.vbx` 的内容执行两遍，而且不报错。C# 只执行一遍。⇒ 所以问题是"没有去重"，不是"路径找不到"。
2. **三层套娃加载没问题**：`main` → `mid` → `leaf`，从别的目录用绝对路径跑主文件，三级都能正确找到文件、内容按源码顺序执行（实测输出 `NEST-level3-leaf`、`NEST-level2`、`NEST-level1`）。⇒ **别去改路径解析**，那不是病根。

## 3. 要改哪里

文件：`Scripting\VisualBasic\VisualBasicScriptCompiler.vb`，`CreateSubmission` 里收集被加载文件的那一段（第 185-199 行附近）。

现在的做法：代码里有个叫 `activeLoads` 的集合，作用是**防止"A 加载 B、B 又回头加载 A"这种绕圈**——它只记录"当前这条加载路径上正在处理的文件"，所以当一个文件加载完、退回上一层，它就被移出了记录。于是两个不同的分支各自加载同一个文件时，第二次加载不会被认为是重复。

要做的：在保留上面那个防绕圈机制的前提下，**再加一份"这一轮编译里已经塞进来的文件"记录**（同样按路径比较、忽略大小写），已经在记录里的文件就跳过、不再塞第二遍。跳过时不报错——和 C# 一致（C# 是静默只算一次）。

改动位置只在 `Scripting` 的这一段。普通 `.vb` 编译（`vbc`）根本走不到这里，因为普通编译里 `#Load` 本身就是错的（`BC36967`）。这一句论证要写进你的回报里。

## 8. 怎么跑测试（只看指定的，别跑全量）

- 单元测试：`dotnet test Scripting\VisualBasicTest\Microsoft.CodeAnalysis.VisualBasic.Scripting.UnitTests.vbproj --filter "FullyQualifiedName~ScriptTests"`
- 长命令一律先把输出重定向到文件，再只看结尾几行；不要把几千行的日志读进来（本仓有子任务因此烧掉四千多万 token 还没留下日志的先例）。
- 真跑脚本文件用 `Interactive\vbi\bin\Debug\net10.0\vbi.exe`。**跑之前先比对时间戳**：`vbi.exe` 必须比你改过的源文件新，否则你测的是旧二进制。
- 输出中文乱码时：先 `file -b 输出文件` 判编码，再决定用 UTF-8 还是 CP936 解码；同一台机器不同时候两种都出现过。
- 在 Git Bash 里传 `/check` 这类以斜杠开头的参数前，先 `export MSYS_NO_PATHCONV=1`，否则会被改成一个奇怪的路径。
