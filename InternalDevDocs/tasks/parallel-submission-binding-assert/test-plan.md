# 怎么测：并行时编译器自检崩溃

（前因后果和禁止事项见同目录 `README.md`。）

## 一、第一阶段的产出不是测试，是证据

这一阶段不许改代码，要交出四样东西：

| 编号 | 要做的事 | 什么算合格 |
|---|---|---|
| 1-1 | 固定"哪两个测试类一起跑"这个组合，连跑 **10 次** | 给出红/绿的具体次数和每次失败的测试名，不许只说"偶发" |
| 1-2 | 不用测试框架，自己开两个线程编译并运行脚本，试两种组合：①两边完全独立；②两边共用同一份 `ScriptOptions` 或共用同一个"上一次提交" | 每种组合给跑了几次、是否出现同样的自检崩溃。出现 ⇒ 倾向产品问题；都不出现 ⇒ 倾向测试装置问题 |
| 1-3 | 在崩溃现场把 `argument.Type` 和 `targetType` 两个类型打印出来（临时工程里打印，不改仓库代码） | 给出两个类型各自的名字和符号来源；拿不到就写"拿不到，卡在哪" |
| 1-4 | 下结论 | 只能写三种之一：**产品并发缺陷** / **测试装置共享状态** / **未定性**。写"未定性"时必须列出已经试过的组合清单。**不许**把"没复现"写成"没问题" |

## 二、这一阶段不许做的事

- 把那条测试设成跳过、删除、或放宽它的断言让它变绿。
- 用"重跑一次就绿了"当结论。
- 在仓库产品代码里加打印/加锁做实验。

- 编译器七个测试门：失败数 0；总数只按新增测试条数增长，跑前先用 `git diff HEAD --numstat` 看真实改动量，不要照抄文档数字。
- 脚本层整套测试：直接运行 `Scripting\VisualBasicTest\bin\Debug\net10.0\Microsoft.CodeAnalysis.VisualBasic.Scripting.UnitTests.exe -automated`，最后一行 JSON 里 `TestsFailed` 为 0（不能用 `dotnet test` 跑这套）。
- 定向那组（46 条规模）至少连跑 6 次，把红/绿次数与本文件第一阶段的基线数字对比着报。

## 五、每条结论标注验证方式

- 第 1 档：单元测试能直接断言（能走这档不许降级）；
- 第 2 档：要真跑程序看输出；
- 第 3 档：只能读代码核对。
