# 任务：查清"脚本提交类的共享字段初始化器为什么是惰性的"，把机制说明写进缺陷登记

（任务文件夹名：`submission-shared-cctor-trigger`。对应缺陷登记：`..\..\issues\issue-submission-shared-constructor-not-run.md` 的 **A 半边**——那份是给人看的，做任务不需要读它，本文件内容自足。）

## 1. 已经定下来的部分，别重做

- 现象：脚本顶层写 `Shared x As Integer = 42` 这样的共享字段，它的初始化器**不会**在脚本主体开始时自动执行；只有真的去读或写那个字段，值才出现。
- 裁定：**这个行为不改**。理由是 C# 脚本的同类字段也是惰性的（两边都往类型上打 `beforefieldinit`，也就是 CLR 不承诺初始化时机），改它等于改语义、没有收益。
- 该补的测试和文档也已经补完了：规范里写清了时机（中英两份都有），并有"读了⇒断到具体值"和"不读⇒观察不到副作用"成对的两个用例（不是只断"没报错"那种空对照）。

**唯一剩下的**：到底**为什么**"调用一个共享方法"不算"触碰共享成员"、从而不触发那个静态构造函数？这一层没人解释过。现在只知道现象，不知道为什么。

## 2. 这个任务就是回答那一个为什么

不许改产品代码。交付物是一段**能站住的机制说明**，写回缺陷登记的正文里。

**第一步：拿二进制证据（不许只读代码猜）**

1. 用脚本编译器发射一个只含 `Shared` 字段初始化器 ＋ 一个 `Shared` 方法的提交，把产出的程序集存到 `tmp\` 下。
2. 读这个类型的元数据，把两件事原样抄下来：
   - 类型上有没有 `BeforeFieldInit` 这个属性位；
   - 有没有 `.cctor`（静态构造函数），以及 `.cctor` 里到底做了什么。
   读法建议：`dotnet` 环境里用 `System.Reflection.Metadata` 或 `MetadataLoadContext` 直接读 `TypeAttributes`，比翻 `ildasm` 文本更不容易读错；哪种都行，但**要贴出读到的原始值**。
3. 结论要能区分这三种情况是哪一种：
   - CLR 在 `beforefieldinit` 下确实允许"调用静态方法"之前不检查初始化标志（合法惰性）；
   - 我们发射的 `.cctor` 被挂错了东西（比如它其实没包含那个字段初始化器）；
   - 方法调用的 IL 形式（例如经由实例/委托转发）绕过了 CLR 认为"需要确保已初始化"的检查点。

**第二步：用最小实验定性**

在同一个程序集里做 3 个变体，每个都跑，记下"共享字段读到的是 42 还是 0"：
- 只调用共享方法（不读字段）；
- 只读字段；
- 先读一个**别**的类型（普通 `Class`）的共享方法作对照——普通类是同样的 CLR 规则，如果普通类也惰性，那说明这跟脚本提交类无关，只是 CLR 的 `beforefieldinit` 语义。

**第三步：写结论**

- 如果结论是"就是 CLR 的 `beforefieldinit` 语义，脚本没有特殊性" ⇒ 把这句话连同第二、三步的证据写进缺陷登记，并检查规范里那段时机描述有没有说得太绝对。**行为仍然不改。**
- 如果结论是"我们的 `.cctor` 发射有问题" ⇒ **停下来回报，不要顺手改发射**。因为那会变成一个真实缺陷，要按流程重新登记再修。
