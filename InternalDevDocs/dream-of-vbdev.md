## 导读

这条河没有断流，只是在 2020 年后拐进了一条慢行道。语料里躺着 2015 到 2023 的 581 个 issue、5319 条评论；把它们摊开，会看见同一条 VB 河从「两岸还能互相喊话」的年代，流到「官方在河心立了块『不再演进』的牌子」——官方口径是「不演进 ≠ 死亡」，VB 仍在官方支持范围（#592 L9 Kathleen 明言 not dead；#322 L1 官方重申 committed；#499 L4 工具链体验继续改善）——再流到岸边居民自己动手砌台阶的今天。真正的水文缺口不是「河快干了」，而是现代 .NET 的水还没被引进来：这是全稿的主线，**一条延续中的河 × 现代化缺口**。这份文档是一张水文图，摊给造新船的人看：哪些地方水深可航、哪些地方有暗礁、哪些地方两岸其实想去的方向并不一样。 [语料快照基线 · 实锤/已提供]

本稿的读者是未来的 proposal / meeting agent。你每写一个新提案，先回答三件事：**你在帮谁**（§3 persona）、**他此刻的心情是什么**（§4 情绪谱）、**你动的这块水面会牵动哪股力、又踩到哪条张力**（§5 六元素、§2 主线、§7 三方）。证据细节不进正文——每条论断以 `#NNN L楼` 锚与三态标注给出可核位置，正文只保留「值得写进愿景」的那一层。

- **母语者与守业者**：用 VB 想问题的人，和守着二十年系统怕再被断一次代的人——他们常被当成「老用户」一个词打发，其实站在河的两岸，怕的东西并不相同（§2 主线-1）。

## §2 主线叙事（main narrative · pillars）

**主线意象句。** 两群人站在同一条河的两岸——一边是数十万守着二十年系统的守业者，怕的从来不是旧，而是再被断一次代；另一边是几百个想带 VB 追上这个时代的前沿派，却总被一句「这不是 VB 的场景」挡在河心。河还是那条河：VB 那份「只说你要说的」英文式可读是河床；可同一批 legacy 语义又被拖成颈上的铁链。二十年间官方在河上修过桥、立过闸，2020 年又在河心立了块「不再演进」的牌子——官方把话说得很清楚：不是断流，是不再开新航道（Kathleen 原话：「VB.NET is not dead……不计划演进，不代表它死了」，#592 L9；工具链体验继续改善，#499 L4）。水没有停，缺的是把现代 .NET 的水引进来的那截渠——两岸的人于是各自开始造自己的引水槽。 [实锤/已检查：#250 L3/L27 双阵营、#322 L9/L31 官方边界、#497 冻结公告、#592 L9 Kathleen 口径；意象化转述=推测/中-高]

**张力叙事（把两岸的喊话放回时间里）。** 对许多人，VB 是母语而不是工具——思路先在 VB 里成型，再翻译给世界（#250 L4，persona-mother-tongue）。可当官方宣布「VB 进 .NET Core」时，留守的人听见的却是「搬过去可以，新特性与新技术栈就别指望了」（#322 L31/L33）：一半人开始收拾行李，留下一句「I left VB, after about 25 years」就此诀别（#322 L22，社区自述）；另一半人各自想办法自救。有人想造一座 VB6→.NET 的桥，把几十万老 VB6 程序员接回这条河（#323 L1），官方在审查前摇了摇头——25 年 C++ 老编译器，谁也说不清放源会放出什么（#323 L8）；有人讲 13 岁侄子的故事：新一代活在掌上屏幕里，而 VB「既教不了入门、也撑不起专业」（#452 L1）；即便只求「能安全用上 Span 那样的东西」，也被一句「VB 不做指针」挡在门外（#250 L124 ↔ L70；#322 L9，张力：ref-struct 消费）。社区与官方于是互相等待：社区等微软给工具，微软等社区大到值得投（#250 L60）；这份隔阂把每个技术缺口都放大成存在焦虑，「能不能消费现代 .NET 库」这种本不该问的问题，成了上不上得去桌的入场券（#300 L7，张力：水×暗）。等到 2020 官方把「不再演进」写进公告（#497），河心那块牌子终于落地；此后的故事不再发生在官方与社区之间，而是发生在社区自己身上——公开信、自造工具、第二实现（#492/#545/#620，imagery-toolsmith-economy）。 [语料陈述=实锤/已检查；「河岸/收拾行李/铁链/牌子」意象化转述=推测/中]

- **2017 提案潮**：设计子集里大量 Proposal/Scenario 在 2017 上半年涌入，2017-08~12 的 LDM 会期被成批「原则通过但永不排期」或批量否决（#29/#48/#170/#186…），真正实现收束的屈指可数（#65 merged、#121 转 PR）。「占位 milestone + open 不关」从此成为停滞的代理信号。 [实锤/已检查]
- **2018 批量 No-plans**：#322（2018-07）官宣 VB 进 .NET Core 3 是「迁移优先」、新 workload 单语化；2018-10 官方成员密集标注 No plans 并成批静默关闭（#229/#299/#303/#304/#305/#307/#317/#318）。社区称之为「复核全部 open」的落地，实为清场。 [时间指纹核对 · 实锤/已检查]
- **2020 #497 演进冻结**：2020-03-11 官方在博客公告「Going forward, we do not plan to evolve Visual Basic as a language」（#497 帖内 2 楼转引博客原文），GitHub 侧以 #497 作为公告帖；官方口径是「不再演进 ≠ 死亡」——Kathleen 当场澄清「两句话都没有排除语言未来发生变化的可能」（#497 L12），2021 更直接说「VB.NET is not dead」（#592 L9）；2020-10 团队成员自述「VB LDM 目前不活跃，因为 .NET 5 (Core) 与 .NET Framework 保持同一水位、不再给 Framework 上任何语言加特性」（#494 L30）。之后新语言提案在官方通道失去受理可能，转入社区路径。 [语料核读 · 实锤/已检查]
- **2023 公开信**：2023-03-02「Open Letter on the Visual Basic Strategy 2023」（#620）——职业 VB 开发者以集体署名请愿「不求 C# 同款新特性、只求少量能力 + 接受社区 PR」，评论区把出路指向 ModVB/CommunityVB/社区自治。 [语料核读 · 实锤/已检查]

这四道弯是同一件事的四个截面：**官方每一次「缩小承诺」都先于社区的「另寻出路」**——2017 的沉默养出 2018 的 No-plans，2018 的天花板宣言在 2020 变成正式冻结，而冻结又把 2021–2023 的社区从「请愿」推向「自建」。读愿景的人若只看其中一道弯，会误判整条河的方向；五根 pillar 就是要让四条时间线在同一张图上各归其位。 [时间因果链=推测/中；各点锚见上]

**主线取景：一条延续中的河 × 现代化缺口。** 语料里其实能同时读出两组彼此接近的事实：官方与多数资深用户都认为 VB 的语言内核是自洽、够用的——官方反复重申「VB 是 .NET 的一部分、微软对它 committed」（#322 L1），Kathleen 个人判断可读性语言在 .NET 平台限制内「已接近能做到的顶点」（#497 L13），并澄清「不演进 ≠ 没有未来会发生改变」（#497 L12）；社区也大量表达「语言本体没问题，缺的是进不了新平台」（#620 L1 公开信正文「不需要新拼写、只缺未被覆盖的能力」、#620 L4 指是框架改动卡住 VB 而非语言本身；#452 L1 判的是「接不住现代场景」）。真正欠的是**接入层**：现代 .NET 生态持续按 C# 长出 ref struct / NRT / 源生成 / 新 workload（#250 L124、#322 L33、#297、#620 L4），而「不再演进」让这层长期欠账。**给本稿读者的统一取景：语言本体不是问题，现代化接入才是问题**——上游停摆是「未竟的需求测绘」留在档案馆（§6），不是需求失效。**VBScriptDotNet 在此的顺位（一句愿景，只引用不裁决）**：在 VB 既有的专业自洽内核之上，做「增强现代化」的承接与延续——续接上游未竟的需求测绘（§2 主线-2、§6 六簇），并把现代 .NET 能力按 decisions 已站位的方向工程化接入（D1/M7/M8/D2 方向，见 §7）。是否成立以 decisions.md 为准，本稿不裁决。 [官方口径锚实锤/已检查：#250 L23「Microsoft will continue to work on Visual Basic」、#322 L1、#497 L12/L13、#499 L4、#592 L9、#494 L30；「内核自洽 + 现代化缺口」为作者按 Anthony 设计本意的转述=推测/高，直接原语待核（见 OPEN O9）；产品顺位=参考非裁决]

### 主线-1 · 母语者与守业者，同一条河的两个渡口

- **愿景句**：让「用 VB 想问题」的母语者不必每次把思路翻译给世界，也让「守着二十年系统」的守业者不必在每次官宣里先确认自己这次有没有被抛下——一份愿景应当同时回答这两个渡口。
- **对位意象**：母语者把 VB 当思维语言（#250 L4「my mind thinks it in VB, and then I translate」），要的是不被「翻译税」打断的前沿与趣味；守业者把 VB 当不动产（#250 L27「my projects have a lifespan of 20 years+」），要的是「别弄坏、长期在」（#322 L35 六个 Windows 服务「our clients are happy」）。意象 = 同一条河的左岸想要流速，右岸想要堤坝。 [persona-mother-tongue / persona-20y-custodian · #250 L4/L27 原句实锤 + 原型提炼=推测/高]
- **反噬风险**：最大的共同伤疤是 VB6→VB.NET 那次断裂（#323、#250 L126「move-to-.NET 弃旧迎新永久伤了社区」）。任何「为快而 breaking」的提案都会触发守业者的断代恐惧；任何「为稳而拒绝新世界」的姿态都会让母语者与前沿派彻底收拾行李——#322 L22 那位约 25 年 VB 用户就是这样离场的（自述诀别，社区自述非官方定性）。愿景若只讨一边欢心，就等于在河心再劈一刀。 [#250/#322/#323 · 实锤/已检查]

### 主线-2 · 上游停摆 ≠ 需求消失

- **愿景句**：把 vblang 停摆、搁置、No-plans 的提案当成「上游未竟的需求测绘」，按簇接进能落地的河道——而不是当成失效的旧纸。
- **对位意象**：vblang 像一座没有归档员的上游档案馆：提案不是废纸，是还没被接走的测绘图纸。2017 原则通过却永不排期、champion 在场却不排期、团队讨论后搁置 合起来构成最大的搁置成因（§6），而这些簇在语料里反复共振：#124 模式家族 ↔ #337 ↔ #541/#519；#152/#190 Out 系 ↔ #60/#67；#194/#198/#282 INPC 家族；#37 Try/Await 增强。官方拒 ≠ 需求失效：#300 的否决理由被后续生态事实冲击（unmanaged 约束泄漏≠指针、报错误导）却无人重开，原提案作者自述刻意留 open 作「被弃」标记（#300 L10，社区自述非官方定性）。 [搁置成因簇 + 家族共振 · 实锤/已检查；「档案馆/测绘图纸」=推测/中]
- **反噬风险**：收编 ≠ 全收。产品若对上游提案无差别承接，会连「为什么搁置」一起继承——spec 债务、场景门未清、被官方判「非语言特性改道类型系统/框架」的项，接进来只是换一个仓库继续积灰。承接该有的形状是**按簇 + 按成因分流**（§6「要活带什么」）。 [推测/中]

### 主线-3 · 演进冻结与社区自救：官方不开新航道，台阶自己长

- **愿景句**：把 2020 冻结之后社区自造的工具（Vazor/ZML、VBMsgBox NuGet、源生成式补丁、乃至 sVB/ModVB 侧路）当作**设计输入**而非杂音——官方路线图上没有的件，社区用手艺补上了，这本身就是最诚实的场景清单。
- **对位意象**：官方不再演进语言（#497「不演进 VB 语言」，官方口径≠死亡，#592 L9）之后，门前长出一排自己砌的台阶（imagery-toolsmith-economy）：XML literals 被养成 Web 视图引擎（#397 → #510 整套 eShopOnWeb 用 VB 交付）、语言缺的语法点在模板层用 label 属性顶替（#420）、运行时件缺口用 NuGet 自造（#448）。台阶是「官方不开新航道 + 社区还在走」的直接产物。 [imagery-toolsmith-economy · 原句实锤 + 意象推测/中]
- **反噬风险**：自救会走向碎片化。同一条语料里并现「一个 VB、一条向前语言」的合流呼吁（#323 L1 正文：VB6.NET 提案者呼吁把 VB6 与 VB.NET 两岸力量合一、别让同名分家各自漂走）与第二实现/分叉的现实（Mercury #491、ModVB、CommunityVB、B# 式更名 #545b）；调和过程明确观察到「主线拒 vs ModVB 选择性收」不是兜底而是有取舍（选择性收 in-notin/shapeof/wildcard，不收 #507/#512/#543 语义簇）。愿景若把自己摆成「又一个分叉」，会稀释「VB」这个本来就被同名分家反复劈过的名字（imagery-name-heist）。 [#545/#492/#491/#620 · 实锤 + 推测/高]

### 主线-4 · 断代引路：客厅一代 vs 掌上一代

- **愿景句**：让「13 岁侄辈」那一代先在今天设备上做出「真实世界有人用」的成果（#452），而不是先背完 Module/Sub Main/Shared 三件套才够得着屏幕（#155）——入门承诺是这条河的源头活水。
- **对位意象**：教侄辈的桥师在客厅被问「现实里谁会用这种例子」（#452 L1 正文），只能自认「liar」；掌上一代对桌面无感（imagery-generation-shift）。而渐进式引路人给出的解药是「第一课屏幕上只有一行 Console.WriteLine，每个痛点之后再揭开一个概念」（#155 L5）。意象 = 客厅时代的「窗体先于仪式」，与掌上时代的「回报以秒计」。 [persona-bridge-teacher / persona-progressive-teacher · #452/#155 原句实锤 + 推测/高]
- **反噬风险**：只讲入门、接不住专业，就会重演 #452 的判决——「既非入门语言、也非专业语言」，最终被官方以「不可行动」关帖，作者三年后自建 sVB（#452 L6/L7）。愿景不能把低门槛做成低天花板；「先见成果」与「能上大桌」必须同一条路（#37 L14「just to get a seat at the table with the big kids」）。 [#452/#37 · 实锤/已检查]

### 主线-5 · 上桌的互操作：能消费现代 .NET，而不必改行

- **愿景句**：让 VB 用户能安全消费现代 .NET 生态（Span/ref struct/unmanaged 约束泛型/异步/EF），而不是每次都在自己项目里开一个 C# 侧门（#46、#238「99% VB + 1% C#」、#512 表达式树差异）——「能不能上桌」不该成为先决门槛。
- **对位意象**：桌边只有 C# 有座位（imagery-table-seat）。VB 人要么为那 1% 开第二个 C# 项目/DLL（#211）、要么当 C# 模板手译者把每个新示例译回 VB（#475 Azure Function 手改 csproj）、要么被编译器 BC30668 挡在 ref struct 门外（#297）。官方边界「VB 不做指针」（#322 L9/#300 L5）与生态现实（约束泄漏、库按 C# 设计）之间，普通消费方被夹住。 [persona-perf-frontier / persona-cs-template-translator · #300/#297/#238/#475 原句实锤 + 推测/中]
- **反噬风险**：半吊子支持比不支持更危险——调和过程反复出现「不 enforce stack-only 则 VB 给 C# 的 span 全变无效」「ignore Obsolete 全变 unsafe」「all span code in VB becomes unsafe」（#250 L99/L107）的暗雷。愿景若承诺「能消费」却不付编译器理解 ref-safe 语义的成本，等于放行指针而不说（#300/#250 暗维）。正确形状是「能安全消费、不必能定义低层」+ 至少给可执行的诊断出口。 [#250/#300/#297 · 实锤 + 推测/高]

**五条 pillar 怎么用。** 提案/愿景句落笔前，先在五条里找自己的位置：是修「翻译税」（1）、还是接「上游未竟」（2）、或是回应「自造工具」（3）、服务「断代引路」（4）、拆除「C#-only 的门」（5）？多数好提案会同时踩 2–3 条，但至少要能说清「我主要服务哪个渡口、次要服务哪个」——说不清，就回到 §3 再认一次 persona。五条 pillar 的排序也暗示优先级：**先安两岸（1），再收上游（2），接住自救（3），引来新水（4），最后拆门（5）**——这个顺序本身是一个可讨论的路线图草案，不是裁决。 [pillar 用法=推测/高 · 本稿自设]

## §4 情绪谱（10 键 · 含希望）

**情绪是一整段代际的潮汐，不是单个帖子的浪花。** 把 2015–2023 摊平看：前期是火占上风的「愿望清单」年代（渴望/热情高密度，语料里大量「would be nice」「why not」句式）；2018 前后浪头转暗（焦虑/愤怒随 No-plans 起）；2020 演进冻结把浪打碎成失落与绝望式自嘲（#497「VB died – became a zombie language」、#572「we stopped hoping years ago」）；而 2023 公开信是退潮后重新蓄起来的一道浪——不再是个人期许，而是集体署名的请愿与指向社区自治的希望（#620）。这十条键不是十个抽屉，是一条河在不同季节的水位。 [语料句实锤/已检查；潮汐叙事=推测/中]

> **情绪记录 ≠ 官方事实（本谱的总注）。** 本节所有「被弃/死亡/僵尸/悼词」式字眼都是**社区情绪的自述与转述**，不是官方定性。官方口径自始至终是：**语言演进冻结，但 VB 未被宣布死亡、仍在官方支持范围**——Kathleen 2021 原话「VB.NET is not dead. 微软不计划演进它，但这不代表它死了」（#592 L9）；官方承诺 VS 工具链体验继续改善（#499 L4）、VB 是 .NET 一部分（#322 L1）。谱里把「被弃感」记这么高，恰恰说明存在一个**情绪与现实之间的落差**：社区要的不是「语言没死」的澄清，而是可信的现代化接入路径（§2 主线取景）。 [官方口径实锤/已检查：#592 L9、#499 L4、#322 L1、#250 L23、#497 L12]

**语域归类：说 dead/dying 的是谁（register，§4 读谱护栏）。** 语料里「dead / dying / death sentence / abandoned」字眼分属三类语域（按发言者身份归类：官方口径 K / 社区自述 M / 圈外攻击 N，细分见下三式），混读会把情绪谱读反：

- **官方口径（K=7）**：官方从不写死亡判词，反复拆「不演进 ≠ no future ≠ dead」——#497 L12「neither says there is no future where changes would occur」、#592 L9 Kathleen 原话「VB.NET is not dead…does not mean it is dead」；并锚定支持范围（#322 L1 官方重申 committed、#250 L23「Microsoft will continue to work on Visual Basic」、#265 L11「part of all the teams」）与资源分配解释（#250 L116）。其中 #497 L13「可读性语言已近上限」是个人判断，社区读作居高临下（#497 L14）。
- **VB 社区自述（M=26，主体）**：说出 dying/dead/abandoned 的绝大多数是 VB 维护者/使用者自己——哀悼（#592 L7「loved every minute of it」、#540 L3 老成员自判死亡）、抗议与督促（#452 L1「death sentence」、#497 L14、#497 L30、#620 L18）、回击与反讽自况（#545 L5「refuse to die」、#323 L17、#250 L112）、被弃隐喻（#211 L42「unwanted child」）。这是本谱「被弃感」的主来源，不是官方定性，更不是对 VB 的攻击。
- **圈外攻击语域（N=2，稀疏）**：真正的第一手圈外攻击在本仓几乎不存在；可锚定的仅 #540 L1 转述 dotnet/maui 判词（"vb.net is basically dead…"）与 #323 L24 对 VB6 的全面贬斥。其余「外人骂」多以 VB 成员转述/引述面目出现（#250 L43/L44 引「Language Religionists」与 SO「Most Dreaded」、#323 L10、#448 L31、#282 L20，反叙 R=6，不并入 N/M 计数）。

**方法学反例（作者口吻必须守）。** ① 把维护者的自我哀悼当圈外攻击 → 虚增「社区自弃」，§7 身份张力失掉「外人宣告死亡 → 社区 refuse-to-die → 官方 not-dead/not-evolving」的三态结构；② 把社区转述的圈外判词当 VB 人自己的情绪 → 把「外压证据」误记为「内源失落」；③ 采信任一语域为事实 → 无论信 M 的绝望还是 N 的判死，都会把谱读歪。本谱只把 M 系记作情绪记录、K 系记作官方口径、N 系记作外压背景。 [语域归类判定=推测/中-高 · 例句已检查]

## §5 六元素灵气映射（雷风火水光暗）

六元素是验收语言而非硬分类；每条诉求可映射多元素，优先讲张力对叙事而非堆表。以下按元素给「这条河的灵气分布」，再给三组最强张力对叙事。可以这样读六元素：**雷与风是「怎么变」的争辩，水与暗是「变什么」的争辩，火与光是「为什么还变」的争辩**——而河面上几乎每一条提案，都是这六股力同时作用的结果。 [本稿六元素自设 · 已接受 · 读法=推测/中]

- **雷（迭代速度）**：全语料最密集的诉求面——「C# 有而 VB 没有/原则通过却不排期」的追赶焦虑（#306/#222/#320），散糖提案（#23/#47/#62/#75/#80 等成员集判定族）都想要「少几步拿到糖」。雷在 2017 提案潮最旺，2018 No-plans 后被官方压住，2020 后随冻结转成对「节奏消失」的愤怒。 [实锤/已检查]
- **风（演化趋势一致性）**：VB 的品牌护城河——「verbosity is clarity」（#362 L7 官方）、关键字压过标点、case-insensitive 是可用性（#211 L83 dyslexia 论）、「code does what it says」（#355）。风在大部分设计讨论里是「别 me-too、别 breaking、别加符号」的刹车，也是 2020 后官方「稳定不演化」的正当化来源。 [实锤 + 推测/高]
- **火（生命阶段）**：存续叙事的载体——#250 大讨论（谁是社区、谁接棒）、#322/#497 的存续判决（社区眼中的判词；官方口径是「演进冻结」而非死亡，#592 L9）、#492/#545/#620 的自救动员。火最旺的时刻不是热情，而是「感到被宣判」之后；2020 后火元素高度集中在冻结公告前后的 grief/meta 帖。 [实锤/已检查]
- **水（核心竞争力）**：VB 的立身之水 = 少仪式、读得懂、do-what-I-mean（#322 L35 几乎不用 Microsoft.VisualBasic.dll 也舒适）、晚期绑定/脚本/REPL 交互（#323 L22 Immediate Window）。但同一批 legacy 语义又被指为「拖慢一切的铁链」（#250 L124「black hole sucking the innovation out of VB's future」）——**水是最强张力的一极**（见下）。 [实锤/已检查]
- **光（价值发挥/存量保值）**：让既有资产保值增值——数十万 legacy 维护者（#250 L3/L12）、My/运行库开源让旧代码有 future（#280：VB 运行库开源获批并移入 corefx，原误挂 #250 L42；另见 #322 L42）、.NET Core 首次可把传统桌面 app 名正言顺迁过去（#322 L30）。光与「社区自救/第二实现」在同一侧：存量不想沉没。 [实锤/已检查]
- **暗（伦理与法规风险/兼容暗雷）**：半吊子支持的暗雷（ref struct 不 enforce → VB 库对 C# 变 invalid program，#250 L99/L107）、平台弃用/能力边界（#322 L33 新 workload 单语化、#238 Xamarin no plans）、老编译器放源风险（#323 L8）、劣质诊断把用户导向死路（#300 L13「Type '?'」）。暗是「没想清楚就承诺」的报复机制。 [实锤 + 推测/高]

**最强张力对叙事（三组，§2 的 pillar 在元素层的投影）：**

1. **核心特色当减速带（水 × 雷/光）**：一边是「late binding 等运行库语义拖慢一切、若以割舍换更快创新也甘愿」（#250 L124），另一边是「no take-backs、特性至少三年、别 break my s#$t」（#250 L70/L106/L123，官方成员与社区成员）。同一成员早一年还自陈「VB 已约 98% 到位，语言本体不加新特性亦可接受——新东西应加在工具/平台层」（#250 L87，2018-07-24），即「语言可减速、平台要提速」——两处各属一楼，读作两个独立时点。取舍未决项：**不删特色的前提下如何减重**；产品 decisions.md M2（默认安全、按需动态 + `(As Type)` 类型化出口）已给方向，但「特色面 = 实现税」的兑换率从未被量化——官方拒发遥测（#250 L122），包袱与创新速度的兑换率没有数据。 [#250 · 实锤/已检查；产品方向=decisions 已采纳项引用]
2. **能消费 ≠ 能定义（水/光 × 暗）**：unmanaged/ref struct 生态准入（#300/#297/#322 L15「为何不直接支持 Span」）撞官方 no-pointer/no-unsafe 边界（#322 L9/#300 L5）+ 半吊子支持暗雷（#250 L99/L107）。取舍未决项：编译器理解 ref-safe 语义的实现成本 vs 生态准入收益；产品 decisions.md D1（RefStructHelper 移植 + suppress obsolete）与 M8（识别 requires-unsafe/MemorySafetyRules 等新元数据为桥接义务，不含 NRT——见 §7-3）是 .vbx 侧答案，原版 VB 社区此张力无解——#300 被否决却刻意不关、理由被生态冲击却无人重开。 [#300/#250/#297 · 实锤 + 推测/高]
3. **C#-only 的门（水/火 × 暗/风）**：生态/平台入口只对 C# 开——模板只吐 C#（#238 Xamarin、#475 Azure Functions、#268 EF 设计时）、ref struct/表达式树差异把普通消费方挡在门外（#297/#512）、「留 1% C#」成为长期补位（#211）。取舍未决项：跨语言互操作/模板可达性/翻译路径是否是一等体验，还是继续让用户「自带翻译上桌」（§2 主线-5、§7 三方张力）。 [#238/#475/#268/#512/#211 · 实锤 + 推测/高]

**元素的用途。** 未来提案自检：这提案动的是雷（快）还是风（不破）？它在把水做强（VB 不可替代处）还是在替 C# 扩盘？它给光（存量保值）讲故事时有没有交付？它踩的暗雷有没有前置设计？六元素失衡 = 提案会在评审里被哪一岸的人反对，通常早就能在语料里读到。 [已接受]

**「要活带什么」（对产品/未来任务的五条建议，推测/高）：**

一句话总纲：**vblang 用十年证明「被批准」不等于「会活」**——要活，靠的不是再多一张批准，而是排期承诺、spec 收口、场景门清、标签卫生与按簇承接这一整条链路。上表六簇里，真正缺的不是「有人点头」，而是「点头之后有人排期、有人写 spec、有人清理」。

1. **要活需要排期承诺**：原则通过 ≠ 活；「批准 + 无 cadence」是 vblang 最大死因，活水要公开「做/不做/何时」。
2. **要活需要 champion 之外的东西**：vblang 里 champion 在场 ≠ 能推进（#101 作者即团队、自持原型 9 年不排期）——缺的是实现资源与排期，不是旗手。
3. **要活需要 spec 收口 + 场景门清**：spec 债务/场景门未清型债务（#40/#478/#221/#222）是「差最后一公里」的死，收编上游特性前先确认 spec 与场景是否闭环。
4. **要活需要标签卫生 + 定期清理**：产品四态本身就是对 vblang「open 默认态、永不清理」的流程解；状态要如实反映活/死。
5. **要活需要按簇承接 + 按死因分流**：家族共振（模式族/异步族/Out 系/INPC 族/样板族）是承接的最小单位，且要区分「需求死」（接）与「决策死」（尊重判决）与「语境死」（不接）。

## §7 modvb 关系与三方张力
