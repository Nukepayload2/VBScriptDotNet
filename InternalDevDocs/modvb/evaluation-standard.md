# ModVB 建议评价标准

> 依据 vblang（`..\vblang`）的 LDM 会议记录与提案实践提炼，融合 MaterialBox 五维验收框架（效果/特性/品质/属性/炼金成分）。
> 用途：为 `proposals\` 下 102 份 ModVB 建议逐一评价，判定其质量与优先级，供 VBScript.NET 支持范围筛选。
> 证据等级一律遵循 `KeyItems/God/main.md` 六档阶梯：未提供 → 已提供 → 已检查 → 已运行 → 已采纳 → 有结果支撑。

---

## 第一部分：LDM 是什么——风格总结

LDM（Visual Basic Language Design Meeting）是 VB 语言设计团队与受邀嘉宾的**创作型会议**，不是决策投票机构。

### 1.1 会议文化

- **集体声音**：笔记用 `We / We think / We like / RESOLUTION:` 书写，不记录"谁说"。分歧被记录但不点名（"Not all of us are happy with..."）。早期（2014）笔记例外，会点名记票；"集体声音"是 2016 年后逐步固化的理想。
- **安全空间**：不是利益代表谈判，不是作秀场所；目标是"为今天和明天的 VB 开发者创造最好的语言"。
- **诚实记录**：会议停摆、团队精力转移、原始笔记待整理都会如实交代。

### 1.2 讨论方式（四段推进）

1. **场景/背景**：先摆问题缺口（"There's a clear VB parity gap here"）。
2. **候选方案枚举**：方案编号（PROPOSAL A/B/C、Proposal 1/2/3）。
3. **权衡**：Q&A 逐点对比；被否定的备选语法也留档（"OTHER DESIGNS CONSIDERED"）。
4. **结论 + 后续**：`RESOLUTION:` 显式落定，附 `Implication:` 与待办。

### 1.3 决策模式

- **结论标记**：大写 `RESOLUTION:` / `Decision:` 单行呈现。
- **三元工具箱**：推迟（绑定"等到什么信号"）/ 否决（价值×成本×风险逐条打分）/ 显式"什么都不做"（"We're proud not to do anything"）。
- **"值得做但太难"可并存**：热情不抵消可行性（"Fantastic idea, and too hard to do"）。
- **状态机**：标签 `LDM In Process / LDM Considering / LDM No Plans / LDM Rejected` 沉淀为可审计状态。

### 1.4 价值取向

- **"VB 味儿 / idiomatic VB"是硬审美判据**，不符合者即使来自 C# 也会被拒。
- **对破坏性变更几乎零容忍**（"We will almost never make breaking changes"）。
- **缩小范围、分阶段落地**（"Treat it as an optimization, not a feature"）。
- **维护"简单/低仪式感"的海量业务用户群**。

### 1.5 与其他语言的互动

- **默认跟随 C#**，除非有充分理由偏离（"we will follow C# unless there is a compelling reason"）；CLR/库层变更直接委托 C# LDM。
- **但保留"VB 味儿"否决权**：命名、可读性、常量表达式限制等由 VB 独立判断。
- **F# 只作灵感参考**，不作为默认。

### 1.6 证据与严谨性

- 事实/推测/待办显式分层：`TODO` / `Follow-up` / `Probably` / `Suspect` / `OPEN QUESTIONS`。
- 外部验证未到位时写明证据悬置。
- 原始笔记与整理笔记诚实区分。

## 第二部分：VB 希望走向什么样的设计——设计方向

### 2.1 核心定位

VB 自我定位为：**简单、低仪式、可读、面向业务应用、对首次开发者友好、高度稳定**的语言。
"VB programmers put high value on simplicity/low ceremony"；"hundreds of thousands of quiet customers primarily want VB to keep doing what it does now"；JSON 一等支持被视为"吸引首次开发者的强磁铁"。

### 2.2 设计原则清单（评价基准）

1. **永不破坏现有代码**——破坏性变更几乎总是导致 Rejected。
2. **保持 VB-like**——任何"看起来不像 VB"的语法都要被拒或加高门槛。
3. **不引入"第二种做事方式"**——扩展表面积的门槛极高。
4. **默认跟随 C#，除非有充分理由**，但 VB 风格优先于 C# 对齐。
5. **读起来像英语、对新手友好**——可读性 > 声明式精炼。
6. **不为边缘场景加特性**——价值不足即 No Plans。
7. **避免隐蔽的控制流/语义变化**——细微字符改变语义是坏设计（`Return?` 被拒）。
8. **不与既有语法冲突**（如 `!`、类型字符）。
9. **消除常见样板**——用最小语法解决高频痛点（85% 场景优先）。
10. **冗长只在有用时是美德**——显式关键字在有助理解时才保留。

### 2.3 VB 主线 vs ModVB 延伸（用于判断"基因"）

| 主题 | VB 主线 | ModVB（Anthony） | 关系 |
|------|---------|------------------|------|
| 顶层语句 | 推迟考虑 | Immersive Files | 一致/更激进 |
| 多 `For` 变量 / `Exit For j` | Approved-in-Principle | 直接采用 | 一致 |
| `Select Case TypeOf` / 模式匹配 | 最期待、分阶段 | `ShapeOf`+`Matches` | 一致（`Matches` 即 Anthony 提出） |
| Range `1 To 10 Step 2` | speclet 中 | LINQ 增强 | 一致 |
| `Replaceable`/`Replaces` | 推迟 | 完整设计 | 一致 |
| Smart Attributes 注入 | 演示获好评 | 系统化 | 一致 |
| `Out` 参数/隐式声明 | 讨论中 | 完整 | 一致 |
| `Null` 字面量 | 2014 拒绝 | 重点推进 | 主线保守，Anthony 激进 |
| `Let` 替换 `Dim` | 无 | 全文使用 | Anthony 独立延伸 |
| 主构造函数 | 拒绝 | Key 字段+自动构造 | 主线拒绝，Anthony 变体 |
| 通配 Lambda `*.X` | 无 | 有 | Anthony 独立延伸 |
| 临时交/并集类型 | 无 | 有 | Anthony 独立延伸 |
| 目标类型转换 | 无 | 有（自评"会打架"） | Anthony 独立延伸 |
| Null 安全全家桶 | null 条件 AddHandler 已 No Plans | 大范围铺开 | 主线保守，Anthony 激进 |

**根本张力**：主线"默认跟随 C#"，Anthony"故意不跟 C#/F#"；主线对扩展设高门槛，Anthony 是大规模扩张。两者共享直觉但节奏与范围不同。ModVB 是主线外的"沙盒式"激进延伸。

## 第三部分：五维评价框架——核心标准

### 3.1 五维重新定义

| 维度 | 语言设计场景含义 | 评价要点 | 对应证据等级 |
|------|------------------|----------|--------------|
| **效果** | 建议预期的**语言能力/开发者体验改进**是否真实显现 | ① Motivation 是否说清目标改进；② 强度可衡量、示例可演示；③ 有原型/运行证实；④ 是否只解决表象不解决根因 | **已运行 / 有结果支撑**才判定显现；仅书面止于"已提供/已检查" |
| **特性** | 建议**继承 VB 哪些基因**或**引入什么新特性** | ① 是否延续 VB 易读/兼容/宽松基因；② 与既有语法和谐还是照搬外部；③ 强弱可衡量；④ 是否混入杂质特性 | **已检查**（读文档即可核实血缘） |
| **品质** | 建议文档**本身是否规范**、边界清晰、无矛盾 | ① 符合 vblang 六章节模板；② 语法/语义/边界/交互明确；③ 示例来自原文且一致；④ 不凭空虚构语法 | **已检查** |
| **属性** | 建议对项目**六元素灵气**的影响（雷=迭代速度/风=演化一致性/火=生命阶段/水=核心竞争力/光=价值发挥/暗=风险） | ① 加速还是拖慢迭代；② 与演化方向一致还是断裂；③ 激活新阶段还是燃尽；④ 强化差异化还是与 C# 同质化；⑤ 盘活资产；⑥ 兼容破坏/歧义/闭源风险 | **已检查**（预测性，须标"待定"，实际影响须"已采纳"） |
| **炼金成分** | 建议**投喂了哪些材料/触媒**，成分标注是否准确 | ① 来源标注准确（原文章节/借鉴 C#/继承 VB6/原创）；② 成分实际影响符合预期（借鉴 C#=风属性兼容风险、继承 VB6=光/水盘活资产、原创=雷/暗创新、闭源=暗）；③ 是否意外引入杂质 | **已检查** |

### 3.2 五维 × 5 级评分量表（行为锚点）

评分含义：**5 = 达成且实证，1 = 未达成**。

#### 效果（语言能力/体验改进显现程度）
| 分 | 行为锚点 |
|----|----------|
| 5 | 目标改进清晰、示例可操作，且有**原型/运行结果**证实；强度达验收标准，无缺失无消退 |
| 4 | 目标改进明确、边界完整，但证据止于书面（无原型/运行） |
| 3 | 只覆盖部分场景；主效果显现但关键子效果缺失/消退 |
| 2 | Motivation 泛泛而谈，改进不可衡量，示例不能演示改进 |
| 1 | 声称的效果与示例矛盾，或目标定义不清 |

#### 特性（VB 基因继承/新特性引入）
| 分 | 行为锚点 |
|----|----------|
| 5 | 完全延续 VB 基因，与既有语法和谐；职责单一，无杂质 |
| 4 | 主体延续 VB 基因，个别措辞轻微外来味 |
| 3 | 明显借鉴外部但做了 **VB 化改造**；或打包了次要无关能力 |
| 2 | 外来特性**直接照搬**未 VB 化；或多个强无关能力捆绑 |
| 1 | 核心与 VB 基因（易读/兼容/宽松）冲突，或大量杂质 |

#### 品质（文档规范与边界清晰度）
| 分 | 行为锚点 |
|----|----------|
| 5 | 完全符合六章节模板；语法/语义/边界/交互全部明确；无矛盾；未决问题如实列出 |
| 4 | 结构完整、边界基本清晰，仅个别细节不精确 |
| 3 | 缺某一章节或在关键处边界含糊；未决问题被轻描淡写 |
| 2 | 多处章节缺失/顺序混乱；自相矛盾；示例与正文冲突；来源可疑 |
| 1 | 结构崩坏、语义自相矛盾，或**凭空虚构原文没有的语法**（性质最重） |

#### 属性（六元素灵气影响）
| 分 | 行为锚点 |
|----|----------|
| 5 | 对雷/水/光等多维明显正向，暗风险小且有对冲设计 |
| 4 | 主维度明显受益，暗风险小且被显式识别 |
| 3 | 有得有失——某维度受益、某维度受损，文档未充分权衡 |
| 2 | 某关键维度受损且无应对（明显破坏兼容/一致性断裂） |
| 1 | 暗风险突出（借鉴闭源、破坏既有代码），或与语言当前生命阶段背道而驰 |

#### 炼金成分（材料/触媒标注与实际影响）
| 分 | 行为锚点 |
|----|----------|
| 5 | 材料来源标注准确完整；各成分与实际影响相符；无杂质 |
| 4 | 主要成分标注正确，个别来源或属性说明略含糊 |
| 3 | 部分来源未标注（借鉴了 C# 却没提）；标注与影响有偏差 |
| 2 | 来源混淆、影响预估与实际明显不符；混入无关特性未说明 |
| 1 | 完全看不出材料来源；或隐含借鉴闭源等高危材料 |

### 3.3 与 vblang 提案结构的映射

| 提案章节 | 主要落入维度 | 说明 |
|----------|--------------|------|
| `Summary` | 效果 | 一句话定义目标改进，效果验收起点 |
| `Motivation` | 效果 + 属性 | 为什么做/支持哪些场景/期望结果 = 效果目标 + 属性倾向 |
| `Detailed design`（含示例） | 特性 + 炼金成分 | 语法形态体现继承/引入的特性；示例血缘暴露材料来源 |
| `Drawbacks` | 属性 + 品质 | 诚实权衡 = 对灵气维度影响的自我评估 |
| `Alternatives` | 属性 | 考虑过哪些方案/不做此功能的代价 |
| `Unresolved questions` | 效果（证据不足）+ 属性（未定） | 见下方未决问题规则 |

**状态行 ↔ 证据阶梯**（模板顶部四复选框天然对应）：

| 提案状态行 | 对应证据等级 |
|------------|--------------|
| `* [x] Proposed` | 已提供 / 已检查 |
| `* [ ] Prototype: Complete` | 已运行 |
| `* [ ] Implementation` | 已运行 |
| `* [ ] Specification`（LDM 接受后） | 已采纳 |
| 附原型/基准测试结果 | 有结果支撑 |

**"未决问题多不多"的评分规则**：
- 未决问题 **0 个**且是初稿 → 可疑（藏问题或过度自信）→ 品质扣至 3 分以下。
- 未决问题 **1–3 个且具体** → 诚实健康 → 品质 4–5 分。
- 未决问题 **≥4 个关键设计点** → 不直接扣品质（如实列出是加分），而是把**效果证据等级封顶**（核心语法未定型 = 效果未显现，效果最多 3–4 分），属性（风/暗）标"待定"。

## 第四部分：强提案品质清单与弱提案红旗

### 4.1 强提案品质清单（可勾选）

- [ ] **一句话摘要**：Summary 能一段话说清"这是什么"。
- [ ] **真实动机与受益者**：Motivation 明确 use case、目标用户、期望产出；最好有量化数据（如 Implicit-default-optional 的 85% 统计）。
- [ ] **可实现性**：Detailed design 达到"懂语言者能理解、懂编译器者能实现"；含文法（BNF）或 spec 章节修改描述。
- [ ] **示例可运行**：能编译、能演示本特性（非 workaround 或报错）的 VB 代码。
- [ ] **边界与角案例**：覆盖 Option Strict On/Off、ByRef、泛型、异步、late-binding 等 VB 特有分叉。
- [ ] **与既有特性交互**：列出受影响特性并验证不变量（CallerInfo、IsTrue/IsFalse、copy-in/copy-out、semantic model、IDE）。
- [ ] **自反的 Drawbacks**：真实列举"为什么不做"的理由并逐一反驳。
- [ ] **认真探索 Alternatives**：含"什么都不做"的代价，说明当前方案为何胜出。
- [ ] **透明的 Unresolved questions**：明确列出 TBD 项及定夺方式。
- [ ] **兼容性分析**：旧代码行为变化、langversion 门控、错误/警告策略。
- [ ] **可核实的状态证据**：状态栏链接指向真实原型分支/PR，无占位符。
- [ ] **语言审美契合**：不引入与现有特性微妙重复的语法，不显著增加新手复杂度。

### 4.2 弱提案红旗清单（危险信号）

- [ ] Drawbacks / Alternatives / Unresolved questions 三节空置或仅剩模板原文。
- [ ] 动机无 use case、无受益者、无数据支撑。
- [ ] 详细设计停留在"注释掉/跳过某段编译器代码"，无文法、无 spec 改动、无角案例。
- [ ] 示例代码无法编译，或演示的根本不是本特性（概念混杂）。
- [ ] 状态栏为占位链接（`PROTOTYPE_OWNER/roslyn/BRANCH_NAME`、`pr/1`）。
- [ ] 无兼容性/breaking change 分析，且对既有语义根基（IsTrue/IsFalse、AndAlso）只字不提。
- [ ] 细节自相矛盾或笔误（互补对表错、`End Sub`/`End Operator` 混用）。
- [ ] 一份提案混杂多个独立特性，边界模糊。

## 第五部分：LDM 追问清单（评价时的拷问库）

评价任何建议时，模拟 LDM 的追问：

1. **语法/文法歧义**：有无句法歧义？有 body 没 body 怎么区分？
2. **角案例/边界语义**：definite assignment、piecewise 初始化、virtual/static 变体、out/ref 传参？
3. **作用域与绑定**：semantic model 返回什么符号？绑定到 property 还是 backing field？
4. **与既有特性的交互**：ByRef copy-in/copy-out？initializer 读其他成员？lambda 内赋值？
5. **Breaking change 与兼容性**：旧代码行为变不变？重编译行为变不变？
6. **Option Strict / 编译选项分叉**：严格/宽松两条路径行为是否一致？
7. **IDE/IntelliSense 影响**：补全显示什么？ByRef 返回值 IDE 怎么展示？
8. **数据/普遍性**：场景是否普遍？有没有数据或用户请求支撑？
9. **更简单的替代方案**：用 analyzer/现有语法/workaround 是否更优？
10. **复杂度/成本/优先级**：实现成本是否匹配价值？能否缩小场景简化实现？
11. **运行时/CLR 硬约束**：是否破坏 PEVerify？是否触达 CLR 存储规则？
12. **值不值得做**：价值 × 成本 × 风险 三个维度逐条打分。

## 第六部分：评价流程

1. **回读配方**：确认建议的 Motivation/Summary（目标、验收、材料来源）。
2. **逐维核对**：按五维（效果/特性/品质/属性/炼金成分）逐项评分，对照第二部分设计原则与 2.3 主线对照表。
3. **模拟 LDM 追问**：用第五部分拷问库补查边界。
4. **标注证据**：每个判断对照证据阶梯标注等级；预测性结论标"待定"。
5. **出结论**：
   - **五维得分**（每维 1–5 分）；
   - **总判定**：达成 / 部分达成 / 未达成；
   - **优先级建议**：按 LDM 三态给 `Active / Consider / Table / Reject`；
   - **返工建议**：指出应补充的章节/证据/设计探索。
