# Visual Basic Language Design Meeting
September 12, 2026

议题是 `proposal-submission-shared-members`——脚本/提交类里的 **`Shared` 成员**，核心问题是**共享字段/属性的初始化器该落在哪里**。我们把这件事摆在桌上，是因为它今天不是「一个可以商量的设计点」，而是**用户可达却无路可走的一片面**：顶层 `Shared sx As Integer = 5` 编译通过、零诊断，宿主取入口点时 `System.TypeLoadException`（我方实测 exit 34）；把同样的 `Await` 形状换成非共享就一切正常（exit 0，`INSTANCE-OK 2`），换成 `Shared` 就让编译器进程被断言终止（exit 35）。同一份源码、同一台编译器，只差一个 `Shared`，而 `Shared` 恰恰是 `spec\spec-scripting-dialect.md:16`/`:48` 明文承诺过「顶层成员默认是实例成员，**除非声明为 `Shared`**」的那个修饰符。

提案把这件事拆成四个候选：**丙**（主候选，把共享初始化器改道并入已有的 async `<Initialize>`）、**甲**（按 D5 拆出独立的静态构造器符号）、**乙**（移植 CS8100 语义、在绑定期给共享初始化器里的 `Await` 报错）、**丙-2**（新造一个共享版 async 初始化器）。提案的动因来自专项调查的一条结论：**「共享不能 `await`」是实现缺口，不是 CLR 也不是语言规则**——所以我们不是在一个「不可能」面前做取舍，而是在两条都能走通的路之间，问哪一条更配得上 VB。这个问题比它看上去难，因为答案取决于一个我们很少被迫正面回答的问题：**`Shared` 这个字在脚本类里还该不该是同一个字。**

我们两条独立路径各读了一遍——一条沿 VB 基因问「`Shared` 在 VB 里是一条关于**什么时候**的承诺，把共享初始化搬进一个每次运行都跑的实例方法，是不是把 `Shared` 换成了另一个词」；一条沿 C# 生态问「这件事在 C# 里是怎么分的、`SynthesizedStaticConstructor` 与 CS8100 是不是同一张设计图上的东西、丙 那次「有意分叉」的理由够不够」。两条路径在**事实基线**上独立收敛（包括各自独立撞上同一处提案未列出的机制缺口）；分歧只出现在**候选定价**上——一条主张「06 的目标应当是『从崩改成报错』，不是『支持 `Await`』」，另一条主张「丙 机制上无摩擦、可以作为一次明说的分叉支持，但它的分叉面被写窄了、它的核心收益不完整」。我们把两份意见按证据而不是按票数融合，落点在 RESOLUTION。

会议的实际内容落在复核撞出的几处：**提案「丙 同时消掉 issue 05」这句在 `Shared ReadOnly` 这一格上不成立**（两条路径独立发现，各自的探针方向不同、结论相同）；**`spec:176` 那句「字段或属性初始化器是 async 上下文」不能当作丙的分叉理由**（自指）；**丙 的分叉面比提案写宽**（非 `Await` 的 `Shared x = 5` 也从「类型级一次性」变成「每次运行一次」）；**甲 的机制在提交类上已经在跑**（顶层 `Const d As Date = #…` exit 0，实测）；以及**一个提案没有讨论的作用域问题**（丙 的分桶改动不含容器种类门，会连带改掉今天健康的非提交脚本类形状）。提案是冻结输入，对它的修正只写进 RESOLUTION。

### 场景与缺口

`Shared` 方法健康，这件事我们复核了：顶层 `Shared Sub S()` exit 0、`Shared Async Function F() … Await …` exit 0（提案 q04/q32，本轮同形状复核一致）。缺口在**初始化器**这一半，而且它有**两个承重点**，不是一个：

第一个承重点是**共享字段/属性的初始化器**。它今天不是「有 bug」而是「没有落点」：收集期按字段的 `IsShared` 把初始化器放进静态桶（`Symbols\Source\SourceMemberFieldSymbol.vb:628-632` 的数组隐式初始化器、`:665-673` 的 `= …` 形态，其中 `:669` 的注释逐字「const fields are implicitly shared and get into this list.」；属性的分桶在 `Symbols\Source\SourceMemberContainerTypeSymbol.vb:2669-2681`），静态桶又由 `AddDefaultConstructorIfNeeded` 的提交分支无条件交给**为实例版设计**的构造器符号（`:2729` 的条件、`:2735` 的 `New SynthesizedSubmissionConstructorSymbol(..., isShared, ...)`），而那个符号的形参表不查 `isShared`（`Symbols\Source\SynthesizedSubmissionConstructorSymbol.vb:31-38`，`:40-44` 直接回吐）——于是共享初始化器真的被写进一个**带形参的 `.cctor`** 的方法体（`MethodCompiler.vb:1481-1487`：`IsScriptConstructor` 为假 ⇒ 走 `BuildConstructorBody`；`Symbols\MethodSymbol.vb:517-521` 的判据要求 `MethodKind = Constructor`，而共享时是 `SharedConstructor`，承重行 `Symbols\SynthesizedSymbols\SynthesizedConstructorBase.vb:192`）。触发边界比 issue 05 登记的更宽：**不是「有 `=` 初始化器」，而是「静态桶里有需要注入的条目」**——`Shared Dim arr(2) As Integer`（无 `=`）同样 exit 34，`Shared sx As Integer`（无初始化器）exit 0。这一对对照是本轮最有用的判别器，我们在 RESOLUTION 里用它。

第二个承重点是**共享成员体/初始化器里对实例成员的隐式引用**（issue 08）：顶层 `Dim sx = 5` 加一个读 `sx` 的共享方法，编译期零诊断、运行期 exit 58 `InvalidProgramException`（栈顶 `Submission#0.S()`）；把同一份代码放进普通类就报 `BC30369`。根因是一句注释所代表的假设——`Binding\Binder_Expressions.vb:2260-2261` 逐字「Any executable statement in a script class can access Me/MyClass/MyBase implicitly but not explicitly. / **No code in a script class is shared.**」——而 fork 让顶层可以写 `Shared`，所以 `:2263-2265` 那个「隐式引用一律 `Return True`」的提前返回就是一句已经不成立的假设在发号施令。

还有一片与 `Shared` **无关**但同一轮清点浮出来的形状：顶层 `Event` / `WithEvents` 落在提交类上撞 `Debug.Assert(Not ContainingType.IsImplicitlyDeclared)` 族（issue 07；`SynthesizedEventAccessorSymbol.vb:495`、`SourceWithEventsBackingFieldSymbol.vb:66`，同族第三处 `SynthesizedWithEventsAccessorSymbol.vb:93`），以及**嵌套类型**里字段/属性初始化器的 `Await`（issue 09：诊断 BC36937 报得出、却不 gate 发射）。它们与「共享初始化器的落点」只共享「落在脚本类上」这个前提，我们登记、划界、不纳入本单元。

### 我们翻源码时，几处锚点改变了讨论的形状

**发射层比提案写的更干净，而且这一点由两条路径独立复核。** 提案 §Alternatives 丙 的「发射层通」只引了赋值侧（`Lowering\LocalRewriter\LocalRewriter_FieldOrPropertyInitializer.vb:47-54`：`:48` `meReferenceOpt = Nothing`、`:49` `If Not initializedSymbols.First.IsShared Then`、`:52` 才造 `BoundMeReference`）与读取侧（`CodeGen\EmitExpression.vb:669-688`：`:674` 只在非共享时碰接收者、`:684-685` `EmitStaticFieldLoad`、`:687` `EmitInstanceFieldLoad`）。复核时我们发现还有第三处、而且是**绑定期**的：共享字段/属性初始化器的接收者在绑定时**就已经是 `Nothing`**——`Binding\Binder_Initializers.vb:248`（数组隐式初始化器）、`:278-280`（字段）、`:347` 一带（属性）都是 `If x.IsShared, Nothing, CreateMeReference(...)`。这把「改道后发射层不需要 `Me`」从「读、写两侧的发射分派」升级为「绑定、降级、发射三段同向」，是丙的重力所在。但我们也立刻发现：这三处**都不回答**「共享只读字段的赋值算不算它该在的地方」——见下一条。

**「共享不能 `await`」是两处实现缺口，不是规则——这条我们逐一核过。** 语言规则只挡用户手写的 `Async Shared Sub New`：`Symbols\Source\SourceMethodSymbol.vb:523-525` 在构造器修饰符解码里按 `Async` 标志报 BC36950（`ERR_ConstructorAsync`），与 `Shared` 无关（`Shared` 的处理在它之后，`:527-537`）；**没有任何规则**挡住编译器自己把 `Await` 放进 `.cctor`。真正拦住的是「没有一步把它拿出来」：`Lowering\AsyncRewriter\AsyncRewriter.vb:364-368` 的 `GetAsyncMethodKind` 首行是 `If Not method.IsAsync Then Return AsyncMethodKind.None`，而 `.cctor` 的 `IsAsync` 恒 False（`Symbols\SynthesizedSymbols\SynthesizedMethodBase.vb:195-200`，`SynthesizedConstructorBase` 不覆盖它）；`Lowering\LocalRewriter\LocalRewriter.vb:799-830` 的 `VisitAwaitOperator` 又**刻意原样保留**该节点（`:802-803` 注释逐字「Await operator expression will be rewritten in AsyncRewriter」）⇒ 节点必然活到 `EmitExpression.vb:206-209` 的 `Case Else`，而 `:207` 的注释逐字写着「Code gen should not be invoked if there are errors.」——这句话恰好是 issue 09 那条路的反讽。⇒ 我们同意提案的这一条：**这不是 CLR 硬约束**，所以本议题的取舍是设计取舍，不是可行性取舍。（同一条边界在同族的 ref struct 判据上也是单向的：`SourceMemberFieldSymbol.vb:140-145` 的受限类型检查只读类型、不读共享性——源码层面如此，同族调查的实跑「`Dim f As Span(Of Integer)` 与 `Shared f As Span(Of Integer)` 报同一条 BC31396」与之一致，本轮未重跑。）

**我们发现一处提案没有触及的机制，它在丙的核心收益上开了一个洞。** 两条路径各自独立撞到这里，探针方向不同、结论相同。编译器自己把「共享只读字段只有一个家」这条规则**编码成了谓词**：`CodeGen\EmitAddress.vb:261-284` 的 `HasHome`，`:278-279` 逐字 `If field.IsShared Then Return Me._method.MethodKind = MethodKind.SharedConstructor`；它的语言依据是 `InternalDevDocs\vblang\spec\type-members.md:1893-1899`（逐字：「For a shared variable, **in the shared constructor** of the class that contains the shared variable declaration.」）；而 VB 确实把 `ReadOnly` 字段发射成 IL `initonly`（`Emit\FieldSymbolAdapter.vb:160-166` 的 `IFieldDefinitionIsReadOnly` + `Compilers\Core\Portable\PEWriter\MetadataWriter.cs:761-764` 的 `FieldAttributes.InitOnly`）。丙 之后，`Shared ReadOnly total As Integer = 2`（**提案 §6 可运行示例里的那一行**）的赋值会被发射成实例方法 `<Initialize>` 里的一条 `stsfld` 到静态 `initonly` 字段。我们原以为这是硬阻断，**探针推翻了**：`Reflection.Emit` 造出的类型里，实例方法与静态方法对 `static initonly` 字段的 `stsfld` 都成功执行（VB 路径 p20：`FRo` 由 1 → 2 → 9 无异常；C# 路径在 .NET 10 与 .NET Framework 两个运行时上各跑一次，同样成功）。⇒ **运行时不会崩**，剩下的是两件别的事：编译器的 `HasHome` 会把它自己的产物判为「无家」，而这条 IL **不可验证**。于是丙 的定价出现了一个分支：接受不可验证 IL，则 `Shared ReadOnly` 也在搬迁范围内；不接受，则它必须留在静态桶里——**而它一留在静态桶里，`:2729` 的条件就重新成立、那个带形参的共享提交构造器就又被造出来**。实测 `Shared ReadOnly sx As Integer = 5` → exit 34、`Shared ReadOnly Property P As Integer = 7` → exit 34，与 `Shared sx As Integer = 5` 同源。⇒ **「丙 同时消掉 issue 05」这句话只在「非只读」这一半成立**，提案与 issue 05 的补充节都写成了无条件。这是本轮对候选定价影响最大的一条发现。

**我们还发现绑定上下文与执行上下文之间有一条已经存在的缝。** 初始化器的绑定上下文由 `Binding\DeclarationInitializerBinder.vb:54-58` 决定，注释逐字「the binding context for an initialization **needs to be the field or property symbol**」，装配在 `Binding\Binder_Initializers.vb:150-153`。丙 之后这个「所在成员」符号不变（提案自己说绑定期不用改），但赋值被搬进一个有 `Me`、每次运行都跑的实例方法——同一个初始化器长期存在两个不一致的「所在成员」。提案 Unresolved 3 正是这条缝的第一个症状：共享初始化器**被放进** `<Initialize>` 却**仍然读不到**宿主对象/前序提交变量，门槛在 `Binding\Binder_Expressions.vb:2612`（`If currentType.TypeKind = TYPEKIND.Submission AndAlso Not currentMember.IsShared Then`，判的是**引用点所在成员**的共享性；REPL 实测 `Shared Dim s1 = Args` → `BC30469`）。一个设计如果路标是「然后你还得再改一次接收者判据来匹配新的执行位置」，那说明执行位置本身值得再问一遍。

**我们核了「丙 的登记面与宿主契约」，它们都站得住。** 宿主契约零改动成立：`SynthesizedEntryPointSymbol.vb:340-389` 的 `<Factory>` 体恰两条语句（`:361-372` 建实例、`:375-382` `Return submission.<Initialize>()`，另有 `:344`/`:347` 两条形参断言），它不关心 `<Initialize>` 的体里有什么；`GetSubmissionInitializer` 的**零消费点**我们独立复核——全 `Compilers\` grep 只有两处命中且都是定义（`VisualBasicCompilation.vb:921` 的 `Friend Function`、`CSharpCompilation.cs:1894` 的 `internal`），宿主走反射（`Scripting\Core\ScriptBuilder.cs:161-163` 的 `CreateDelegate<Func(object(), Task<T>)>`、`:189-196` 的 `GetEntryPointRuntimeMethod`，报错点在 `:194`）。顺序语义也确实天然保住：字段与顶层语句都往同一队尾追加（`SourceMemberContainerTypeSymbol.vb:1565-1585`，`:1571` 注释逐字「initializers should be added in syntax order」+ `:1572-1573` 两条断言），顶层语句今天已经在这条流里（`:2633`），`spec\spec-scripting-dialect.md:64` 的「in source order」是单一序列模型。**丙 的优点是真的；问题不在这里。**

**最后一个提案没有讨论的作用域面（本轮新增）。** 分桶点本身**不含容器种类门**：`SourceMemberFieldSymbol.vb:628-632`/`:665-673` 与 `SourceMemberContainerTypeSymbol.vb:2669-2681` 对任何容器都跑。而 `AddDefaultConstructorIfNeeded` 只有 `TypeKind = Submission` 那一支才走「带形参的提交构造器符号」（`:2726-2737`）；非提交脚本类（`DeclarationKind.Script`、`TypeKind.Class`，`spec:98`）走的是 `:2739-2758` 的 Class 分支 → `EnsureCtor`（`:2771-2802`，`New SynthesizedConstructorSymbol` 于 `:2800`，形参恒空）——**形状是对的**。非提交脚本类由 `vbc` 的 script 命令行模式可达（`VisualBasicCommandLineParser.vb:1493` 的 `SourceCodeKind.Script`、`:1551`、`:1561` 的 `IsScriptRunner`，配合 `VisualBasicCompiler.vb:96` 的 `scriptParseOptions`），产品宿主则全产 `Submission`（D5 已证实例 4 同向）。⇒ 丙 若按字面实施（「收集期不再把共享字段/属性的初始化器放进静态桶」）会**连带改掉今天健康的非提交脚本类形状**（把它的共享初始化从 `.cctor` 搬进 `<Initialize>`），而提案只论证了提交类。这不是兼容性论据（D6 不允许），是**改动面没有钉边**：要不显式限定到 `TypeKind.Submission`，要不显式裁定非提交脚本类也一起改并给它补回归测试。（「非提交脚本类今天健康」这一条是**推测（高置信）**：源码链闭合——Class 分支造的是无参符号、与甲同形——但我们没构造出该模式下的可观测探针。）

**最后，Release 下的形状我们补了实测**（较旧二进制 `e307d0f`，只当参照）。提案把 Release 行为列为未测，因为它决定「今天到底是崩还是静默产出错东西」。答案分三类：issue 05 形状 exit 34（与 Debug 同，Release 无关）；`Await` 形状 exit 9，异常是 `System.InvalidOperationException: Unexpected value 'AwaitOperator'`——根因在 `Dependencies\Contracts\ExceptionUtilities.cs:21-28`（`Debug.Assert(false, output)` 在 Release 被编译掉，函数返回 `InvalidOperationException`，由 `EmitExpression.vb:209` 的 `Throw` 抛出），**不是静默的错误产物**；而 issue 07 的两处断言族在 Release 下 **exit 0 正常打印**（嵌套 `Event` → `EVENT-OK`、顶层 `WithEvents` → `WE-OK`）——`Debug.Assert` 编译掉之后，那两条路照样把程序跑出来了。这最后一条对 issue 07 的修法有直接价值：**它说明那两处断言在 Debug 之外并不保护任何东西**，至少在这两个形状上如此。

### 候选逐一权衡

**丙（主候选）：我们不采纳。** 先把它的优点记全：机制可行（读、写、绑定三段都不需要 `Me`）；宿主契约零改动；顺序语义天然保住；绑定期确实不用改（`MethodCompiler.vb:599-607` 把**同一个** `scriptInitializer` 与**同一个** `_diagnostics` 传给静态桶与实例桶两条绑定路径）；它确实让顶层共享初始化器里的 `Await` 合法。但四条代价压过了收益：

① **它换掉了 `Shared` 的含义。** 原版 spec 三处逐字：`vblang\spec\type-members.md:1269`「they are run after the program begins executing, but **before any references to a member of the type**」、`:2021`「executed after the program begins, but **before the `Shared` variable is first referenced**」。（我们同时注意到该节 `:1308` 逐字写着「The above guarantees **do not apply** in the situation where a shared constructor is implicitly created for shared initializers」，即「隐式共享构造器」这一格本来就带着「顺序未定义」的免责——所以准确的表述不是「VB 承诺了严格时机，丙 违反承诺」，而是「VB 的模型是**类型级、先于首次引用**，丙 把它换成**语句级、每次运行一次**」，而同一语言里两个 `Shared` 不同义是设计缺陷）。实测代理见 VB 路径 p22：嵌套类 `Public Shared ReadOnly t As Date = MakeT()`、读它的顶层语句写在声明**之前**，输出顺序是 `CCTOR-RAN` 然后 `year=2020`。

② **它的核心收益不完整**（见上一节的 `HasHome`/`initonly` 一格）：`Shared ReadOnly` 要么接受不可验证 IL，要么留在静态桶里、issue 05 对它残留。

③ **它的收益面很窄。** 脚本里最值得 `Await` 的东西——`Args`、宿主 API、前序提交的状态——都在 `Binder_Expressions.vb:2612` 的盲区里（实测 REPL `Shared Dim s1 = Args` → `BC30469`），提案明确不放开（Unresolved 3）。丙 让「共享初始化器可以 `Await`」合法，但能 `Await` 的只剩与会话无关的常量式异步。

④ **它是与 C# 的有意分叉，而三条理由经不起推敲。** 理由①「提交类的『静态』不是 CLR 意义上的进程级静态——每个提交是新类型、宿主逐提交 await」只覆盖「新提交」这一半：同一个 `Script` 重跑时类型与程序集被复用，`.cctor` 不重跑而 `<Initialize>` 会重跑，而**非 `Await`** 的 `Shared x = 5` 也正是这条路上的一员（这一形状 C# 明确支持，`SourceMemberContainerSymbol.cs:5714-5719` + `MethodCompiler.cs:547-550` 的承重行 `:549`）——所以丙 的分叉面比提案写宽。理由②「`spec:176` 早已无 `Shared` 限定词地承诺字段/属性初始化器是 async 上下文，丙 是兑现承诺」是**自指**的：那句话正是本提案 §7a 计划改写的一行，而且同一节的 `:177` 说「The initializer is asynchronous, so the await is legal at run time」，对共享初始化器今天同样不成立——两句话都只是**描述不准确**，把描述改准（加 `Shared` 限定）与「兑现」是对等的两种修法，不能拿它证明必须分叉。理由③「丙 同时消掉 issue 05」——甲 也能消，且代价更小（见下）。⇒ 分叉的理由剩不下一条是甲 无法满足的。

**甲：我们采纳，而且它是这一格的基准形状。** 它是 D5 已证实例 1 的**逐点复制**：C# 的静态初始化器构造器是**另一个类**（`Symbols\Synthesized\SynthesizedStaticConstructor.cs:12` 不派生实例构造器、`:72-78` `ParameterCount = 0`、`:80-86` `Parameters = Empty`、`MethodKind.StaticConstructor`、`:239-245` `IsStatic = True`、`:247-253` **`IsAsync = False`**），而 C# 的提交构造器类里**根本没有 `isShared` 这个入参**（`SynthesizedSubmissionConstructor.cs`），两条支并列在 `SourceMemberContainerSymbol.cs:5701-5708`（`TypeKind.Submission ? new SynthesizedSubmissionConstructor(...) : new SynthesizedInstanceConstructor(...)`）与 `:5714-5719`（`!hasStaticConstructor && hasNonConstantInitializer(StaticInitializers)` → `new SynthesizedStaticConstructor(this)`）。VB 的对侧是**一个类承载两种语义**，甲的改动就是把这一个类拆回两个。**它已经在提交类上跑着**——`CreateSharedConstructorsForConstFieldsIfRequired`（`SourceMemberContainerTypeSymbol.vb:3195-3214`：`:3197` 读 `StaticInitializers`、`:3204` 用 `includingNonMetadataConstants:=True`、`:3206` `New SynthesizedConstructorSymbol(isShared:=True)`）就是同一条路，由 `MethodCompiler.vb:614-639` 单独编译；实测顶层 `Const d As Date = #1/1/2020#` → exit 0。⇒ 这是「延申现有机制」最干净的一例：改动面只有一处分支，且**没有用户可见语义变化**（今天这两个形状都崩）。我们特别钉一条形态口径：甲 **不是**「同一个符号、形参表随 `isShared` 分叉」（那是 issue 05 的候选 A），而是**两个符号**（候选 B）——因为 C# 的静态构造器连类型层次都不同，选 A 会得到一个「形参对了、但仍是一个类承载两种语义」的半成品，那正是 D5 已证实例 1 指控的病灶本身。我们同时记录甲的一处未实测交互（两套机制都按 `.cctor` 名查重：`EnsureCtor` 的键在 `:2773`、对方在 `:3201`，互相可见 ⇒ 「常量初始化器与新造的共享构造器落到同一个 `.cctor`」源码级可达）与一处 C# 侧的 gap（`SynthesizedStaticConstructor.CalculateShouldEmit` 的「全默认值不发射」在 VB 无等价物，属既有分歧、记为后续小项）。

**乙：我们采纳，并把 issue 06 的目标定为「从崩改成报错」。** 提案的一条硬事实我们独立复核成立且应保留：**只往 `GetAwaitInNonAsyncError` 加分支这条路不可达**——`Binder_Expressions.vb:4720-4728` 的 `IsInAsyncContext()` 第二分支逐字 `Return (containingMember.Kind = SymbolKind.Field OrElse containingMember.Kind = SymbolKind.Property) AndAlso containingMember.ContainingType.IsScriptClass`，**不查 `IsShared`**；`:4740-4744` 是 `If IsInQuery … ElseIf Not IsInAsyncContext() Then ReportDiagnostic(… GetAwaitInNonAsyncError())`；`:5055-5069` 只有三个出口。共享字段时 `IsInAsyncContext()` 为真 ⇒ `:4743` 根本不执行 ⇒ 乙 必须改**调用结构**。方向上的两条支撑我们格外看重：C# 侧是**脚本专属**码 CS8100（`Binder\Binder_Await.cs:160-171` 的 `Field` + `IsScriptClass` + `IsStatic`，实例直接 `return false` 放行；`ErrorCode.cs:1335`、`CSharpResources.resx:3831-3833`），VB 侧则有**同族的自有规则** `ERR_BadStaticInitializerInResumable = 36955`（「Static variables cannot appear inside Async or Iterator methods.」，`Errors\Errors.vb:1585`、`VBResources.resx:4736-4738`）——VB 早就表态「静态存储的初始化不允许出现在可恢复方法里」，乙 是把这条方向补到共享初始化器这一格，不是新造原则。三条落地条件我们写进 RESOLUTION：必须**新码**（不复用 BC36937，消息不对症）；判据必须**覆盖共享属性**（C# 的判据看到的是属性的后备字段——`SourceMemberContainerSymbol.cs:5917-5924`、`FieldOrPropertyInitializer.cs:18-20` 的注释逐字「possibly a backing field of a property」，另有 `Binder_Initializers.cs:185`/`:220-226` 把 `ContainingMemberOrLambda` 设成 `FieldOpt` 的承重一环；**而 VB 的属性初始化器 `ContainingMember` 是 `PropertySymbol`，不能照抄**，实测 `Shared ReadOnly Property P As Integer = Await Task.FromResult(7)` exit 35、与共享字段同一承重点）；必须**改调用结构**。乙 的覆盖边界也要写清：它只覆盖**顶层**共享字段/属性初始化器，**不覆盖**嵌套类型那条（issue 09）。

**丙-2：我们不采纳。** 排序语义必破是实锤：`SynthesizedEntryPointSymbol.vb:340-389` 的 `<Factory>` 体是写死的两条语句（`:384-388`），而 `spec:64` 要求「in source order」的单一序列 ⇒「第 3 行的共享初始化器在第 5 行顶层语句之前」在两方法模型里无法表达。除此之外还有一条 C# 侧的代价：它会新增一个 C# 侧**不存在**的合成入口点成员，并要 `<Factory>` 承担「两个 task 合成一个」，而 `spec:169` 逐字把 `<Initialize>`/`<Main>`/`<Factory>`/`Submission#N` 列为「spelled identically in the C# scripting implementation, so tooling … can rely on the spelling being stable **across languages**」。⇒ 收益与丙 相同、代价更高，无位置。

### 一处需要明说的取舍依据

提案 §「候选关系」更正过一句旧表述（「甲与乙不可互相替代 + 06 只能从崩改成报错」），更正的理由是丙 让 06 变成「支持」。我们**否决了丙**，于是那两句话在结论上重新成立——但**依据不同，必须写清**：不是「没有别的路」，而是「另一条路（丙）的收益不完整、代价是语言概念改义」。我们**不**沿用旧表述的字面理由，也不以「改了既有语义」为由否决任何候选：按 D6，本议题涉及的形状今天全部必崩或必错（`Shared sx = 5` → 34、共享 `Await` → 35、共享只读 → 34、隐式 `Me` → 58），**没有在用语义可破坏**，兼容性在本轮一次也没有被用作否决理由。

## RESOLUTION

1. **issue 05 的修法取「甲」**：`SourceMemberContainerTypeSymbol.vb:2726-2737` 的 `TypeKind = Submission` 分支按 `isShared` 分叉——共享时走同文件的 `EnsureCtor`（`:2771-2802`，`New SynthesizedConstructorSymbol` 于 `:2800`，形参恒空见 `SynthesizedConstructorSymbol.vb:49-53`），实例时仍走 `SynthesizedSubmissionConstructorSymbol`。**形态是「两个符号」（issue 05 候选 B），不是「一个符号、形参表分叉」（候选 A）**——依据 D5 已证实例 1：C# 的静态构造器是另一个类、连类型层次都不同（`SynthesizedStaticConstructor.cs:12`、`SynthesizedSubmissionConstructor.cs` 类里没有 `isShared` 入参）。`plan` 阶段前置实证一条验收用例：同一文件同时含 `Const d As Date = #…`（走 `CreateSharedConstructorsForConstFieldsIfRequired`）与 `Shared x As Integer = 5`（走新分支），确认两者落到同一个 `.cctor`。
2. **issue 06 的目标是「从崩改成报错」，修法取「乙」**：在绑定期给共享字段/属性初始化器里的 `Await` 报诊断。三条硬条件：(a) **新错误码**（脚本专属，形状对齐 CS8100；不复用 `ERR_BadAwaitNotInAsyncMethodOrLambda = 36937`）；(b) 判据覆盖**共享属性**（VB 的初始化器 `ContainingMember` 是 `PropertySymbol`，不能照抄 C# 的 `case SymbolKind.Field`）；(c) 落点在**调用结构**（`Binder_Expressions.vb:4740-4744` 一带），不是 `GetAwaitInNonAsyncError`（`:5055-5069`）里加 `case`——共享字段时 `:4743` 不可达（实锤）。
3. **不采纳「丙」**（共享初始化器改道并入 `<Initialize>`）。否决理由全部落在 D6 明文保留的四类里，**不涉及兼容性**：(a) 它把脚本类的 `Shared` 换成与语言其余部分不同义的东西（`type-members.md:1269`/`:2021` 的模型是类型级、先于首次引用），而同一 `Script` 重跑还会使「非 `Await` 的 `Shared x = 5`」由类型级一次性变成每次运行一次（C# 在同位置是 `.cctor` 语义）；(b) 它的核心收益「同时消掉 issue 05」在 `Shared ReadOnly` 一格上不成立（见 4）；(c) 收益面窄（`Binder_Expressions.vb:2612` 仍挡住宿主/前序提交），代价面在**声明收集期**，牵动的约束比甲 多；(d) 与 D5 的同形性反向（甲 才是 C# 的逐点复制）。**记录复活条件**：若日后要让共享初始化器支持 `Await`，须先重写分叉理由（必须覆盖「同一 `Script` 重跑」这一半）并关闭 `Shared ReadOnly` 一格（先跑 ILVerify/PEVerify 拿实锤再裁）。**另外**，如果将来真走这条路，改动必须显式钉容器种类（分桶点不含容器门，见 8）。

## Implication

落定之后，共享字段/属性的初始化器这条线变成**一条形状正确、语义不变的路**：它仍由无参共享构造器承载（甲），因此 `Shared` 在脚本类里与语言其余部分同义（类型级、先于首次引用），`Shared ReadOnly` 的赋值仍在共享构造器里（符合 `type-members.md:1893-1899`），不引入任何不可验证 IL；其中写 `Await` 的形状从「终止编译器进程」变成「一条能定位到行的诊断」（乙），与 C# 的 CS8100 同向。D5 的已证实例 1（提交构造器两类分立）从「登记在册的分叉」变成「已落地的对齐」，`decisions.md` 的该条**无需改写**。

反过来，我们放弃了一次「让共享初始化器可以 `Await`」的机会，也放弃了把共享初始化器与实例初始化器在机制上抹平的想法。我们清楚这次放弃的边界：不是因为「不可行」（丙 机制上通得过，我们复核了），不是因为「怕 breaking change」（D6，且今天没有在用语义可破坏），而是因为**它要求 `Shared` 在脚本方言里换一个意思**，而这个代价买到的东西（与会话无关的异步表达式可以做共享初始化）与它放弃的东西（语言概念的单一性、`ReadOnly` 规则的完整性、更小的改动面）不成比例。如果将来产品真的需要这一格，条件写在 RESOLUTION 3 里。

对相邻单元的影响：`meeting-script-extension-methods` 的 R17 把 p10 的最小修法写成「形参表随 `isShared` 分叉」（issue 05 候选 A），与本轮的甲（候选 B）不一致——按 D5 的口径应指向候选 B，我们在此记录该措辞订正。issue 07 / 08 / 09 各自独立，`plan` 阶段请分别立项，不要把三条并进同一份设计。
