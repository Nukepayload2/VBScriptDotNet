议题是 `proposal-script-extension-methods`——脚本模式下**哪些类型可以承载扩展方法**、承载不了时**该说什么**、承载了之后**跨提交还算不算数**。提案把这件事钉在一条全局判据上：`AllowsExtensionMethods`（`Compilers\VisualBasic\Portable\Symbols\NamedTypeSymbolExtensions.vb:108-111`）逐字 `Return container.TypeKind = TypeKind.Module OrElse container.IsScriptClass`。脚本类第一次成为「扩展方法的家」，而它**没有**标准模块那份隐式 `Shared`（`vblang\spec\types.md:689` 逐字「A *standard module* is a type whose members are implicitly `Shared`」），于是同一个概念在两种宿主里要求相反的修饰符（标准模块里写 `Shared` 是 BC30433，`Compilers\VisualBasic\Portable\Binding\Binder_Utils.vb:1685-1695` 的 `InvalidModifiersInModule` 首项即 `SyntaxKind.SharedKeyword`；脚本类里不写它则连诊断都没有）。三处缺口（非 `Shared` 成员无诊断、顶层 `Module` 静默失效、跨提交不可收集）都是从这一条判据与「模块成员隐式共享」这条前提的错位里长出来的。

我们两条独立路径各读了一遍——一条沿 VB 基因问「`<Extension> Shared Function` 在脚本顶层算不算给 VB 开第二种做事方式、按 VB 习惯写代码的作者第一直觉会撞到什么」，一条沿 C# 生态问「这件事在 C# 里有没有先例、`InSubmissionClassBinder` 与 CS1105/CS1109 是不是同一张设计图上的东西」。两条路径在四个缺口的事实基线上独立收敛，也都把提案的探针当作既定输入接受；分歧只出现在**候选的定价**与**提案自述的三处 C# 事实**上。

会议的实际内容落在复核撞出的几处：**提案 §7 有一行把 C# 与 VB 写成同义、而缺口②正住在那个错里**；**缺口②的根因不是「缺一条诊断」，是 VB 内部两个谓词的分裂**；**一条 C# 既有诊断（嵌套容器，CS1109）提案没认出来，它是 F 的最强论据**；**既有两个正向测试在空转的原因被定位到两层，其中主因与 Option Strict 无关**；以及**提案两处代价被低估**（C、窄 D）。提案是冻结输入，对它的修正只写进 RESOLUTION。

## Proposal: 脚本类中扩展方法的合法形式与缺失诊断 / Extension Methods in Script Classes

_Related: [`../proposals/proposal-script-extension-methods.md`](../proposals/proposal-script-extension-methods.md)；姊妹会议与父域 `../proposals/proposal-scripting-dialect.md` / `../meetings/meeting-scripting-dialect.md`（本单元只写「顶层类型的落点层」及其牵动的扩展收集，不重述声明/提交模型）；扩展能力的另一端 `../proposals/proposal-consume-csharp-extension-and-interface-shared.md`；缺陷登记 `../issues/issue-script-top-level-extension-method-crash.md` 与 `../issues/issue-submission-shared-field-initializer-typeload.md`；决策 `../decisions.md` D5（`:35-46`，本提案的三个缺口分别落在 D5 已证实例 2 / 实例 3 的核对 / 实例 4 与「名字查找」区域）；共享层台账 `../upstream-merge.md`_

### 场景与缺口

脚本里写扩展方法是**可达且已经能用一半**的能力：顶层 `<Extension> Shared Function Twice(s As String) As String` 之后 `"abc".Twice()` 输出 `abcabc`（提案 p1，已运行；本轮对同一形状的复核一致）。问题不在「要不要这个能力」，在**它的边界没有把关点**，而且边界上有三种不同形状的失败：

1. 漏写 `Shared`。Debug 构建被 `Debug.Assert(Me.IsShared)`（`Compilers\VisualBasic\Portable\Symbols\Source\SourceMethodSymbol.vb:1504`）终止进程，Release 越过断言后在降级层对 `Nothing` 求 `.Type`（`Compilers\VisualBasic\Portable\CodeGen\Optimizer\StackScheduler.Analyzer.vb:662-663`）。输入是最普通不过的顶层声明。
2. 顶层 `Module`。它被降级成脚本类的嵌套类型，其中的 `<Extension>` 声明点**零诊断**（连 BC36551 都不报），调用点只给一条指错方向的 BC30456，**模块自己的方法体内也取不到自己的扩展方法**。
3. 跨提交。REPL 提交 2 声明 `<Extension> Shared Function Twice`，提交 3 调 `"abc".Twice()` 报 BC30456；同一形状的**普通成员**跨提交正常。提交链遍历只实现了成员查找这一半。

我们最在意的一条是：**这三种失败都发生在「按 VB 教的方式写 VB」之后**。VB 教人写扩展方法的方式是「放进 `Module`，别写 `Shared`」。脚本作者照做，只有两条路——把 `Module M ... End Module` 原样搬上来（缺口②），或者把方法体搬到顶层、照模块习惯只写 `<Extension>`（缺口①）。所以评价候选时我们问的不是「它修了哪个缺口」，而是「按 VB 习惯写的作者，第一直觉会得到什么」。

### 翻源码：锚点逐一复核

**`AllowsExtensionMethods` 的四个消费点属实，是实锤。** 全仓检索 `AllowsExtensionMethods` 只命中五处，除定义（`NamedTypeSymbolExtensions.vb:109`）外四处在 `SourceMemberContainerTypeSymbol.vb:3341`（收集侧三合一判据）、`SourceMemberMethodSymbol.vb:86`（快速属性过滤）、`SourceMethodSymbol.vb:1501`（早期解码）与 `:1627`（完整解码的诊断序列）。提案这一条「全仓有 4 个消费点」成立。

**诊断序列独缺 `Shared` 检查属实。** `SourceMethodSymbol.vb:1621-1648` 逐行读下来是：`MethodKind` 非法 → `ERR_ExtensionOnlyAllowedOnModuleSubOrFunction`（`Errors.vb:1327` = BC36550）；`Not m_containingType.AllowsExtensionMethods()` → `ERR_ExtensionMethodNotInModule`（`:1328` = BC36551）；`Me.ParameterCount = 0` → `ERR_ExtensionMethodNoParams`（`:1329` = BC36552）；`Else` 内先 `Debug.Assert(Me.IsShared)`（`:1634`）再查首参 Optional / ParamArray / 泛型约束。「成员必须 `Shared`」这一条**在整段序列里没有位置**。而负向测试也不是零——`Compilers\VisualBasicSymbolTest\SymbolsTests\SymbolErrorTests.vb:17292`（BC36551）与 `:17315`（BC36552）都在——缺的恰是这一条，且因为诊断不存在，**它今天不可能有测试**。

**C# 侧是两段独立检查，而提案把其中一段认成了另一段。** 我们逐行读 `Compilers\CSharp\Portable\Symbols\Source\SourceOrdinaryMethodSymbol.cs:204-257` 的 `ExtensionMethodChecks`：`:213-229` 首参检查；`:230-232` `(object)ContainingType.ContainingType != null` → `ERR_ExtensionMethodsDecl`（**CS1109**，`CSharp\Portable\Errors\ErrorCode.cs:669`）；`:234-242` `!ContainingType.IsScriptClass && !(ContainingType.IsStatic && ContainingType.Arity == 0)` → `ERR_BadExtensionAgg`（CS1106）；`:243-246` `else if (!IsStatic)` → `ERR_BadExtensionMeth`（CS1105）。**`:230` 那条只看「容器是否嵌套」，不看容器种类，且不带 `IsScriptClass` 豁免**（豁免只出现在 `:234` 的白名单那一条）。对照 VB：`:1627` 的判据是 `AllowsExtensionMethods()`，对**嵌套 `Module` 一律放行**（`TypeKind.Module` 分支为真，不看嵌套）。

于是提案 §7 对照表的「嵌套类型」一行（C# `:230-232` ↔ VB `:1627-1628`）**把两件不同的事写成了同义**：C# 是**嵌套检查**，VB 是**容器种类检查**，两者在嵌套 `Module` 上给出相反答案。这一格不是措辞问题——**缺口②的全部内容就住在这一格里**。改对它的收益是实打实的：F 的定性从「脚本专属新诊断」变成「**把 C# 有、VB 移植时丢掉的那一段检查补回来**」，而这份提案的核心论据正是「移植不完整」，所以这是白捡的论据。

顺着这一格我们还找到一条 VB 自己写下的旁证：**消费侧**（PE）的容器判据里「顶层」这条要求是在的——`Compilers\VisualBasic\Portable\Symbols\Metadata\PE\PENamedTypeSymbol.vb:921-936` 逐字注释「Only top level non-generic types with an Extension attribute are valid containers of extension methods.」，判据含 `_container.Kind = SymbolKind.Namespace AndAlso _arity = 0`（`:929`）。也就是说「顶层」在 VB 的语言里**实有**，只是**声明侧漏了检查**。

**缺口②的根因是 VB 内部两个谓词的分裂（正向发现）。** 同一个事实在 VB 有两份互相不一致的谓词：诊断侧问 `AllowsExtensionMethods()`（`SourceMethodSymbol.vb:1627`，不说嵌套）；收集侧问 `MightContainExtensionMethods`（`SourceMemberContainerTypeSymbol.vb:3336-3348`），后者在 `:3341` 要求 `_containingSymbol.Kind = SymbolKind.Namespace AndAlso Me.AllowsExtensionMethods() AndAlso Me.AnyMemberHasAttributes`。嵌套 `Module` 的 `_containingSymbol` 是脚本类而不是命名空间，于是**声明期放行、收集期静默否决**。这条比「缺一条诊断」精确得多，也是 F 可以「不新造机制」的根据：把已有的事实从「静默否决收集」升级为「同时报诊断」，判据无需新造。C# 在两处用的是同一事实，且两处都说（收集侧靠命名空间遍历天然排除，诊断侧 CS1109）。

我们顺手确认了 F 不需要碰早期解码：嵌套 `Module` 的 `isExtensionMethod` 本来就为 `False`（`:1511` 的 `m_containingType.MightContainExtensionMethods` 为假），所以 `:1504` 的断言对它不可达（p3 无断言即其行为证据）。**B 则必须碰**——p2 的断言栈就是 `:282 → :439 → :1504`。

**缺口②的收集侧我们还核到一条：一个既有常规 VB 测试把「嵌套模块不承载扩展方法」钉住了。** `Compilers\VisualBasicSymbolTest\SymbolsTests\ExtensionMethods\ExtensionMethodTests.vb:1036-1067`（`MightContainExtensionMethods_InSource`，`<Fact>` 非条件门控）用 `Module Module1 / Module Module2 / Class Class1` 断言 `module2.MightContainExtensionMethods` 与 `class1.MightContainExtensionMethods` 均为 `False`（`:1061`、`:1065`）。它对 E-a 的定价有直接含义：放宽 `:3341` 必须**脚本作用域**（提案已写对——加 `OrElse _containingSymbol.IsScriptClass`），否则会翻掉这条断言；反过来说，这条断言也是 E-a 落地时的现成回归锚。

**缺口③（候选 A 的证伪）复核属实。** 把接收者搬进实参表、清空 `ReceiverOpt` 的是降级层：`Compilers\VisualBasic\Portable\Lowering\LocalRewriter\LocalRewriter_Call.vb:77` 调用 `:120-147` 的 `UpdateMethodAndArgumentsIfReducedFromMethod`，后者以 `method.CallsiteReducedFromMethod` 判定扩展调用、把 `receiver` 插到实参表第 0 位（`:133-143`）后 `receiver = Nothing`（`:145`）、`method = reducedFrom`（`:146`）。发射端看到的就是「接收者进实参表、`ReceiverOpt` 为空」的静态形状。而 `StackScheduler.Analyzer.vb:656-683` 的两条分支正好把这个形状钉死：非共享分支解引用 `receiver.Type`（`:663`），共享分支断言 `receiver Is Nothing OrElse receiver.Kind = BoundKind.TypeExpression`（`:682`）。p1 在 Debug 构建下通过（该断言在 Debug 执行，`CodeGen\CodeGenerator.vb` 与 `Optimizer.vb` 均为无条件调用），反过来证明扩展调用的 `receiver` 就是 `Nothing`。**两份形状在同一 `BoundCall` 上不可同时成立，「加个分支」不是 A 的实现路径。**

**缺口④的机制链逐条属实，且 C# 的对照是同一个动作。** `Binding\Binder_Lookup.vb:858-936` 的 `LookupInSubmissions` 逐提交用 `LookupWithoutInheritance(submissionSymbols, submission.ScriptClass, …)`（`:874-875`），推进在 `:885`/`:916`，末尾 `:932` 留 `' TODO (tomat): extension methods`；名字枚举侧同构（`:2030-2051`，TODO 在 `:2050`）。入口在 `:583-584`（`TypeKind.Submission` → `LookupInSubmissions`）。而扩展收集走的是**独立的 binder 链遍历**：`LookupForExtensionMethods`（`:1183-1259`）沿 `currentBinder.m_containingBinder` 逐级调 `CollectProbableExtensionMethodsInSingleBinder`（`:1219`、推进在 `:1256-1257`），链上每一级的贡献点就是 `Binding\NamedTypeBinder.vb:99-107` 的 `_typeSymbol.AppendProbableExtensionMethods`（`Symbols\NamedTypeSymbol.vb:318-330`，只被 `MightContainExtensionMethods` 门控）。顶层链由 `Compilers\VisualBasic\Portable\Binding\BinderFactory.vb:172-177` 构造：`NamedTypeBinder(rootNamespaceBinder, SourceScriptClass)`，父是 `NodeUsage.CompilationUnit` 的 `NamespaceBinder`（`:159-161`）。**这条链上没有提交节点**，上游作者在两处留下了同一句 TODO。

C# 把同一件事做成了 binder 节点：`Compilers\CSharp\Portable\Binder\InSubmissionClassBinder.cs:26-53`，`GetAllExtensionCandidatesInSingleBinder`（`:34-40`）里 `for (var submission = this.Compilation; submission != null; submission = submission.PreviousSubmission) { submission.ScriptClass?.GetAllExtensionMembers(...); }`。**两侧的钩子契约同形**——VB `Binder.vb` 的 `CollectProbableExtensionMethodsInSingleBinder` 对 C# 的 `GetAllExtensionCandidatesInSingleBinder`，链遍历都在调用方。所以「新造一个 binder 节点、override 该钩子」在两侧是同一个动作，H 的形态 (a) 是名副其实的移植，而不是发明。

**一条提案未写的四条排除规则（正向发现）。** 缺口④的「空转」分析落在 `Binder_Lookup.vb:1176-1181` 的 `ShouldLookupExtensionMethods` 上。提案与两条独立路径都只引了 `:1178` 的 `Not container.IsObjectType()`；我们逐行读下来，这个谓词**有三条子句**：

```vb
Return options.ShouldLookupExtensionMethods AndAlso
   Not container.IsObjectType() AndAlso
   Not container.IsShared AndAlso
   Not container.IsModuleType()
End Function
```

中间那条 `Not container.IsShared` 是**空转的**——`Symbols\TypeSymbol.vb:257-261` 逐字「VB doesn't have a concept of shared types.」后 `Return False`，故对任何类型接收者它恒为真。第三条 `Not container.IsModuleType()`（`Symbols\TypeSymbolExtensions.vb:150-153` = `TypeKind.Module`）**额外排除标准模块类型的接收者**。所以真正按接收者类型起作用的排除是两条：`Object` 接收者与 `Module` 接收者（第一条子句 `options.ShouldLookupExtensionMethods` 是选项门，不是接收者排除）。模块接收者在脚本里是否可达（例如把模块名当接收者用）**我们未实证，标推测**；但这条修正了提案的表述——**「`Object` 接收者被排除」只是排除集的一半**，而这一点对「诊断只能落在声明点」的结论是加强而不是削弱。

**「既有测试空转」的两层归因成立，且主因与 Option Strict 无关。** 我们逐行核了两个测试（`ExtensionMethodTests.vb:2425-2440` 与 `:2442-2478`；后者提案引作 `:2443-2481`，`End Sub` 实际在 `:2478`）：两者接收者都是 `Object`（`Dim o As New Object()`），前者只 `comp.VerifyDiagnostics()` + `Assert.True(comp.SourceAssembly.MightContainExtensionMethods)`（`:2438-2439`），后者只两次 `VerifyDiagnostics()` + 声明侧断言（`:2468-2469`、`:2476-2477`）——**都不涉及调用点解析**。判别探针 p13d（`Option Strict On` 下得 BC30574，而不是「扩展被采用」）把主因钉在「扩展查找根本没跑」，与编译选项无关；Option Strict Off 只决定「排除之后是静默晚绑定还是报错」。

这里我们额外发现一处产品路径的硬锚点：脚本宿主的 `Option Strict Off` **不是**继承自编译选项默认值，而是 `Scripting\VisualBasic\VisualBasicScriptCompiler.vb:218` 在 `CreateSubmission` 里写死的 `optionStrict:=OptionStrict.Off`（对照 `Compilers\VisualBasic\Portable\VisualBasicCompilationOptions.vb:75` 的默认值）。这比「默认值是 Off」更硬，也说明这条宽松基因是宿主的显式选择。

**kind 映射复核属实，且我们从第三个角度又看到一次。** `Scripting\VisualBasic\VisualBasicScriptCompiler.vb:208-232` 的 `CreateSubmission` 走 `CreateScriptCompilation`（`Compilation\VisualBasicCompilation.vb:368-389`，`:388` 写死 `isSubmission:=True`，脚本类名在 `:215` 传给 `scriptClassName`）；`CommonCompiler` 那条路走公有 `Create`（`:327-341`，`:339` 写死 `isSubmission:=False`）。我们在声明树构造层又撞到同一条分叉：`Declarations\DeclarationTreeBuilder.vb:140` 的 `kind:=If(_isSubmission, DeclarationKind.Submission, DeclarationKind.Script)`。产品内 `VisualBasicCommandLineParser.Script` 的 8 处调用方也复核一致（`Vbi.vb:18`、`VisualBasicReplServiceProvider.vb:21`；`MockVbi.vb:11`、`CommandLineTests.vb:67`、`ImportsAccumulationFailureTests.vb:168/:194/:207/:220`），且 `Scripting\Core\Hosting\CommandLine\CommandLineRunner.cs` **零 `CreateCompilation` 调用**，三条执行路径都是 `Script.CreateInitialScript<…>`（`:243`、`:291`、`:357`）。

**一条陈旧的注释（正向发现，`Suspect`）。** `DeclarationTreeBuilder.vb:192` 的注释逐字是「Script class is not static and contains no extensions.」，与 C# `CSharp\Portable\Declarations\DeclarationTreeBuilder.cs:292` **逐字相同**（两个函数目前是一对一镜像，连命名空间分流的注释都同义）。而 fork 的 `AllowsExtensionMethods` 恰恰把脚本类当成扩展容器。我们推断这是「脚本类承载扩展方法是后打的补丁、注释没跟上」的迹象——但该注释处于 `declFlags` 语境、并不直接断言扩展收集，故记在此处标 **`Suspect`**。它与「缺口①连负向测试都没有」是同一个故事。

### 权衡一：缺口① —— B 是移植补全，G 是拼写发明，C 是反向分叉

**B（维持现状 + 补诊断）是组①里唯一纯粹的移植缺口。** C# 在同一位置有 CS1105，文案逐字「Extension method must be static」；VB 侧四条消费点、两处断言、零诊断。B 不改 IL 形状（`Shared` 的发射路径已由 p1 实测健康），并且把「必须 `Shared`」这件**有语义的事**在**声明点**告诉作者——`Shared` 在这里不是仪式，它承载「没有实例上下文」这个语义（标准模块的隐式 `Shared` 之所以无害，是因为模块里没有任何实例状态可失去；脚本类里有）。条件有两条：早期解码的守卫必须与诊断**同批**落地（否则 p2 仍终止进程——这是实锤，`SourceMethodSymbol.vb:1500-1504` 与 `:1633-1634` 两处断言），诊断消息要点名 `Shared`。

**C（整体禁止脚本类的扩展方法）我们反对，而且提案的定价过乐观。** 提案说「缺口④让 C 的代价下降」——这个打折不成立。缺口④只发生在**提交链**上；`.vbx` 文件执行是**单提交**（`spec\spec-scripting-dialect.md:163` 逐字「A `.vbx` file that is executed as a script is a submission and therefore goes through `<Factory>`；the two paths are distinguished by whether the compilation is a submission, not by the file extension.」），在那里扩展方法 100% 可用（p1 就是 `.vbx` 形态的实证）。C 拿走的是**主场景的全部**。它还与 C# 显式豁免脚本类反向：`SourceOrdinaryMethodSymbol.cs:234` 的 `!ContainingType.IsScriptClass` 是 C# 里唯一让 `.csx` 能写扩展方法的路（嵌套 `static class` 在 C# 被 CS1109 拒绝），而脚本里没有 `Namespace` 可供改道（BC36965，提案 p7）。C 之后 `.vbx` 里**没有任何**写扩展方法的位置。

**G（带 `<Extension>` 的顶层成员隐式 `Shared`）我们赞成方向但不上主路，表为可选项。** 它确实是「低仪式」一边的诚实答案，且同时消掉 p2 崩溃与「必须写 `Shared`」的别扭；**元数据与语义与 B 完全等价**（它不产生新的元数据形状，只改变拼写的强制程度），所以它**不是 interop 问题**，纯是拼写与可读性的权衡——按 `spec-scripting-dialect.md:258` 的先例（该 spec 把「从 `.csx` 迁移要改写多少」当公开代价来记），B 是 `static`↔`Shared` 的一对一、迁移零改写，G 让关键字消失、迁移要删词。但它要付三样东西，缺一不可：

- **范围严格限于带 `<Extension>` 的顶层成员**（提案已写对）；把整个脚本类隐式共享会推翻方言的实例模型。
- **规范必须把「失去实例上下文」写成明文规则**（`spec-scripting-dialect.md:60` 现在说的是「顶层 `Sub`/`Function` 默认是实例成员、可读写顶层 `Dim`」，G 会让一段代码「加个属性就换了共享性」，出错要等作者写完方法体才响）。
- **注入点必须先落地，而它不在 `Binder_Utils.vb:91`。** 复会重读了那一行所在的函数：`MapKeywordToFlag(syntax As SyntaxToken)`（`Binder_Utils.vb:85`）**只收一个语法 token**——没有 binder、没有属性表、没有容器上下文，属性**结构上注不进这一行**。我们原先把风险写成「属性识别是否早于修饰符判定」的**顺序**问题，复会复核后改口：`flags` 是 `SourceMemberMethodSymbol` 构造函数的**入参**（`SourceMemberMethodSymbol.vb:72`）、`_quickAttributes` 才在 **ctor 体内**由 `QuickAttributeChecker` 算出（`:85`），「标志先算好、属性后识别」是构造顺序的事实；但可行注入点在属性解码/符号构造期，代价是给 `DecodeConstructorModifiers`/`DecodeMethodModifiers`（`SourceMethodSymbol.vb:417-420` 只收 `SyntaxTokenList`）一路加参数。这是**有界的重构，不是一行判据**。

三道前置与两道闸门（缺一不可）：范围严格限于带 `<Extension>` 的顶层成员（提案已写对，把整个脚本类隐式共享会推翻方言的实例模型）；规范必须把「失去实例上下文」写成明文规则（`spec:60` 现在说的是顶层 `Sub`/`Function` 默认是实例成员、可读写顶层 `Dim`，G 会让一段代码「加个属性就换了共享性」，出错要等方法体写完才响）；闸门 **G1** 改写为「**注入点 + `IsShared` 全部消费者清单**」（已知至少 `SourceMethodSymbol.vb:1504`、`:1634`、`Binder_Expressions.vb:2612`）已被逐条覆盖。**新增前置闸门 G0（先于 G1）**：G 必须正面回答——`spec:16` 的映射表把顶层 `Sub`/`Function` 的共享性**唯一地**交给 `Shared` 这个词，而 `SourceMemberMethodSymbol.vb:86-89` 的现有机制只把属性当**减项**（不满足容器白名单就把它抹掉）、**从不添加修饰符**，C# 在同一位置也没有属性豁免（`SourceOrdinaryMethodSymbol.cs:243` 只看 `IsStatic`）——那么「让属性决定共享性」是否构成 `spec:33` 所说的**第二种做事方式**。**G0 不过，即使 G1 通过也不复活。** G2（B 的书写成本被证明是真实阻碍）与 G3（落地时给信息级提示）维持。

**①b（不写 `Shared` 的顶层成员一律按 `Shared`）我们独立定名，并直接否决。** 复会前它被折进「状态静态化」一并定价；复会复核后我们认为这个折法不成立——它改的是**成员默认共享性**这一轴，与「状态承载方式」那一轴代价形状不同：它**静默改掉既有合法代码的语义**（`spec:60` 承诺顶层实例方法可读写顶层 `Dim`，`spec` 自带示例 `spec:83-85` 的 `Function AddOne` 读 `counter` 会当场失效）。按 D4 的 P1 硬约束（不改变合法既有代码的正确语义）应当**直接否决**，理由与状态静态化无关，也与容器种类无关。

**A（非 `Shared` 也当扩展）维持证伪。** 除形状冲突外，更根本的是它拆掉了「扩展方法必须无实例状态」这条前提，而这条前提是 C# `static`、VB `Shared`、模块成员隐式共享三方一致的立场；VB 在这里说不出自己的理由（提案 §5.4 关于 IL `this` 类型错配那一步标推测，我们保留该标注——它不构成判决的依赖，C# 在同位置选择禁止）。复会补一条精度要求：A 的证伪**与容器种类无关**（`LocalRewriter_Call.vb:120-147` 的 `receiver = Nothing` 不读 `TypeKind`），所以容器种类的讨论**不得**拿「A 已否决」当论据或反论据。

### 权衡二：缺口② —— F 是纪律下限，D / 窄 D / E 家族各要付一项硬代价

**F（只补诊断、不改能力）我们采纳为底线级，且它不是「新诊断」。** 三条论据：①C# 在同一位置有 CS1109（嵌套检查，`:230-232`），VB 消费侧的判据也写着「only top level」（`PENamedTypeSymbol.vb:921-936`）——「顶层」这条要求在 VB 里实有，只是声明侧漏了检查；②VB 早就算过同一个谓词，只是用它静默否决收集（`SourceMemberContainerTypeSymbol.vb:3341`），所以 F 判据无需新造；③它落在**声明点**而不是调用点，成本低于 B（不需要碰早期解码）。它同时回应了本流程的一条既有纪律：`../meetings/meeting-scripting-dialect.md:150` 对 `WithEvents`/`Handles` 的裁决逐字「实现挂钩或给显式诊断，二选一，**不接受静默**」——缺口②的形状逐条对应（一个语言规定了必须发生的语义效果在这里静默不发生，只见一条指向别处的 BC30456）。所以 F 不是「可选项」，是**下限**。

F 还有一条只属于 VB 的判断：**在脚本里，调用点不是报告扩展方法问题的可靠位置**——在默认编译选项下，同一类错误会按接收者分裂成四种表现：`String` 接收者给一条**指错方向**的 BC30456、`Object` 接收者**零诊断**、标准模块类型接收者同样不查扩展（`:1180`）、非 `Shared` 声明**直接终止进程**。机理有锚点：`Option Strict Off` 是宿主写死的默认（`VisualBasicScriptCompiler.vb:218`），「成员找不到」因此降级成晚绑定；而 `Object` 接收者连扩展查找都不进（`Binder_Lookup.vb:1178`）。宽松/晚绑定基因决定了诊断只能落在声明点——这是我们对 B 与 F 都投票的第三个理由，也是我们反对「靠强化调用点 BC30456 提示」那种省事做法的理由。

**窄 D（只把 `Module` 放回命名空间层）我们反对当前形态。** 通路确实存在（`DeclarationTreeBuilder.vb:184-188` 的脚本分支已有「Namespace 声明 → `childrenBuilder`」的通路），代价看起来只是一个条件表达式。但它在**技术基线上已经确认会拿走一项今天成立的能力**：本轮 REPL 实测「提交 1 声明顶层 `Module M` / `Function F()`，提交 2 `? M.F()`」输出 `7`——**顶层 `Module` 在 REPL 里跨提交可见**，与 `Class` 基线同形（提案 §9.2 只对 `Class` 做了实测，对 `Module` 标推测；现在基线存在）。而 `spec-scripting-dialect.md:125` 是一句**规范承诺**：逐字「The lookup covers every member of a previous script class, including the nested types that top-level type declarations produce, so a type declared in one submission can be constructed and used in a later one.」提案的 spec 冲击面清单引的是 `:62`、`:66`、`:48`，**恰恰漏了唯一一句把跨提交可见性写成明文承诺、并因此与窄 D 直接冲突的 `:125`**。按 VB 自己的纪律（「We will almost never make breaking changes to Visual Basic」），破坏一条刚写进规范的跨提交承诺，代价等级高于「引入一个新特性」。提案把窄 D 的代价写成「只断模块的跨提交可见性」——那个「只」字用得太轻。窄 D 还会顺手拿走模块内方法对脚本类顶层 `Shared` 成员的不限定名访问（p9 的 ⑦），并且会留下「`Class` 跨提交可见、`Module` 不可见」的不对称语义。

**D（顶层类型全部搬回命名空间层）我们反对当前形态，理由比提案更独立于 D5。** 提案已按 `decisions.md:42` 的核对得出「这是新特性不是对齐」。我们把它升级为**独立于 D5 成立**（证据级为 C# 源码已检查；本仓 C# 测试不可求值，故「C# 实际报什么」未实测）：C# 的「兄弟类型留命名空间层」只出现在**顶层语句模式**（`acceptSimpleProgram`），而该模式**没有脚本类、没有提交链**，且顶层语句文件里的顶层方法会被 `LocalFunctionSymbol.cs:82-85` 按 `ERR_BadExtensionAgg`（CS1106）拒绝承载扩展方法；C# 14 的 `extension` 块在脚本里同样不可用（`SourceNamedTypeSymbol.cs` 要求容器 `IsStatic && Arity == 0 && ContainingType is null`，**无 `IsScriptClass` 豁免** → CS9283）；`.csx` 里的 `namespace` 被 CS7021 拒绝（对应 VB 的 BC36965）。**C# 里「扩展方法有独立容器」只存在于普通编译（Regular，非顶层语句）**——那正是 VB 的常规模式。D / 窄 D 把「脚本类的容器」与「顶层语句模式的类型落点」拼起来，得到的组合在 C# 里两边都不存在。另加一条 §9.3 的漏洞：它的可行解②（给 `LookupInSubmissions` 加「前序提交的全局命名空间」查找）与 `spec-scripting-dialect.md:127` 冻结的裁定正面冲突——逐字「**Decision**: cross-submission lookup is limited to script class members and host object members. Widening it would make a submission's private implementation details visible to unrelated later code.」

**E 家族我们按机制档位分别裁决，不打包。** ⑧（脚本类免限定名访问 module 成员）与 ⑤（扩展方法双向可见）是**两件不同的事**——一个是普通成员查找，一个是扩展收集。E-a（只放宽 `:3341`）只解 p6、不解 p3，留下「在模块里能调用、在脚本顶层不能调用」的半截边界，**这种边界比现状更难解释也更难写进规范**；而且它服务的场景（让嵌套 `Module` 承载扩展方法）正是 C# 用 CS1109 明确拒绝的场景。E-b 要为「常规 VB 里语法上根本不存在的嵌套 `Module`」定义一套**脚本专有**的扩展收集语义（VB 对此的 bar 很高：`vblang\meetings\2018\vbldm-notes-2018.06.13.md:34` 逐字「our bar for expansion of the surface area - making a second way to do things - will be relatively high even when it's a good idea」），要新引入遍历面与缓存，还要处理 `seenContainingTypes` 的分组约束。E-c 改的是**每一次名字查找**的语义，直接对抗 `spec-scripting-dialect.md:66` 已经写出的作用域规则，回归面与 IDE 名字枚举面是十一条里最大的。三条都在「让嵌套 `Module` 的扩展方法能用」这一件事上，而 F 已经用声明点诊断把同一件事收口；**在这个前提下 E 家族没有剩下要服务的场景**，故三条均不采纳。

### 权衡三：缺口④ —— H 是唯一「不加重语言表面」的一条，但它带三条附加条件

我们强推 H（给提交链加扩展容器节点）。理由是它**不新增语法、不新增写法、不新增修饰符规则、不动声明模型**——十一条里只有它「只把机制补完」；它补的是一个被上游自己标记过的缺口（两处 `' TODO (tomat): extension methods`，且 `BinderFactory.vb:176` 的原注释自陈设计意图是 `we'll need to plug-in submissions`）；并且 VB 在这一点上**说不出自己的理由**：`AllowsExtensionMethods` 的容器判据、晚绑定、`Overloads`/遮蔽、proximity 都没有一条能解释「成员能跨提交、扩展不能」（机理链已复核；「无 VB 特有理由」这一结论是推测）。按 D5 的口径，缺口性质是**移植不完整**。不做它的后果是半截能力：扩展方法在 REPL 里活不过一行——而这恰恰是方言最核心的承诺。三条附加条件必须写进裁决：

1. **形态取 (a)**：新增一个对齐 `InSubmissionClassBinder` 的 binder 类型、override `CollectProbableExtensionMethodsInSingleBinder`，**装入条件对齐 `IsSubmissionClass`**。形态 (b)（把提交链知识塞进 `NamedTypeBinder`）不可取：`NamedTypeBinder` 是**通用**的，同时服务 Regular 模式的隐式类（`BinderFactory.vb:163-170`）与 `TypeBlockFull`（`:206-214`），塞进去会让 Regular 编译也带上提交链知识——C# 正是为此才另立 `InSubmissionClassBinder` 且只在 `isSubmissionClass` 时装入。
2. **落地前先补登一条既有分歧。** H 要碰的区域**已有未登账的 fork 分歧**：`upstream-merge.md` §2 没有 e307d0f「Consume shared interface and extension everything」的条目，而该 commit 改了 `NamedTypeBinder.CollectProbableExtensionMethodsInSingleBinder` 的签名（加了 `extensionMembers As ArrayBuilder(Of Symbol)` 参数并在方法内追加了 `AppendProbableExtensionMembers`）。也就是说 H 的 3-way 评审**缺少该区域的基线记录**；不先补登，「新增一条 ledger 条目」不足以让评审可做。
3. **范围必须显式收窄到经典扩展方法一路。** `NamedTypeBinder.vb:99-114` 同时收两路：`AppendProbableExtensionMethods`（经典）与 `AppendProbableExtensionMembers`（C# 14 扩展成员，走 `<G>$<hash>` 分组类型）。但 C# 侧**脚本里根本不能声明扩展成员**（CS9283），C# 收集扩展成员还要求容器 `IsClassType() && IsStatic && !IsGenericType`，脚本类不满足——所以 C# 的跨提交收集在脚本类上实际只覆盖经典一路。**扩展成员这一路在脚本里属 VB 独有，只能按 VB 自身语义定价，不得用「对齐 C#」论证它。**

还有一条问法要更正：提案 Unresolved 13② 问「跨提交的 proximity 语义，C# 侧如何算」。**C# 路径的独立全库检索在 `Compilers\CSharp\Portable\**` 对 `proximity` 命中 0 次**（我们未重跑该检索，标 C# 路径已检查）——proximity 是 VB 独有机制（`Binder_Lookup.vb:1206`/`:1256` 从 0 起、每上一级 binder `+= 1`），C# 没有对应算法，「C# 怎么算」无解。正确问法是「**VB 的前序提交候选取第几级**」，且必须由「新旧提交同名扩展方法的重载偏好」用例来定义，否则会在这个点上与 C# 无声分叉。C# 的形状可供参考之处只有一条：它把整条提交链放在**同一个 binder 节点**内遍历，所有提交的候选落在**同一批**、同一 proximity，普通重载决议接管——VB 应照此定义为「前序提交的候选与当前提交同批」，不要发明「新提交优先」。

### 权衡四：测试鉴别力——「它通过了」不等于「它有效」，以及 p10 对裁决的约束

本次复核最值钱的一条发现是：**同一个测试形状，在 C# 是有效鉴别器，在 VB 是空转**。C# 的 `ExtensionMethodTests.cs:3804-3830` 与 VB 的 `:2442-2478` 形状完全相同（`previousScriptCompilation`、`? o.G().F()`、`F` 只在 `source0`、接收者 `Object`）；C# 无晚绑定，找不到成员即 CS1061，所以 `VerifyDiagnostics()` 干净**证明**两个扩展都被解析；VB 侧同样的断言什么都证明不了（主因：`Object` 接收者被排除出扩展查找；副因：Option Strict Off 静默晚绑定）。这不是提案的缺陷，而是移植 C# 脚本功能时的一类系统性测试风险——所以 H / B / G 的验收用例必须避开这个盲区：接收者用**非 `Object`** 类型（如 `String`，p1 的形状）、跨提交调用并**断言返回值**（不能只 `VerifyDiagnostics`），再加一条负例（前序提交漏 `Shared` 时后续提交应报 B/G 的诊断）。既有两个用例要不要一并改，见 RESOLUTION。

另有一条裁决约束必须写进材料：**p10 的雷不能假定不存在**。顶层 `Shared` 字段带初始化器会让宿主 `TypeLoadException`（`Scripting\Core\ScriptBuilder.cs:194` 的 `assembly.GetType(..., throwOnError: true, ...)`），C# 的正解形状已经在（`SourceMemberContainerSymbol.cs:5701-5719` 把提交构造器与静态初始化器构造器拆成两个符号）。B / G / E 的 ⑦ 面都会让脚本类 `Shared` 面被更多使用，从而增大踩到它的概率。我们**不要求本轮修 p10**（它另有登记），但要求：裁决只把 `Shared` 当作**扩展方法必需的成员修饰符**来推广（B 的语法），**不得**顺势宣称「脚本类的 `Shared` 成员面整体可用」。

### 权衡五：复会 —— 「机制上是 class、心智上是 module」要不要换容器种类

复会回到一条此前没有被裁定的方向：**把提交容器的种类从 `TypeKind.Submission` 换成 `Module`**，理由是「写脚本的人很难感知到顶层容器其实是 class，而 VB 习惯把『顶层能直接放声明』理解成 module；把 submission 做成 Module，这层错配就消解了」。我们分两步裁：先数清「错配」在用户能观测到的面上到底有多少，再看换种类的代价落在哪里。

**第一步：把「用户以为自己在写 module」从一句话变成一张可数的表。** 我们逐条读规范与源码，得到 8 个可观测维度（口径限定：只覆盖我们列出的这 8 个，不声称是全集）：

**第二步：四个缺口哪一个挂在容器种类轴上？一个都不是。** 缺口① 的判据是成员修饰符规则（`AllowsExtensionMethods` 读的是 `IsScriptClass`，而 `IsScriptClass` 读 `DeclarationKind`——`NamedTypeSymbolExtensions.vb:108-111`、`SourceMemberContainerTypeSymbol.vb:1297-1298`；注意它与 `IsSubmissionClass`（`NamedTypeSymbol.vb:691-695`，读 `TypeKind`）是**包含**关系而非正交：`IsSubmissionClass ⇒ IsScriptClass`）；缺口② 的判据是 `SourceMemberContainerTypeSymbol.vb:3341` 要求 `_containingSymbol.Kind = SymbolKind.Namespace`，而嵌套类型的 `_containingSymbol` 是**承载类型符号**（`:254-278` 的 `CreateNestedType` 传 `Me`）；缺口④ 的判据是 binder 链上有没有提交节点（`BinderFactory.vb:172-177` 的脚本单元链上只有 `NamedTypeBinder(rootNamespaceBinder, SourceScriptClass)`，`:176` 的原注释自陈 "we'll need to plug-in submissions"）。缺口③ 的形状冲突（`LocalRewriter_Call.vb:120-147`）同样不读 `TypeKind`。

**形态③（容器种类改 Module）：否决，而且是两种不可行。** 最小改法（只改 `DeclarationTreeBuilder.vb:140` 的 `kind`）**源码级不可行**，但理由要换——复会推翻了「构造函数断言当场失败」与「两个谓词当场矛盾」这两条：`DeclarationKind.Module` 会让 `Create` 走 `Case Else`（`SourceMemberContainerTypeSymbol.vb:239-240`）到 `SourceNamedTypeSymbol`，而全仓 `New ImplicitNamedTypeSymbol` **只有一个构造点**（`:237`，只在 `ImplicitClass`/`Script`/`Submission` 三分支内），断言**不可达**；`IsScriptClass` 与 `IsSubmissionClass` 则会**一起变假**，不矛盾。真正的致命点是：`IsScriptClass` 变假 ⇒ `MethodCompiler.vb:564` 的 `If containingType.IsScriptClass Then` 整块不执行、`SourceMemberContainerTypeSymbol.vb:2761` 的 `If Not isShared AndAlso IsScriptClass Then` 也不成立 ⇒ **`<Initialize>`、`<Factory>`、提交构造器一个都不合成**，宿主那侧无处取入口；同时符号实现类被整条换掉，脚本类的 `Friend Or Partial Or NotInheritable`（`DeclarationTreeBuilder.vb:143`）落到 Module 上还要再过 `SourceNamedTypeSymbol` 的模块修饰符检查。完整改造（接受模块全部语义）**不是「成本高」，是换一套语言**：模块成员隐式 `Shared`（`Binder_Utils.vb:1180`）、永不可实例化、`Shared` 反成 BC30433、模块体不能放可执行语句（`types.md:736-742`）、模块不得嵌套在类型里（`types.md:728`）、成员进入所在命名空间的声明空间（`types.md:689`）——它会得到一个**既不是标准模块、也不是提交类的第三种容器**：外表像模块，却仍然要实例化、要放顶层语句、要走 `<Factory>`。**「心智模型一致」这个收益是打折的**，而且它换不到用户手里——**用户看不见 `TypeKind`**，换种类在用户可见面上的净变化只有一项：显式 `Me` 的诊断从 BC36966 变成 BC32001（`Binder_Expressions.vb:2262-2277`）。

**③ 还有一条比已否决的窄 D 更重的代价。** 跨提交名字查找的**入口条件是 `TypeKind`**：`Binder_Lookup.vb:583-584` 是 `Case TypeKind.Submission → LookupInSubmissions`，而 `:580` 把 `Class, Module, Structure, Delegate, Array, Enum` 六个值合在一起走 `LookupInClass`（枚举侧 `:609-613` 同构）。容器变 Module 之后，**上一提交的脚本类走不到 `LookupInSubmissions`，全部成员的跨提交查找改道**——不只是模块的。对照 R9：窄 D 只断「模块的跨提交可见性」就已经因为违反 `spec:125` 的明文承诺被否决；③ 断的是**全部**。这把尺子应当并成同一条纪律：**不得以叙事问题为由改动落点层或容器种类层**。（「断掉」仍是**推测**——入口条件与分派是实锤，运行行为我们没跑。）

**③ 在 D5 那一维上是反向的，而这次复会把 delta 的两个 C# 前提订正了。** 订正后的事实更反对换种类，而不是更支持：`Module` **不是**「C# 没有的种类」——它在**共享枚举**里（`Compilers\Core\Portable\Symbols\TypeKind.cs:58` 的 `Module = 8`，与 `:83` 的 `Submission = 12`、`:93` 的 `Extension = 14` 并列），准确说法是**C# 从不产出它**（`EnumConversions.cs` 无 Module 分支；C# `Portable` 里 `TypeKind.Module` 只有 2 处且都在显示层 `SymbolDisplayVisitor.Types.cs:648/:764`；`IsModuleType` **0 命中**）。而且 **C# 的提交类本来就是 `TypeKind.Submission`**（`EnumConversions.cs:23-24`）——两个编译器在「提交容器」这一格**本来就同形**，共同取舍是「语义不同于普通类时给它一个**专用** `TypeKind`，而不是复用一个语义不符的既有声明形态」。③ 恰好是反方向。元数据侧也赚不到分：换种类后发射成 `sealed class`（`NamedTypeSymbolAdapter.vb:964-977`，**不是** `abstract sealed`）＋ `StandardModuleAttribute`（`SourceNamedTypeSymbol.vb:2639-2644`），但 **C# 的 PE 符号从不产出 Module**（`PENamedTypeSymbol.cs:2232-2288` 无 Module 分支），只有 VB 自己会经 `StandardModuleAttribute` 回读成 `Module`（`PENamedTypeSymbol.vb:1160-1166`）——**C# 生态看不出它是模块，VB 自己却把全部模块语义都激活了**。按 D5（`decisions.md:35-46`）：`:37` 的定案是「架构上让 vbi 追平 csi」、`:44-46` 要求「不能因存在分叉就默认放弃对齐」「要说明为什么 VB 必须分叉」，而 `:45` 那句「VB 有 C# 无的概念：`Module`、`Shared`、晚期绑定」是**要求论证的义务条款，不是许可清单**。③ 拿不出机制理由，只有叙事理由——**而叙事问题不该用机制改动来回答。**

**形态②（保留种类、把顶层状态改成静态）：否决，且它的代价比我们原先记的高。** 机制层对四个缺口零收益（判据见上，一条不挂状态承载方式）。人机工程层我们原先记的「顶层『实例』这一不可感知概念消失」这条收益我们也在复会里打了折：`spec:131` 自己已经写明该机制形状 "is an implementation detail and is not part of the contract of this specification"——**想消掉这句话带来的困惑，改述规范（④）即可，不必动符号/降级/发射/宿主/规范五层**；删掉一个看不见的概念，不会让读规范的人**多知道**任何事，却让 `spec:48/:131/:165` 三段实例叙事在规范里变成说不通的话。复会实跑的那条探针还提供了一个更硬的事实：**顶层 `Shared` 状态跨提交的读写本来就成立**（提交 1 `Shared Tag As String` 不带初始化器 → 提交 2 `? Tag Is Nothing` 得 `True` → `Tag = "hi"` → `? Tag` 得 `"hi"`），所以② 改的**只是「不写 `Shared` 的默认值」**。但复会同时纠正了「那它只是默认值反转、机制已经存在」的读法：`Binder_Expressions.vb:2612` 的 `Not currentMember.IsShared` 修饰的是**引用点所在成员**（`BindSimpleName` 在 `:2570` 传的是 `Me.ContainingMember`），顶层语句的宿主 `<Initialize>` 不是 `Shared`，条件因此成立，**接收者会被造成 `BoundPreviousSubmissionReference`**——VB 全树**没有** C# 那样的 `RequiresInstanceReceiver`（0 命中；C# 的对应物在 `Binder_Expressions.cs:2377-2380` 静态成员直接给 `null` 接收者），VB 只对「共享成员走实例」在 `qualKind = QualifiedViaValue` 时给 BC42025（`Binder_Expressions.vb:3729-3748`），而提交脚本类名 `Submission#N` 写不出来、跨提交状态只能不限定名访问，所以连那条警告都不响。**结论：即便目标成员是 `Shared`，接收者链仍是实例链**，`SynthesizedSubmissionFields` 的实例半边不会因为「状态静态化」而自动失去理由。② 因此不是「默认值反转」，而是**降级层与合成字段的改写**，并且它还要先做 D5 已证实例 1 的构造器拆分（否则顶层 `Shared` 面一扩大就踩到 p10——本轮已实跑复现）。**机制层零收益、代价跨五层、还要背一个前置修复——不采纳。**

**形态④（呈现/叙事层）：采纳，且升级为 ①/B/F/H 的叙事前置。** 它是唯一零机制代价、零回归面（P1 硬约束天然满足）、又正对上面那张对照表缺口的手段。复会给它加一条不可让的附带条件：**它必须说真话——不得把容器讲成模块**；把 1:6 的对照讲清楚，并把「与标准模块相反」登记成显式偏离，而不是制造第二个错配。具体交付物四块：①`spec:48` 除现有否定半句外，补一句正对误读的话（脚本方言里没有模块；顶层 `Module` 是脚本类的嵌套类型（`spec:62`），它不承载扩展方法（F 的诊断）；承载扩展方法的顶层成员必须 `Shared`）；②`spec:308-317` 的 divergence 表加一行「脚本类里的 `<Extension>` 成员必须 `Shared`，与标准模块相反」；③`spec:231-239` 的诊断族表为 B 与 F 各加一行并标 C# 对应物；④（复会新增子项）**诊断措辞承载叙事**——B 不能只报「必须 `Shared`」，要点出「标准模块的成员隐式 `Shared`，脚本顶层容器不是标准模块，所以这里的 `Shared` 是**必需**而不是非法」；F 对齐 CS1109 的两段式并给出替代写法（照 VB 既有会教人的消息体例，如 BC42367）。`spec:234` 的 BC36966 与 `:233` 的 BC36965 已经证明方言愿意用诊断文本承担教学，④-iv 只是把同一条纪律用到 B/F 上，**零新增机制**。

**形态①（拼写层）与上面三者的关系不变**：① ⊥ ②、① 与 ③ 效果互斥（③ 之下 `Shared` 反而非法）、④ ⊥ 全部、H ⊥ 全部。① 的位置仍是 **Table**，但闸门按「权衡一」重写后的版本（G0 前置 + G1 改为注入点与消费者清单）。

**复会的结论一句话**：错配是真的，但它的根在**叙事层与把关点层**，不在容器种类轴；容器**保持 `TypeKind.Submission`**。**收口是 ④（强推）为主、B/F（把关点）为辅、① 为可选后缀。**

### VB 基因对照 / C# 生态对照

- **`<Extension> Shared Function` 在脚本类里，是 VB 规范没有描述过的第三种容器。** 这个组合在标准 VB 里三面夹死：模块里写 `Shared` 是 BC30433（`Binder_Utils.vb:1685-1695` + `Errors.vb:361`），类/结构里写 `<Extension>` 是 BC36551（`SourceMethodSymbol.vb:1627`，消息逐字「Extension methods can be defined only in modules.」，`VBResources.resx:3131`），接口里 `Shared` 也非法。能同时接受 `<Extension>` 与 `Shared` 的容器全 VB 只有脚本类一个，而脚本类是编译器合成的。VB 规范把容器定义成「标准模块」（`vblang\spec\type-members.md:908` 逐字「They can only be declared in standard modules」）与「不可实例化的类型」（同文件 `:921` 的 Note 逐字「…and the containing type is not an open generic type and cannot be instantiated…」；`vblang\spec\types.md:689` 逐字「Standard modules **may never be instantiated**」），而脚本类恰恰**是被实例化的**（`spec-scripting-dialect.md:48` 逐字「a script class is instantiated — once by a submission's `<Factory>`, once by a script file's `<Main>`」）。**结论：能力可以留（C# 做着，VB 说不出不能做的理由），但必须承认它是一条 VB 没有的写法组合**——规范要把「脚本类里的 `<Extension>` 成员必须是 `Shared`」写成**显式方言偏离**（`spec-scripting-dialect.md:308-317` 的 divergence 表目前没有这一行），并且缺口①、②都必须报错而不是断言/静默。
- **C# 的严格只发生在声明侧，消费侧是宽容的（C# 路径的源码级结论，未实测）。** `PENamedTypeSymbol` 一类从元数据判定 `MightContainExtensions` 只要求模块级 `[Extension]` 属性（源码注释：Dev11 起就支持非 static 类上的扩展方法），所以即便 VB 把扩展方法挂在非 static 的脚本类上，C# 消费者照样看得见。**本产品的实际可达面很小**（所有脚本宿主产 in-memory `Submission`，脚本程序集不进 AOT 产物），所以这条是「无损」而非「有收益」。跨语言工具链的形状承诺（`spec-scripting-dialect.md:169`）只覆盖 `<Initialize>`/`<Main>`/`<Factory>`/`Submission#N` 四个名字，**不含类型落点**——D / 窄 D 会让脚本编译的元数据形状出现 C# 工具链没见过的形态（兄弟类型不在脚本类里）；实际影响面未验证（推测），登记为定价项。
- **两条侧路必须照录。** 常规 VB 里作者**写不出**嵌套 `Module`（`Parser\BlockContexts\DeclarationContext.vb:59-62` 对 `SyntaxKind.ModuleStatement` 报 `ERR_ModuleNotAtNamespace` = BC30617，`Errors.vb:469`，消息逐字「'Module' statements can occur only at file or namespace level.」，而同一处的 `ClassStatement`/`StructureStatement`/`EnumStatement` 放行）——脚本模式的降级发生在声明树构造期（`DeclarationTreeBuilder.vb:184-188`），于是 Language 层明令禁止的状态被语义层无声地造了出来。这是缺口②在语言层的出处，也是 F「通用诊断在原理上也成立」的依据。
- **两条破坏面审计。** B / F 只新增诊断，不改既有合法代码的语义（P1 硬约束满足，`decisions.md:51-56`）；H 改的是共享编译器树的 Binding 层，落点须走 `upstream-merge.md` 记账与 3-way 评审；D / 窄 D / E-b / E-c 会改变合法既有代码的行为面（跨提交可见性、名字查找语义），不满足 P1 硬约束。四条候选（C、G、D、窄 D）中，C 与 G 涉及「能力边界」的移动，D 与窄 D 涉及「已承诺行为」的移动。
- **容器种类这一维：两侧本来就同形，且共同取舍是「给专用 `TypeKind`」。** C# 的提交类是 `TypeKind.Submission`（`Compilers\CSharp\Portable\Symbols\EnumConversions.cs:23-24`，非提交脚本类才是 `TypeKind.Class`），VB 的提交类也是 `TypeKind.Submission`（`DeclarationTreeBuilder.vb:140` + `SourceMemberContainerTypeSymbol.vb:175-176` 一侧的 `Submission Or NotInheritable`）。`Module` 在**共享枚举**里存在（`Compilers\Core\Portable\Symbols\TypeKind.cs:58`），但 **C# 从不产出**（`EnumConversions.cs` 无 Module 分支；C# 产线的 `IsModuleType` **0 命中**、`TypeKind.Module` 仅 2 处且都在显示层）；反方向 VB 也不产出 C# 的 `Extension = 14`（`:93`）。所以 C# 的「让 class 容器承载扩展方法」走的是**豁免**（`SourceOrdinaryMethodSymbol.cs:234` 的 `!ContainingType.IsScriptClass`），而不是把类改成模块——**C# 的可参照之处是「类也可以是扩展宿主」，不是「换容器种类」**。元数据侧同理：换种类后 C# 的 PE 符号也读不出「模块」（`PENamedTypeSymbol.cs:2232-2288` 无 Module 分支），只有 VB 自己会经 `StandardModuleAttribute` 回读（`PENamedTypeSymbol.vb:1160-1166`）。

### RESOLUTION:

1. **定性**：本提案是**缺陷基线与候选定价**提案，不是能力提案；四缺口的事实刻画成立（两条独立路径各自复核一致），缺口①③④的「移植不完整」定性在 C# 侧都找得到先例（CS1105 / CS1109 / `InSubmissionClassBinder`），缺口②是 VB 特有形态（`Module` 是 VB 概念）。方案取 **B + F + H**，三者**捆为一体**裁决（B 决定怎么写、F 决定嵌套 `Module` 报什么、H 决定跨提交可不可用）；只取组①而不取 H，作者拿到的仍是一条跨提交断掉的能力。映射 `decisions.md` **D5**（`:35-46`）与 **M2/M7**；按 D4 判 P1 档①（C# 已覆盖、非底层内存机制）。**复会补一句裁定（本 RESOLUTION 为 2026-09-12 聚焦复会的口径）**：脚本容器的种类（`TypeKind.Submission`，class 语义）是方言的**承重承诺**，本议题**不含**容器种类更改；任何 Module 化方向须另立提案，并**先**正面回答 `spec:125`（跨提交可见性明文承诺）与 `spec:66`（顶层声明的作用域不进入嵌套类型体）在 Module 语义下如何成立——即先证明它不是语义冲突，而不是先证成本。
2. **候选 B：采纳（组①主推，P1）。** 维持「脚本类里只有 `Shared` 成员可作扩展方法」，补齐缺失诊断。两处改动**同批落地**：①早期解码侧给 `SourceMethodSymbol.vb:1500-1502` 的条件补 `Me.IsShared` 守卫（消除 `:1504` 断言可达性，止血 p2 的进程终止）；②完整解码侧在 `:1624-1648` 的序列里补分支。诊断**必须点名 `Shared`**（对齐 CS1105 的「must be static」句式，而不是复用 BC36551 的「only in modules」——对脚本类那句话是误导）。`SourceMethodSymbol.vb:1621-1648` 的四条消费点与 `AllowsExtensionMethods` 的四消费点均已逐一复核（`SourceMemberContainerTypeSymbol.vb:3341`、`SourceMemberMethodSymbol.vb:86`、`SourceMethodSymbol.vb:1501`/`:1627`）。**复会加强**：B 是「容器种类不改」这一裁定的**唯一用户可见落点**，所以它的消息除点名 `Shared` 外还要承担叙事职责（见 R21 的 ④-iv）——讲出「标准模块的成员隐式 `Shared`，脚本顶层容器不是标准模块，所以这里的 `Shared` 是必需而不是非法」这层意思；只报「必须 `Shared`」等于补了把关点、没补叙事。
3. **候选 G（复会定名 ①a）：表为可选（Table），不作对外主写法；复活闸门按复会重写。** 与 B **互斥**（同一场景「合法化」vs「报错」二选一）。它的语义与元数据与 B **完全等价**，故不是 interop 问题；作为「低仪式」一侧的糖可以接受，但必须满足三道前置：范围严格限于带 `<Extension>` 的顶层成员（不得扩到整个脚本类）、规范明文写出「失去实例上下文」这条后果、以及**注入点已落地且覆盖全部 `IsShared` 消费者**。**复会改判两处闸门**：原 **G1** 写成「先 spike 证实『属性识别早于修饰符判定』的顺序」——复会重读后确认该表述不准确：`Binder_Utils.vb:85` 的 `MapKeywordToFlag(syntax As SyntaxToken)` **只收一个 token**，属性**结构上注不进那一行**，所以问题不是「顺序」而是**换注入点**；G1 因此改写为「注入点定在属性解码/符号构造期，且 `IsShared` 的全部消费者（至少 `SourceMethodSymbol.vb:1504`、`:1634`、`Binder_Expressions.vb:2612`）都被逐条覆盖」。**新增前置闸门 G0（先于 G1）**：①a 必须先正面回答「`spec:16` 的映射表把顶层 `Sub`/`Function` 的共享性唯一交给 `Shared`，而 `SourceMemberMethodSymbol.vb:86-89` 的现有机制只把属性当减项、从不添加修饰符（C# 同位置亦无属性豁免，`SourceOrdinaryMethodSymbol.cs:243` 只看 `IsStatic`），那么让属性决定共享性是否构成 `spec:33` 禁止的第二种做事方式」——**G0 不过，即使 G1 通过也不复活**（G0/G1 合称 ①a 的复活闸门）。G2（B 的「必须写 `Shared`」书写成本被证明是真实阻碍）、G3（落地时给信息级提示，防「加个属性就换了共享性」）维持。**连带项**：①a 若取代 B，「漏 `Shared` 应报诊断」这一负例**不可表达**，R12 的验收用例要改写为「同形状零诊断」。**①b**（不写 `Shared` 的顶层成员一律按 `Shared`）自复会起**独立定名并独立否决**，见 R22。**D5 的迁移代价口径**：B 是 `static`↔`Shared` 一对一、从 `.csx` 迁移零改写；①a 要删词（`spec-scripting-dialect.md:258` 的既有先例把这类迁移代价当公开代价记录）。
4. **候选 A：否决（Reject，维持证伪）。** 扩展调用要求「接收者作第 0 实参、静态发射」（`LocalRewriter_Call.vb:120-147` 的 `receiver = Nothing` + `method = reducedFrom`），实例成员声明要求「接收者作 `this`、实例发射」（同一 `BoundCall` 的 `ReceiverOpt` 只能是其一）；`StackScheduler.Analyzer.vb:662-683` 的两条分支断言把这个形状钉死。C# 在同位置选择禁止（CS1105）。保留此条仅为记录证伪结论。**复会补一条精度要求**：A 的证伪**与容器种类无关**（`receiver = Nothing` 不读 `TypeKind`），所以容器种类的讨论不得拿「A 已否决」当论据或反论据。
5. **候选 C：否决（Reject，并订正代价定价）。** 提案「缺口④让 C 的代价下降」**不成立**（本 RESOLUTION 为 supersede 口径）：`.vbx` 单提交是主场景、扩展方法在那里 100% 可用（p1 已运行），C 拿走的是主场景的全部；脚本里没有 `Namespace` 可供改道（BC36965），C 之后 `.vbx` 里没有写扩展方法的位置；与 C# 的 `IsScriptClass` 豁免（`SourceOrdinaryMethodSymbol.cs:234`）反向分叉。**复会补一句**：C 的定价**不随容器种类改变**（`AllowsExtensionMethods` 读 `IsScriptClass`，改 `TypeKind` 影响不到它），所以 ③ 不改变 C 的结论。
6. **候选 F：采纳（底线级，P1）。** 它不是新诊断，是**把 C# 有、VB 移植时丢掉的嵌套检查补回来**（CS1109，`SourceOrdinaryMethodSymbol.cs:230-232`，`:234` 的白名单豁免不覆盖它；VB 消费侧 `PENamedTypeSymbol.vb:921-936` 的「only top level」旁证）。落点在 `SourceMethodSymbol.vb:1624-1648` 的序列里、`:1633` 的 `Else` 之前或之内（否则进不去），判据为「承载类型是否嵌套」（`m_containingType.ContainingType IsNot Nothing`）；是否加 `IsScriptClass` 限定见 OPEN QUESTIONS。**用新码**（不复用 BC36551——对嵌套 `Module` 那句话会说反）、消息对齐 CS1109 的两段式（点明位置 + 「嵌套」）。**不需要碰早期解码**（嵌套 `Module` 的 `isExtensionMethod` 本来为 `False`，`:1511`）。F 与 B 落在**同一段序列**，须合并设计诊断码与优先级；「嵌套 `Module` + 非 `Shared`」不可达（模块成员隐式共享），故两条诊断不会同时成立。**复会加强两处**：① F 多一条**VB 自有**的移植论据——消费侧 `PENamedTypeSymbol.vb:925-926` 的注释逐字「Only top level non-generic types with an Extension attribute are valid containers of extension methods.」，判据含 `_container.Kind = SymbolKind.Namespace AndAlso _arity = 0`（`:929`）：也就是说「顶层」这条要求在 **VB 自己的 PE 侧一直有、声明侧漏了**，F 的定性可以更强（不再是「C# 有 VB 没有」，而是「VB 自己两处有、一处漏」）；② **F 与容器种类正交，且 ③ 不能替代 F**——嵌套 `Module` 的 `_containingSymbol` 是**承载类型符号**（`SourceMemberContainerTypeSymbol.vb:254-278` 的 `CreateNestedType` 把 `Me` 传下去），换种类之后 `:3341` 要求的 `Kind = SymbolKind.Namespace` 依旧不成立，静默失效照旧。
7. **候选 H：采纳（强推，P1），形态 (a)。** 新增对齐 `InSubmissionClassBinder`（`Compilers\CSharp\Portable\Binder\InSubmissionClassBinder.cs:34-40`）的 binder 类型，override `CollectProbableExtensionMethodsInSingleBinder`（`Binder_Lookup.vb:1219` 的调用点已现成，链遍历者不用改），装入条件 `IsSubmissionClass`（`TypeKind.Submission`），使 `DeclarationKind.Script`（无链）不受影响。两条 `' TODO (tomat): extension methods`（`:932`、`:2050`）随之收口。**范围显式收窄**：只覆盖经典扩展方法一路；C# 14 扩展成员一路在脚本里属 VB 独有（C# 脚本内不可声明——CS9283；C# 收集要求 `IsClassType() && IsStatic && !IsGenericType`，脚本类不满足），只能按 VB 自身语义定价。**前置硬条件**：先补登 `upstream-merge.md` 里 e307d0f 对 `NamedTypeBinder.CollectProbableExtensionMethodsInSingleBinder` 签名的既有分歧（现无条目），否则 3-way 评审无基线可对。**形式 (b) 否决**（会把提交链知识放进 Regular 编译也走的 `NamedTypeBinder`）。**复会补一条维护约束**：H 的装入条件**绑定在容器种类上**（`IsSubmissionClass` = `TypeKind.Submission`，`NamedTypeSymbol.vb:691-695`），所以任何容器种类方向的改动都必须**同步复核 H 的装入点**。
8. **跨提交 proximity 必须定义在 VB 自身语义内（本 RESOLUTION 为 Unresolved 13② 的 supersede 口径）。** `proximity` 在全 `Compilers\CSharp\Portable\**` **零命中**——它不是 C# 机制，「C# 怎么算」这个问法作废。C# 可参照之处只有「整条提交链在同一个 binder 节点内遍历、所有候选同批同 proximity」。VB 应定义为「**前序提交的候选与当前提交同批**」，不发明「新提交优先」；该取值须由「新旧提交同名扩展方法的重载偏好」用例落定。
9. **候选 D / 窄 D：否决当前形态（Reject）。** 窄 D 的技术基线已确认会拿走今天成立的能力（**顶层 `Module` 在 REPL 里跨提交可见**，本轮实测 `? M.F()` → `7`），并直接违反 `spec-scripting-dialect.md:125` 的规范承诺；同时保不住 p9 的不限定名访问、留下 `Class`/`Module` 跨提交可见性的不对称。D 的定性是**新特性**（不依赖 D5 也可独立成立：C# 顶层语句模式无脚本类无提交链且顶层扩展方法被 CS1106 拒绝、C# 脚本里扩展块被 CS9283 拒绝、`.csx` 里 `namespace` 被 CS7021 拒绝——「脚本编译 + 命名空间层兄弟类型承载扩展方法」这个组合 C# 两边都没有），且其 §9.3 的可行解②与 `spec-scripting-dialect.md:127` 冻结的裁定（跨提交查找限于脚本类成员与宿主对象成员）**正面冲突**。二者若要重提，须另立提案并正面回答「跨提交还看得见吗」。**复会把这一条扩为通用纪律（③ 与 D / 窄 D 共用同一把尺子）**：**不得以叙事问题为由改动落点层或容器种类层**——窄 D 只断「模块的跨提交可见性」就已经因违反 `spec:125` 被否，而把容器种类改成 `Module` 会让上一提交的脚本类走不到 `LookupInSubmissions`（入口条件 `Binder_Lookup.vb:583-584` 是 `TypeKind`；`:580` 把 `Module` 与 `Class` 等六值合列走 `LookupInClass`，枚举侧 `:609-613` 同构），**全部成员**的跨提交查找一起改道，比窄 D 重一个量级。标注口径：「改道」的入口条件与分派是**实锤**，「断掉」是**推测**（运行行为未跑）。
